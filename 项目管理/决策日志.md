## D-002 · ST Agent 采用「主干开发 + 短生命周期任务分支 + Conventional Commits（中英混排·带任务号）」

- **背景**：`项目管理/` 执行层落地后缺一份入库规范；需在「单人 + AI Agent、严格对齐任务账本工作流、本地优先数据主权」前提下确定 Git 分支模型、提交约定与文档落点。

## D-004 · 权限作用域匹配口径跨任务统一（剥 `<>` 包裹 + `*.x` 兼匹配裸域 `x`）

- **背景**：T-L1-001.3 执行沙箱需按 01 §10 权限声明做范围匹配。实测 `parse_permission`（T-SC-001 实现，已合入）返回的 scope **含 §10 记法的尖括号**（`local_read:<data/cache/**>` → `<data/cache/**>`），官方 Pack 也确实按带括号形态声明；若不统一剥括号，任何消费方直接拿 scope 匹配都会全部判越界。另 `net_access` 声明 `*.baostock.com` 时，L0 同步实际用的逻辑主机名为裸服务名，需约定子域通配是否含裸域。
- **选项**：① 改 `parse_permission` 返回裸 scope（动已合入的 T-SC-001 契约实现，波及其测试）；② 消费方各自剥括号（口径可能漂移）；③ 定一条跨任务统一规则并各消费方遵循；④ 子域通配 `*.x` 是否兼匹配裸域 `x`（是 / 否）。
- **决策**：③ + ④（是）。**权限声明以带 `<...>` 的完整形态为准**，消费方匹配前剥掉外层 `<>`（本仓库实现见 `st_agent.l1.sandbox._scope_of`）；`net_access` 的 `*.example.com` **同时匹配裸域 `example.com`**（大小写不敏感，末尾点忽略）。**不改 01 §10 / 不动 `parse_permission`**——以既有实现为准，避免契约实现返工。
- **理由**：①+② 分别引入契约返工与口径漂移；③ 把「带括号声明」这一既有事实固化为可复用的消费规则，后续 T-L1-002（MCP tool→Skill 映射）、T-ECO-002（导入校验流水线）同样要按 §10 声明做范围核对，统一口径即免各自发明。裸域兼匹配是 net 场景的实务需要（`*.baostock.com` 应覆盖 `baostock.com` 本体）。
- **影响**：`st_agent/l1/sandbox/{scopes,sandbox}.py` 交付该口径；01 §10 与 02/03 架构文档**不改**（§10 的 `<path-scope>` 本就按占位记法书写，实际取值含括号，属实现细节）。后续按 §10 做范围匹配的任务复用本口径，勿各自实现。

## D-010 · MCP 客户端自研最小面（不引官方 `mcp` SDK）+ 远程响应经 sender 闭包带回（不动 L0）

## D-011 · PR 合入启用 GitHub auto-merge，取代「等 CI 绿后手动 squash」｜**补充见 D-012**

- **背景**：本仓库自 [D-002](决策日志.md) 起采用「主干开发 + 短生命周期分支 + squash 合入即删分支」，但合入方式一直靠人工守着 CI——历次收口日志反复记同一条：「本仓库仍禁用 GitHub auto-merge（既有结论未变），故合入仍为等 CI 绿后手动 squash」。**该禁用不是配置疏漏，而是平台限制**：GitHub 的 auto-merge **不支持私有仓库 + free 计划**。2026-09-26 负责人指示把惯例改为**启用 auto-merge、CI 通过后自动合入**，并**先行把仓库可见性由私有改为公开**、在仓库设置里手动开启 auto-merge——这两项前置动作均由人完成，不是 Agent 能单方面切换的开关。

- **决策**：**B**——前置动作（仓库改公开 + 手动开启 auto-merge）已由负责人完成；仓库侧 `allow_auto_merge` 现为 `true`。Agent 侧流程固定为 PR 建好后即 `gh pr merge <n> --auto --squash --delete-branch`。
- **理由**：单人 + Agent 场景下「守着 CI」是纯等待成本——CI 已是机器门禁（[D-006](决策日志.md) 落地 `.github/workflows/ci.yml`），人盯不增加任何保证；C 面向并发合并的团队流程，单分支流无收益；D 无需改可见性，但要多养一条自建 workflow，且合并权限落在 workflow token 上，不如平台原生路径清晰——**故改可见性换原生 auto-merge 是负责人的取舍**。**代价要认**：① auto-merge 一旦条件满足即落地，**没有事后补检查的机会**，故把 §5.2 的「人工 / Agent 自查」两条明确前置到**建 PR 之前**；② 又因 squash 提交体取自分支的**单条 commit**，「一任务一条干净 commit」这条既有要求变得更要紧（多 commit 分支会丢掉 `Task:` trailer 保证）；③ **本惯例绑定仓库公开**——若仓库改回私有，auto-merge 随平台限制失效，须退回 A 或改用 D。
- **影响**：[Git协作规范.md](Git协作规范.md) §3.3「合入 / 删除」两条、§3.4 映射表「合入」行、§5.2 新增「合入方式」段、§9 速查卡片同步；此前「收口日志直推 main」的做法仍保留（本次即首次由 PR 走 auto-merge 合入的收口批次）。仓库侧设置**冷读双路确认**：REST `allow_auto_merge` 与 GraphQL `repository.autoMergeAllowed` 均为 `true`。**仓库可见性已由私有改为公开**（负责人决定，2026-09-26）——`docs/` 下的 PRD / 架构规格随之公开可读；这与本项目「本地优先 / 数据主权」的对外姿态不冲突（仓库只有代码与设计文档，无任何用户数据），但**属对外可见性变更，记此备查**。
- **教训（操作面，值得后续复用）**：本条初稿写过一段**因果颠倒**的推理，需留痕以免重犯——「`gh api -X PATCH -F allow_auto_merge=true` 返回 HTTP 200 但值未变」→ 判为「私有 + free 计划不支持」→ 随后换 `-f` 读回 `true` → 又推翻了前一个判断、把功劳归给自己的 PATCH。真相是：**前一个判断方向本来就对**（确为平台限制），而值变 `true` 是**负责人在两次读取之间把仓库改公开并手动开启**的结果。两条教训：① 设置类 API 的返回体可能是**改写前**的回显，不能当作生效证据，须**冷读复核**；② 相隔的两次读取之间若有**外部人工变更**的可能，「我发现值变了」不等于「我改变成功了」——归因前先排除他人操作，否则会留下与事实相反的因果记录。本条已于 2026-09-26 按负责人指正更正。

## D-012 · 补齐 auto-merge 的生效条件：`main` 须有必检规则（ruleset `main-require-ci`）+ 管理员 bypass

- **背景**：[D-011](决策日志.md) 把 PR 合入改为启用 auto-merge，落地后**即刻实测发现只开 auto-merge 达不到「CI 绿后合入」**：GitHub 的 auto-merge 只等**被分支规则要求**的检查，而本仓库 `main` **无分支保护、无 ruleset**（`branches/main/protection` 404、`rulesets` 为空）——auto-merge 于是**无等待对象、立即合入**。三条证据：① PR #20 `mergedAt 07:35:09`；② 其 CI run（SHA `d22c794`）`07:34:49` 启动、合入时仍 `in_progress`；③ 挂 auto-merge 前一刻读 PR 得 `checks: []`、`mergeStateStatus: UNKNOWN`。即当时实际效果是「合入不等 CI」，比原手动流程**更松**，与目标相反。
- **选项**：必检规则——A. 加 ruleset 要求 CI 检查 · B. 不加必检、接受「合入不等 CI」（与目标相反）· C. 关掉 auto-merge 退回手动；直推 main 惯例——D. 给管理员配 `always` bypass、保留「收口日志直推 main」· E. 取消直推、收口日志也走 PR。
- **决策**：人选定 **A + D**。新建 ruleset `main-require-ci`（id `24035392`；`target: branch`、条件 `refs/heads/main`、`enforcement: active`；规则 `required_status_checks` → 必检 `check`，`strict_required_status_checks_policy: false`），并配 `bypass_actors: [{actor_id: 199922225, actor_type: User, bypass_mode: always}]`（API 返回 `current_user_can_bypass: always`）。
- **理由**：**A** 是让 D-011 的目标真正成立的**必要条件**——没有必检，auto-merge 就是「不等 CI 直接合」，把机器门禁（[D-006](决策日志.md)）架空；`strict_required_status_checks_policy: false` 是有意为之：单分支流下不必强制「分支须最新」，免得每次都被要求 rebase。**D** 保留既有「收口日志直推 main」惯例（收口条目天然引用刚合入 PR 的号与 hash，属后置提交），省掉把每次收口都变成一次 PR；代价是管理员可绕过门禁——单人仓库可接受。
- **影响**：`main` 自此拒绝**非 bypass 者**的直推与不合规 PR 合入（必检 `check` 通过才放行）；[Git协作规范.md](Git协作规范.md) §3.3 补「关键机制」与「两条前置条件」、§5.2「合入方式」段补前提。**本批 PR 自身即验证样本**：在「CI 仍在跑」的窗口挂 auto-merge，若 `autoMergeRequest` 非空且 PR 保持未合，机制即成立。
- **教训**：D-011 把「auto-merge 已开」当成「门禁已生效」，**两者不是一回事**——判断这类开关是否达成目标，要看它**等的对象**是否存在（本例：必检规则），而不是看开关自身的值。与 D-011 的「值变了 ≠ 我改成功了」同源：**读配置要读得出行为**。

## D-015 · `Store` 并发口径：分区级互斥（读与写同锁）+ 同目录原子替换 + 删除反序｜**补充见 D-016**

- **背景**：L0 遗留册 [E1](遗留问题/L0-遗留问题.md) —— `T-L1-002.3` 的 GWT-4 全链路用例实证 `Store.put` / `delete` 的「读内存清单缓存 → 重建 → 写回」三步**全程无锁**，同分区并发写者互相覆盖、条目静默丢失（后写者的快照不含前写者的条目，`gateway.query` 查不到该次出网）。[02 §2](../docs/技术架构-v2/02-L0-本地优先基座.md) 与 [01 契约](../docs/技术架构-v2/01-平台共享契约.md)（不定义 `Store`）都未写并发口径，故**覆盖范围与锁粒度都是空白**，E1 的「归属」栏原为「人」，即待人定策。
- **选项**：
  - 并发覆盖域 — **A**. 进程内串行化（分区级锁）· **B**. A + 跨进程文件锁 · **C**. 单写者队列
  - 锁粒度与读路径 — **D**. 单把全局锁、读无锁 · **E**. 分区级锁、读也进同一把锁 · **F**. 分区级锁、读无锁 + 读侧不一致重试
  - 落盘原子性 — **G**. 顺带改「同目录 tmp + `os.replace`」原子替换 · **H**. 只加锁、不改落盘
  - 删除顺序 — **I**. 改「先写清单、后删文件」· **J**. 维持「先删文件、后写清单」
- **决策**：**A + E + G + I**（**A / G** 由人于 ④ 对齐选定；**E / I** 为实现期经对齐复述提交人确认）。
- **理由**：
  - **A** 覆盖实证场景与真实调用形态（L1 `StdioTransport` 常驻 pump 线程、`McpHub` 的信令线程与工作线程会同分区落盘）；**B** 的跨进程场景目前只存在于「App 与长跑脚本同开同一 root」的**假设**（无 app / 组合根层，见 L0 册 B1），为它引入平台分支的文件锁不划算——故在 02 §2.4 把该范围**显式排除**，而不是默默不管。
  - **E** 是对 ④ 首轮「读路径无需加锁」判断的**更正**（见下「教训」）：`get` 是「读清单 + 读文件」**两步**，写者在「数据文件已替换、清单未更新」的窗口里会让读方拿到不一致配对并抛 `StorageCorruptionError`——那是**假损坏报告**，比丢条目更危险的用户可见故障。**D** 会把 `data_cache`（可含数十 MB 的 `market.db` opaque blob）的写与其余分区耦合；**F** 的重试面更大且仍留窗口。分区级锁 + 读同锁把「同一分区的读写」整体做成一致快照，代价是锁内一次 AES + 一次文件 I/O，无长持有；且**任何路径都不同时持有两个分区的锁**，故无死锁序问题。
  - **G** 因加锁只约束**并发写者**，而读路径真正要的是「不看到半截文件」——非原子写会留下「读到半截密文 / 半截清单」的窗口（写者自身崩溃亦然）；同目录 tmp + `os.replace` 在 Windows / POSIX 均为同卷原子，约 2 行即封住。
  - **I** 因反序（先删文件）在删除中途崩溃会让清单指向已删文件，重开被判**分区损坏**（数据看似损坏）；反序后崩溃只留一个不在清单口径内的**孤儿文件**（无害，由清单驱动的校验忽略它）。这是「失败显式化 / 不留假损坏」在删除路径上的落点。
- **影响**：`src/st_agent/l0/storage/store.py` 的 `Store` 公共 API **签名零变更**，语义增强为「同一进程内、同一分区并发读写安全」；新增私有 `_part_lock`（延迟创建 + 双检的 `RLock`）与 `_atomic_write`，以及 `_part_locks` / `_part_locks_guard`；[02 §2.4](../docs/技术架构-v2/02-L0-本地优先基座.md) 新增「并发访问口径」（保证范围 / 分区间隔离 / **不**保证多进程同开同一 root / 落盘原子性）。**后续消费方（L2 / L3 / L5 / L6 各层对 `Store` 的写入）一律依赖该口径**，不再自行加「并发窗口内单一写者」的退让约定——`tests/l1/test_mcp_lifecycle.py` 的相应注释已随本件更新。**连带**：原子写会在强杀时留下崩溃残留 tmp（大小可达待写文件本身），已登记 [L0 册 E2](遗留问题/L0-遗留问题.md) 待人定策。若将来确需支持多进程并存同一 root，须新增 `D-NNN` 并以 `supersedes: D-015` 指回本条。
- **教训（判断更正，值得复用）**：本条初稿在 ④ 对齐时把「读路径无需加锁」当成结论报给人，理由是「读的是 frozen 清单对象、字典换值在 GIL 下原子」。该理由只覆盖了**清单自身**的读，**漏掉了「清单 + 文件」是两个对象**——写者更新两者之间必然存在一个窗口，读方在该窗口内就会看到不一致配对。**结论**：判断「某读路径是否要加锁」时，要数清该读操作依赖的**共享状态份数**，而不是只验证其中一份是不是原子的。

## D-016 · 原子替换的 Windows 瞬时句柄冲突：`os.replace` 有界重试（3 次，仅 `PermissionError`）｜**补充见 D-017**

- **背景**：`T-L0-008` 把清单与文件落盘改为「同目录 tmp + `os.replace`」（[D-015](决策日志.md)）后，**验证期实测**全量跑出一次偶发失败：`Store.create` 写 `config` 分区清单时 `os.replace` 抛 `PermissionError: [WinError 5] 拒绝访问`（源为刚建的 `.manifest.bin.tmp-<hex>`）。全部样本：全量 7 轮里 1 次（约 2000+ 次建库 / 写盘），单跑、重跑、5 轮压测（345 用例）均不复现——**不可稳定复现**。
- **成因**：Windows 的 `MoveFileEx` 在**源或目标被外部句柄短暂持有**时报 `EACCES`（实时扫描、索引器是常见来源，非本进程持有——已核 `_manifest` / `_verify_partition` 均为 `read_bytes()` 即开即关）。这是 tmp+replace 原子写模式在 Windows 上的**已知代价**：CI 跑 `ubuntu-latest`，**永远照不到**这条。
- **选项**：**A**. 对 `PermissionError` 有界重试（3 次、退避 20/40ms）· **B**. 不加重试，登记遗留待人定策 · **C**. 退回非原子写（`write_bytes` 直写）
- **决策**：**A**（由人于验证期选定；本任务范围内落地）。
- **理由**：**A** 把外部抖动挡在核心写路径之外，且**只**对 `PermissionError` 生效——磁盘满、路径不存在等 `OSError` 不重试，**持续冲突照样显式失败**（不静默、不降级为非原子写），故「失败显式化」原则未被削弱；代价是一次错误路径上的有界 `sleep`（最多 60ms）。**B** 会让本机偶发 `PermissionError` 冒到调用方（数据不损坏，但写入失败），而 CI 永远发现不了、只有人肉偶遇——与 [D-014](决策日志.md) 的「不做变更自然无需走 ⑦」不同，这里**不处理等于把已知缺陷留在核心写路径**。**C** 会牺牲原子性，正是本任务要建立的东西，直接自相矛盾。
- **影响**：`src/st_agent/l0/storage/store.py` 新增模块级常量 `_REPLACE_ATTEMPTS = 3` / `_REPLACE_BACKOFF_S = 0.02`，`_atomic_write` 内加重试循环（`tmp` 在最终失败时照旧清理）。**02 §2.4 的契约不变**（仍要求「原子替换 + 中断只留完整旧版本」）——重试是实现的健壮性手段，不改变对外语义，故**不触发工作流第 ⑦ 步**。**这是本类原子写在本仓库的统一口径**：后续任何新增的 tmp+replace 落盘（如 L2 / L6 的批量写）应复用同一常量与语义，不各造退避。用例 `tests/l0/test_store_concurrency.py` 的 `test_atomic_replace_retries_transient_permission_error`（抖动被吸收）与 `test_atomic_replace_retry_is_bounded_and_leaves_no_tmp`（次数有界 + 残留已清）钉住该口径。
- **参考**：执行日志 `[T-L0-008]` 验证行 · [D-015](决策日志.md) · `src/st_agent/l0/storage/store.py` · `tests/l0/test_store_concurrency.py` · 任务文件假设 A6

## D-020 · 试跑（03 §4 调试协议）的五项落地口径：试跑记录标识独立成契约 ID / 门禁只拦不可执行类 / 试跑不登记输出复用 / 暂停可单步 / 对比只认状态与载荷

## D-022 · 模板库的三项落地口径：template_id 不登记契约 ID / fork 不落盘 / fork 重名加序号

- **背景**：`T-L1-003.5` 落地 [03 §4](../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md) 的「模板库 + 空状态」。§4 只写了两句话（「官方预置工作流模板……可 fork 后修改」「无自建工作流时展示模板库 + 用一句话描述入口」），**未定**：模板标识要不要进 [01 §1](../docs/技术架构-v2/01-平台共享契约.md) 的契约 ID 表、fork 是「只返回 DAG」还是「即落盘」、fork 派生的 `flow_id` base 与用户既有工作流冲突时怎么办。这三条会被 `T-L3-004`（渲染模板库）与 `T-ECO-*`（分享）直接消费，且与 `.4` 已定的「草稿态不落盘、接受是唯一落盘点」「重名即拒」存在**表面冲突**，故一次定案并写明差异属有意。
- **选项**：
  - 模板标识 — **A**. 不登记（`template_id` 只在 L1 进程内寻址，不持久化不分享）· **B**. 登记进 01 §1（`tpl_<名>`，L3 可按它寻址 fork）
  - fork 落盘 — **C**. 不落盘（只返回 DAG，交 `CanvasEditor` 编辑、「接受」落盘）· **D**. fork 即落盘 v1.0
  - fork 重名 — **E**. base 已存在即加序号（`_2` / `_3` …）· **F**. 重名即拒、提示改名
- **决策**：**A + C + E**（三项均由人在 ④ 对齐时逐项选定推荐项，2026-09-26）。
- **理由**：
  - **A**：[01 §1](../docs/技术架构-v2/01-平台共享契约.md) 对登记 ID 的要求是「全局唯一、生成后不可变、**可本地持久化**」——`template_id` 三条都不满足（它是随包发布的常量集合中的键，从未落盘）。先前登记的两例恰是反证：`flow_id`（[D-018](决策日志.md)）与 `trial_id`（[D-020](决策日志.md)）**都已落盘**才登记。**B** 有实益（L3 可直接按 id 寻址），但代价是契约变更 + 同步各层文档，换来的只是把一次函数入参变成契约类型——收益不抵 宪法 8 的链路成本。
  - **C**：与 [D-021](决策日志.md) 的「草稿态一律不落盘、『接受』是唯一落盘点」**同构**——fork 产物即「来自模板的草稿」，同样应交编辑面，落盘走「接受」（自带 `ChangeRecord` 变更留痕与回滚单位）。**D** 的两处代价：绕过「接受」路径的变更留痕（fork 出的版本无 `change_id` 可回滚）；用户 fork 后不编辑即产生一个没人要的 v1.0，且再 fork 一次又要去重——而 C 下「fork 两次得同一个 base」正是 A3 想要的语义。

## D-027 · 公共认知 Bundle 的评分 / 评级口径：规则化加权、阈值即分位、归一化等权

- **背景**：[T-L1-004.2](tasks/T-L1-004.2-公共认知Bundle执行器.md) 要落地 03 §2.1 的 6 个执行器，其中 4 个需要「分数 / 评级」而文档只给了关键输出的**名称**（名单变更 diff / 可解释触发原因 / 条件清单 + 满足度 / 热力图 + 风险评级 / 高换手高热度预警 / 机构优选池），没有口径。若各自发明，同一个「风险等级」在 `delisting-risk-scan` 与 `risk-alert` 之间会漂移——而 [T-L1-003.5](tasks/T-L1-003.5-模板库与空状态.md) 的官方模板正是把前者接进后者。
- **选项**：
  - 退市风险打分 — **A**. 四类信号**加权**（面值 0.4 / 盈利 0.3 / 预告 0.2 / 偿债 0.1，合计 1.0）+ 声明参数 `threshold` 作「判 high 的分位」、`threshold/2` 判 medium（选定）· **B**. 等权（每命中 0.25）· **C**. 只输出命中清单不打分
  - 基本面评分 — **D**. 三项指标按**上限归一化后等权平均**（ROE 30% / 净利率 30% / 净利同比 100% 封顶），声明参数 `margin` 作入选分位（选定）· **E**. 加权不同系数 · **F**. 只输出硬条件命中与否
  - 板块热力评级 — **G**. 按板块内 ST 占比分档（≥50% high / ≥25% medium / 其余 low）（选定）· **H**. 按涨跌幅分档 · **I**. 按绝对 ST 家数分档

- **决策**：**A + D + G + J**。
- **理由**：
  - **A**：四类信号的**严重度本就不同**（面值退市是不可逆的硬约束，资产负债率只是提示项），等权（B）会让「仅负债率偏高」与「跌破面值」同分。加权后声明参数 `threshold`（默认 0.8）取得自然语义——「要判 high 至少要命中组合权重 0.8」，`min_value=0`/`max_value=1` 的既有取值域恰好是权重和的值域，种子无需改动（T-L1-004.1 假设 A2：不增删既有参数）。
  - **D**：三项指标量纲不同（ROE / 净利率 / 同比增速），直接相加不可比；**归一化 + 等权**是「不引入第二组主观系数」的最小口径，`NORMALIZATION_CAPS` 集中在一处便于复核。`margin`（默认 0.3，取值域 0–1）从而成为**分数下限**，与种子描述「安全边际下限」字面一致。
  - **G**：板块热力的**输出承诺是「风险评级」**而非涨跌幅排名——ST 占比直接对应「该板块的风险集中度」，与 `st-list-sync` 的名单口径同源；用涨跌幅（H）会让「热力」退化成行情榜。
  - **J**：绝对阈值（K）在牛熊两市会整体误报或整体静默，分位（L）需要全市场排序且语义随样本漂移；**与自身窗口均值比**是唯一的「个体异常」口径——「高换手 / 高热度」本就是相对该标的常态而言。

## D-029 · 信息面采集通道定为「L0 网关直抓」（L1 册 `C1` 承接机制的通道归属）
