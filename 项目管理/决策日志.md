- **决策**：B+A 组合——以现有 frontmatter 依赖图为账本内核（B），叠加 Spec Kit 的 constitution + plan/tasks 精简流程（A）；暂不引入 C 的并行编排。
- **理由**：项目已是「规范先行」文档体系，B 复用度最高、纯本地无平台锁定（与本地优先价值观自洽）；A 补齐缺失的 tasks/verify 执行段；单人场景下 C 成本过高，留作 M2 后提速选项。
- **影响**：新增 `项目管理/` 执行层，不改动 `docs/` 规格；本目录七文件即其落地。

## D-002 · ST Agent 采用「主干开发 + 短生命周期任务分支 + Conventional Commits（中英混排·带任务号）」

- **背景**：`项目管理/` 执行层落地后缺一份入库规范；需在「单人 + AI Agent、严格对齐任务账本工作流、本地优先数据主权」前提下确定 Git 分支模型、提交约定与文档落点。
- **选项**：分支模型 — 主干开发+短分支 / GitHub Flow（常驻 PR 审查）/ 纯单分支直推 / Git Flow；提交约定 — Conventional Commits 中英混排+任务号 / 简化任务号前缀+中文 / 纯英文 Conventional；落点与范围 — 全套并联动任务流 / 仅分支+提交精简 / 全套+顺带建脚手架。
- **决策**：主干开发 + 每任务短生命周期分支（squash 合入即删，命名 `type/T-ID-slug`）；Conventional Commits 中英混排（type 英文枚举 + 中文 subject）+ 每条 commit 强制 `Task:` trailer；规范落 `项目管理/Git协作规范.md`（全套：仓库布局/.gitignore/分支/提交/pre-commit+PR 卡点/里程碑 tag），并与工作流、任务账本 `render`、`verify_docs.py`、三日志联动。本轮只写规范，`git init`/`.gitignore`/`.pre-commit-config.yaml` 脚手架留待正式启动开发时执行。
- **理由**：单人场景下 Git Flow/常驻 develop 过重；主干+短分支保持线性历史且与「一任务一文件」的账本粒度天然对齐。任务号 trailer 实现 `git log --grep` 与 `tasks/*.md` 的双向追溯，呼应「无留痕不关闭」。`.gitignore` 单列数据主权红线，因产品核心承诺是本地优先、用户投资数据/密钥零接触，误入库即安全事故。纯本地 Markdown + git 与 D-001「无 SaaS 锁定」自洽。

## D-004 · 权限作用域匹配口径跨任务统一（剥 `<>` 包裹 + `*.x` 兼匹配裸域 `x`）

- **背景**：T-L1-001.3 执行沙箱需按 01 §10 权限声明做范围匹配。实测 `parse_permission`（T-SC-001 实现，已合入）返回的 scope **含 §10 记法的尖括号**（`local_read:<data/cache/**>` → `<data/cache/**>`），官方 Pack 也确实按带括号形态声明；若不统一剥括号，任何消费方直接拿 scope 匹配都会全部判越界。另 `net_access` 声明 `*.baostock.com` 时，L0 同步实际用的逻辑主机名为裸服务名，需约定子域通配是否含裸域。
- **选项**：① 改 `parse_permission` 返回裸 scope（动已合入的 T-SC-001 契约实现，波及其测试）；② 消费方各自剥括号（口径可能漂移）；③ 定一条跨任务统一规则并各消费方遵循；④ 子域通配 `*.x` 是否兼匹配裸域 `x`（是 / 否）。
- **决策**：③ + ④（是）。**权限声明以带 `<...>` 的完整形态为准**，消费方匹配前剥掉外层 `<>`（本仓库实现见 `st_agent.l1.sandbox._scope_of`）；`net_access` 的 `*.example.com` **同时匹配裸域 `example.com`**（大小写不敏感，末尾点忽略）。**不改 01 §10 / 不动 `parse_permission`**——以既有实现为准，避免契约实现返工。
- **理由**：①+② 分别引入契约返工与口径漂移；③ 把「带括号声明」这一既有事实固化为可复用的消费规则，后续 T-L1-002（MCP tool→Skill 映射）、T-ECO-002（导入校验流水线）同样要按 §10 声明做范围核对，统一口径即免各自发明。裸域兼匹配是 net 场景的实务需要（`*.baostock.com` 应覆盖 `baostock.com` 本体）。
- **影响**：`st_agent/l1/sandbox/{scopes,sandbox}.py` 交付该口径；01 §10 与 02/03 架构文档**不改**（§10 的 `<path-scope>` 本就按占位记法书写，实际取值含括号，属实现细节）。后续按 §10 做范围匹配的任务复用本口径，勿各自实现。
- **参考**：执行日志 `[T-L1-001.3]` · `tests/l1/test_sandbox.py::TestScopesAndValidation`

- **背景**：T-L1-001.5（沙箱接线 runner）的 LLM 出网路径需 `llm_transport` 的 `provider → host` 入参，而该映射与「谁构建 `LlmClient` 并注入 `SkillRunner`」在 spec 中未定义。核查（2026-09-26）确认：`tasks/` 与 `docs/` 全量检索无任何**未完成**任务承载 `EndpointRegistry` / `CredentialVault` / `LlmClient` 装配；`src/st_agent/` 无 app/装配层；最接近的调用方 T-L3-002（派发总线）与 T-L1-005（定时调度）均为 bootstrap 空壳。属需登记的未决（[Q-001](阻塞与未决.md)）。

- **决策**：A。`provider → host` 映射暂由 L1 沙箱持有（按 01 §7 `ConfigEntry` 七字段形态持久化于 `config/llm-provider-host/<provider>.json`，提供 `resolve(provider)`）；运行时装配（Store → L0 服务 → L1 运行时 → 交由上层）**新立 T-L1-006** 承载，并由其复核该映射是否迁回 L0。
