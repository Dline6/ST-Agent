## D-002 · ST Agent 采用「主干开发 + 短生命周期任务分支 + Conventional Commits（中英混排·带任务号）」

- **背景**：`项目管理/` 执行层落地后缺一份入库规范；需在「单人 + AI Agent、严格对齐任务账本工作流、本地优先数据主权」前提下确定 Git 分支模型、提交约定与文档落点。

## D-004 · 权限作用域匹配口径跨任务统一（剥 `<>` 包裹 + `*.x` 兼匹配裸域 `x`）

- **背景**：T-L1-001.3 执行沙箱需按 01 §10 权限声明做范围匹配。实测 `parse_permission`（T-SC-001 实现，已合入）返回的 scope **含 §10 记法的尖括号**（`local_read:<data/cache/**>` → `<data/cache/**>`），官方 Pack 也确实按带括号形态声明；若不统一剥括号，任何消费方直接拿 scope 匹配都会全部判越界。另 `net_access` 声明 `*.baostock.com` 时，L0 同步实际用的逻辑主机名为裸服务名，需约定子域通配是否含裸域。
- **选项**：① 改 `parse_permission` 返回裸 scope（动已合入的 T-SC-001 契约实现，波及其测试）；② 消费方各自剥括号（口径可能漂移）；③ 定一条跨任务统一规则并各消费方遵循；④ 子域通配 `*.x` 是否兼匹配裸域 `x`（是 / 否）。
- **决策**：③ + ④（是）。**权限声明以带 `<...>` 的完整形态为准**，消费方匹配前剥掉外层 `<>`（本仓库实现见 `st_agent.l1.sandbox._scope_of`）；`net_access` 的 `*.example.com` **同时匹配裸域 `example.com`**（大小写不敏感，末尾点忽略）。**不改 01 §10 / 不动 `parse_permission`**——以既有实现为准，避免契约实现返工。
- **理由**：①+② 分别引入契约返工与口径漂移；③ 把「带括号声明」这一既有事实固化为可复用的消费规则，后续 T-L1-002（MCP tool→Skill 映射）、T-ECO-002（导入校验流水线）同样要按 §10 声明做范围核对，统一口径即免各自发明。裸域兼匹配是 net 场景的实务需要（`*.baostock.com` 应覆盖 `baostock.com` 本体）。
- **影响**：`st_agent/l1/sandbox/{scopes,sandbox}.py` 交付该口径；01 §10 与 02/03 架构文档**不改**（§10 的 `<path-scope>` 本就按占位记法书写，实际取值含括号，属实现细节）。后续按 §10 做范围匹配的任务复用本口径，勿各自实现。
- **参考**：执行日志 `[T-L1-001.3]` · `tests/l1/test_sandbox.py::TestScopesAndValidation`

## D-011 · PR 合入启用 GitHub auto-merge，取代「等 CI 绿后手动 squash」｜**补充见 D-012**

- **背景**：本仓库自 [D-002](决策日志.md) 起采用「主干开发 + 短生命周期分支 + squash 合入即删分支」，但合入方式一直靠人工守着 CI——历次收口日志反复记同一条：「本仓库仍禁用 GitHub auto-merge（既有结论未变），故合入仍为等 CI 绿后手动 squash」。**该禁用不是配置疏漏，而是平台限制**：GitHub 的 auto-merge **不支持私有仓库 + free 计划**。2026-09-26 负责人指示把惯例改为**启用 auto-merge、CI 通过后自动合入**，并**先行把仓库可见性由私有改为公开**、在仓库设置里手动开启 auto-merge——这两项前置动作均由人完成，不是 Agent 能单方面切换的开关。

- **决策**：**B**——前置动作（仓库改公开 + 手动开启 auto-merge）已由负责人完成；仓库侧 `allow_auto_merge` 现为 `true`。Agent 侧流程固定为 PR 建好后即 `gh pr merge <n> --auto --squash --delete-branch`。
- **理由**：单人 + Agent 场景下「守着 CI」是纯等待成本——CI 已是机器门禁（[D-006](决策日志.md) 落地 `.github/workflows/ci.yml`），人盯不增加任何保证；C 面向并发合并的团队流程，单分支流无收益；D 无需改可见性，但要多养一条自建 workflow，且合并权限落在 workflow token 上，不如平台原生路径清晰——**故改可见性换原生 auto-merge 是负责人的取舍**。**代价要认**：① auto-merge 一旦条件满足即落地，**没有事后补检查的机会**，故把 §5.2 的「人工 / Agent 自查」两条明确前置到**建 PR 之前**；② 又因 squash 提交体取自分支的**单条 commit**，「一任务一条干净 commit」这条既有要求变得更要紧（多 commit 分支会丢掉 `Task:` trailer 保证）；③ **本惯例绑定仓库公开**——若仓库改回私有，auto-merge 随平台限制失效，须退回 A 或改用 D。
- **影响**：[Git协作规范.md](Git协作规范.md) §3.3「合入 / 删除」两条、§3.4 映射表「合入」行、§5.2 新增「合入方式」段、§9 速查卡片同步；此前「收口日志直推 main」的做法仍保留（本次即首次由 PR 走 auto-merge 合入的收口批次）。仓库侧设置**冷读双路确认**：REST `allow_auto_merge` 与 GraphQL `repository.autoMergeAllowed` 均为 `true`。**仓库可见性已由私有改为公开**（负责人决定，2026-09-26）——`docs/` 下的 PRD / 架构规格随之公开可读；这与本项目「本地优先 / 数据主权」的对外姿态不冲突（仓库只有代码与设计文档，无任何用户数据），但**属对外可见性变更，记此备查**。
- **教训（操作面，值得后续复用）**：本条初稿写过一段**因果颠倒**的推理，需留痕以免重犯——「`gh api -X PATCH -F allow_auto_merge=true` 返回 HTTP 200 但值未变」→ 判为「私有 + free 计划不支持」→ 随后换 `-f` 读回 `true` → 又推翻了前一个判断、把功劳归给自己的 PATCH。真相是：**前一个判断方向本来就对**（确为平台限制），而值变 `true` 是**负责人在两次读取之间把仓库改公开并手动开启**的结果。两条教训：① 设置类 API 的返回体可能是**改写前**的回显，不能当作生效证据，须**冷读复核**；② 相隔的两次读取之间若有**外部人工变更**的可能，「我发现值变了」不等于「我改变成功了」——归因前先排除他人操作，否则会留下与事实相反的因果记录。本条已于 2026-09-26 按负责人指正更正。

## D-012 · 补齐 auto-merge 的生效条件：`main` 须有必检规则（ruleset `main-require-ci`）+ 管理员 bypass

- **背景**：[D-011](决策日志.md) 把 PR 合入改为启用 auto-merge，落地后**即刻实测发现只开 auto-merge 达不到「CI 绿后合入」**：GitHub 的 auto-merge 只等**被分支规则要求**的检查，而本仓库 `main` **无分支保护、无 ruleset**（`branches/main/protection` 404、`rulesets` 为空）——auto-merge 于是**无等待对象、立即合入**。三条证据：① PR #20 `mergedAt 07:35:09`；② 其 CI run（SHA `d22c794`）`07:34:49` 启动、合入时仍 `in_progress`；③ 挂 auto-merge 前一刻读 PR 得 `checks: []`、`mergeStateStatus: UNKNOWN`。即当时实际效果是「合入不等 CI」，比原手动流程**更松**，与目标相反。
- **选项**：必检规则——A. 加 ruleset 要求 CI 检查 · B. 不加必检、接受「合入不等 CI」（与目标相反）· C. 关掉 auto-merge 退回手动；直推 main 惯例——D. 给管理员配 `always` bypass、保留「收口日志直推 main」· E. 取消直推、收口日志也走 PR。
- **决策**：人选定 **A + D**。新建 ruleset `main-require-ci`（id `24035392`；`target: branch`、条件 `refs/heads/main`、`enforcement: active`；规则 `required_status_checks` → 必检 `check`，`strict_required_status_checks_policy: false`），并配 `bypass_actors: [{actor_id: 199922225, actor_type: User, bypass_mode: always}]`（API 返回 `current_user_can_bypass: always`）。
- **理由**：**A** 是让 D-011 的目标真正成立的**必要条件**——没有必检，auto-merge 就是「不等 CI 直接合」，把机器门禁（[D-006](决策日志.md)）架空；`strict_required_status_checks_policy: false` 是有意为之：单分支流下不必强制「分支须最新」，免得每次都被要求 rebase。**D** 保留既有「收口日志直推 main」惯例（收口条目天然引用刚合入 PR 的号与 hash，属后置提交），省掉把每次收口都变成一次 PR；代价是管理员可绕过门禁——单人仓库可接受。
- **影响**：`main` 自此拒绝**非 bypass 者**的直推与不合规 PR 合入（必检 `check` 通过才放行）；[Git协作规范.md](Git协作规范.md) §3.3 补「关键机制」与「两条前置条件」、§5.2「合入方式」段补前提。**本批 PR 自身即验证样本**：在「CI 仍在跑」的窗口挂 auto-merge，若 `autoMergeRequest` 非空且 PR 保持未合，机制即成立。
- **教训**：D-011 把「auto-merge 已开」当成「门禁已生效」，**两者不是一回事**——判断这类开关是否达成目标，要看它**等的对象**是否存在（本例：必检规则），而不是看开关自身的值。与 D-011 的「值变了 ≠ 我改成功了」同源：**读配置要读得出行为**。

## D-015 · `Store` 并发口径：分区级互斥（读与写同锁）+ 同目录原子替换 + 删除反序｜**补充见 D-016**

- **背景**：L0 遗留册 [E1](遗留问题/L0-遗留问题.md) —— `T-L1-002.3` 的 GWT-4 全链路用例实证 `Store.put` / `delete` 的「读内存清单缓存 → 重建 → 写回」三步**全程无锁**，同分区并发写者互相覆盖、条目静默丢失（后写者的快照不含前写者的条目，`gateway.query` 查不到该次出网）。[02 §2](../docs/技术架构-v2/02-L0-本地优先基座.md) 与 [01 契约](../docs/技术架构-v2/01-平台共享契约.md)（不定义 `Store`）都未写并发口径，故**覆盖范围与锁粒度都是空白**，E1 的「归属」栏原为「人」，即待人定策。
- **选项**：
  - 并发覆盖域 — **A**. 进程内串行化（分区级锁）· **B**. A + 跨进程文件锁 · **C**. 单写者队列
  - 锁粒度与读路径 — **D**. 单把全局锁、读无锁 · **E**. 分区级锁、读也进同一把锁 · **F**. 分区级锁、读无锁 + 读侧不一致重试
  - 落盘原子性 — **G**. 顺带改「同目录 tmp + `os.replace`」原子替换 · **H**. 只加锁、不改落盘
  - 删除顺序 — **I**. 改「先写清单、后删文件」· **J**. 维持「先删文件、后写清单」
- **决策**：**A + E + G + I**（**A / G** 由人于 ④ 对齐选定；**E / I** 为实现期经对齐复述提交人确认）。
- **理由**：
  - **A** 覆盖实证场景与真实调用形态（L1 `StdioTransport` 常驻 pump 线程、`McpHub` 的信令线程与工作线程会同分区落盘）；**B** 的跨进程场景目前只存在于「App 与长跑脚本同开同一 root」的**假设**（无 app / 组合根层，见 L0 册 B1），为它引入平台分支的文件锁不划算——故在 02 §2.4 把该范围**显式排除**，而不是默默不管。
  - **E** 是对 ④ 首轮「读路径无需加锁」判断的**更正**（见下「教训」）：`get` 是「读清单 + 读文件」**两步**，写者在「数据文件已替换、清单未更新」的窗口里会让读方拿到不一致配对并抛 `StorageCorruptionError`——那是**假损坏报告**，比丢条目更危险的用户可见故障。**D** 会把 `data_cache`（可含数十 MB 的 `market.db` opaque blob）的写与其余分区耦合；**F** 的重试面更大且仍留窗口。分区级锁 + 读同锁把「同一分区的读写」整体做成一致快照，代价是锁内一次 AES + 一次文件 I/O，无长持有；且**任何路径都不同时持有两个分区的锁**，故无死锁序问题。
  - **G** 因加锁只约束**并发写者**，而读路径真正要的是「不看到半截文件」——非原子写会留下「读到半截密文 / 半截清单」的窗口（写者自身崩溃亦然）；同目录 tmp + `os.replace` 在 Windows / POSIX 均为同卷原子，约 2 行即封住。
  - **I** 因反序（先删文件）在删除中途崩溃会让清单指向已删文件，重开被判**分区损坏**（数据看似损坏）；反序后崩溃只留一个不在清单口径内的**孤儿文件**（无害，由清单驱动的校验忽略它）。这是「失败显式化 / 不留假损坏」在删除路径上的落点。
- **影响**：`src/st_agent/l0/storage/store.py` 的 `Store` 公共 API **签名零变更**，语义增强为「同一进程内、同一分区并发读写安全」；新增私有 `_part_lock`（延迟创建 + 双检的 `RLock`）与 `_atomic_write`，以及 `_part_locks` / `_part_locks_guard`；[02 §2.4](../docs/技术架构-v2/02-L0-本地优先基座.md) 新增「并发访问口径」（保证范围 / 分区间隔离 / **不**保证多进程同开同一 root / 落盘原子性）。**后续消费方（L2 / L3 / L5 / L6 各层对 `Store` 的写入）一律依赖该口径**，不再自行加「并发窗口内单一写者」的退让约定——`tests/l1/test_mcp_lifecycle.py` 的相应注释已随本件更新。**连带**：原子写会在强杀时留下崩溃残留 tmp（大小可达待写文件本身），已登记 [L0 册 E2](遗留问题/L0-遗留问题.md) 待人定策。若将来确需支持多进程并存同一 root，须新增 `D-NNN` 并以 `supersedes: D-015` 指回本条。
- **教训（判断更正，值得复用）**：本条初稿在 ④ 对齐时把「读路径无需加锁」当成结论报给人，理由是「读的是 frozen 清单对象、字典换值在 GIL 下原子」。该理由只覆盖了**清单自身**的读，**漏掉了「清单 + 文件」是两个对象**——写者更新两者之间必然存在一个窗口，读方在该窗口内就会看到不一致配对。**结论**：判断「某读路径是否要加锁」时，要数清该读操作依赖的**共享状态份数**，而不是只验证其中一份是不是原子的。

## D-016 · 原子替换的 Windows 瞬时句柄冲突：`os.replace` 有界重试（3 次，仅 `PermissionError`）｜**补充见 D-017**

- **背景**：`T-L0-008` 把清单与文件落盘改为「同目录 tmp + `os.replace`」（[D-015](决策日志.md)）后，**验证期实测**全量跑出一次偶发失败：`Store.create` 写 `config` 分区清单时 `os.replace` 抛 `PermissionError: [WinError 5] 拒绝访问`（源为刚建的 `.manifest.bin.tmp-<hex>`）。全部样本：全量 7 轮里 1 次（约 2000+ 次建库 / 写盘），单跑、重跑、5 轮压测（345 用例）均不复现——**不可稳定复现**。
- **成因**：Windows 的 `MoveFileEx` 在**源或目标被外部句柄短暂持有**时报 `EACCES`（实时扫描、索引器是常见来源，非本进程持有——已核 `_manifest` / `_verify_partition` 均为 `read_bytes()` 即开即关）。这是 tmp+replace 原子写模式在 Windows 上的**已知代价**：CI 跑 `ubuntu-latest`，**永远照不到**这条。
- **选项**：**A**. 对 `PermissionError` 有界重试（3 次、退避 20/40ms）· **B**. 不加重试，登记遗留待人定策 · **C**. 退回非原子写（`write_bytes` 直写）
- **决策**：**A**（由人于验证期选定；本任务范围内落地）。
- **理由**：**A** 把外部抖动挡在核心写路径之外，且**只**对 `PermissionError` 生效——磁盘满、路径不存在等 `OSError` 不重试，**持续冲突照样显式失败**（不静默、不降级为非原子写），故「失败显式化」原则未被削弱；代价是一次错误路径上的有界 `sleep`（最多 60ms）。**B** 会让本机偶发 `PermissionError` 冒到调用方（数据不损坏，但写入失败），而 CI 永远发现不了、只有人肉偶遇——与 [D-014](决策日志.md) 的「不做变更自然无需走 ⑦」不同，这里**不处理等于把已知缺陷留在核心写路径**。**C** 会牺牲原子性，正是本任务要建立的东西，直接自相矛盾。
- **影响**：`src/st_agent/l0/storage/store.py` 新增模块级常量 `_REPLACE_ATTEMPTS = 3` / `_REPLACE_BACKOFF_S = 0.02`，`_atomic_write` 内加重试循环（`tmp` 在最终失败时照旧清理）。**02 §2.4 的契约不变**（仍要求「原子替换 + 中断只留完整旧版本」）——重试是实现的健壮性手段，不改变对外语义，故**不触发工作流第 ⑦ 步**。**这是本类原子写在本仓库的统一口径**：后续任何新增的 tmp+replace 落盘（如 L2 / L6 的批量写）应复用同一常量与语义，不各造退避。用例 `tests/l0/test_store_concurrency.py` 的 `test_atomic_replace_retries_transient_permission_error`（抖动被吸收）与 `test_atomic_replace_retry_is_bounded_and_leaves_no_tmp`（次数有界 + 残留已清）钉住该口径。
- **参考**：执行日志 `[T-L0-008]` 验证行 · [D-015](决策日志.md) · `src/st_agent/l0/storage/store.py` · `tests/l0/test_store_concurrency.py` · 任务文件假设 A6

## D-022 · 模板库的三项落地口径：template_id 不登记契约 ID / fork 不落盘 / fork 重名加序号

- **背景**：`T-L1-003.5` 落地 [03 §4](../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md) 的「模板库 + 空状态」。§4 只写了两句话（「官方预置工作流模板……可 fork 后修改」「无自建工作流时展示模板库 + 用一句话描述入口」），**未定**：模板标识要不要进 [01 §1](../docs/技术架构-v2/01-平台共享契约.md) 的契约 ID 表、fork 是「只返回 DAG」还是「即落盘」、fork 派生的 `flow_id` base 与用户既有工作流冲突时怎么办。这三条会被 `T-L3-004`（渲染模板库）与 `T-ECO-*`（分享）直接消费，且与 `.4` 已定的「草稿态不落盘、接受是唯一落盘点」「重名即拒」存在**表面冲突**，故一次定案并写明差异属有意。
- **选项**：
  - 模板标识 — **A**. 不登记（`template_id` 只在 L1 进程内寻址，不持久化不分享）· **B**. 登记进 01 §1（`tpl_<名>`，L3 可按它寻址 fork）
  - fork 落盘 — **C**. 不落盘（只返回 DAG，交 `CanvasEditor` 编辑、「接受」落盘）· **D**. fork 即落盘 v1.0
  - fork 重名 — **E**. base 已存在即加序号（`_2` / `_3` …）· **F**. 重名即拒、提示改名
- **决策**：**A + C + E**（三项均由人在 ④ 对齐时逐项选定推荐项，2026-09-26）。
- **理由**：
  - **A**：[01 §1](../docs/技术架构-v2/01-平台共享契约.md) 对登记 ID 的要求是「全局唯一、生成后不可变、**可本地持久化**」——`template_id` 三条都不满足（它是随包发布的常量集合中的键，从未落盘）。先前登记的两例恰是反证：`flow_id`（[D-018](决策日志.md)）与 `trial_id`（[D-020](决策日志.md)）**都已落盘**才登记。**B** 有实益（L3 可直接按 id 寻址），但代价是契约变更 + 同步各层文档，换来的只是把一次函数入参变成契约类型——收益不抵 宪法 8 的链路成本。
  - **C**：与 [D-021](决策日志.md) 的「草稿态一律不落盘、『接受』是唯一落盘点」**同构**——fork 产物即「来自模板的草稿」，同样应交编辑面，落盘走「接受」（自带 `ChangeRecord` 变更留痕与回滚单位）。**D** 的两处代价：绕过「接受」路径的变更留痕（fork 出的版本无 `change_id` 可回滚）；用户 fork 后不编辑即产生一个没人要的 v1.0，且再 fork 一次又要去重——而 C 下「fork 两次得同一个 base」正是 A3 想要的语义。

## D-027 · 公共认知 Bundle 的评分 / 评级口径：规则化加权、阈值即分位、归一化等权

- **背景**：[T-L1-004.2](tasks/done/M0/T-L1-004.2-公共认知Bundle执行器.md) 要落地 03 §2.1 的 6 个执行器，其中 4 个需要「分数 / 评级」而文档只给了关键输出的**名称**（名单变更 diff / 可解释触发原因 / 条件清单 + 满足度 / 热力图 + 风险评级 / 高换手高热度预警 / 机构优选池），没有口径。若各自发明，同一个「风险等级」在 `delisting-risk-scan` 与 `risk-alert` 之间会漂移——而 [T-L1-003.5](tasks/done/M0/T-L1-003.5-模板库与空状态.md) 的官方模板正是把前者接进后者。
- **选项**：
  - 退市风险打分 — **A**. 四类信号**加权**（面值 0.4 / 盈利 0.3 / 预告 0.2 / 偿债 0.1，合计 1.0）+ 声明参数 `threshold` 作「判 high 的分位」、`threshold/2` 判 medium（选定）· **B**. 等权（每命中 0.25）· **C**. 只输出命中清单不打分

- **决策**：**A + D + G + J**。
- **理由**：
  - **A**：四类信号的**严重度本就不同**（面值退市是不可逆的硬约束，资产负债率只是提示项），等权（B）会让「仅负债率偏高」与「跌破面值」同分。加权后声明参数 `threshold`（默认 0.8）取得自然语义——「要判 high 至少要命中组合权重 0.8」，`min_value=0`/`max_value=1` 的既有取值域恰好是权重和的值域，种子无需改动（T-L1-004.1 假设 A2：不增删既有参数）。
  - **D**：三项指标量纲不同（ROE / 净利率 / 同比增速），直接相加不可比；**归一化 + 等权**是「不引入第二组主观系数」的最小口径，`NORMALIZATION_CAPS` 集中在一处便于复核。`margin`（默认 0.3，取值域 0–1）从而成为**分数下限**，与种子描述「安全边际下限」字面一致。
  - **G**：板块热力的**输出承诺是「风险评级」**而非涨跌幅排名——ST 占比直接对应「该板块的风险集中度」，与 `st-list-sync` 的名单口径同源；用涨跌幅（H）会让「热力」退化成行情榜。
  - **J**：绝对阈值（K）在牛熊两市会整体误报或整体静默，分位（L）需要全市场排序且语义随样本漂移；**与自身窗口均值比**是唯一的「个体异常」口径——「高换手 / 高热度」本就是相对该标的常态而言。

## D-029 · 信息面采集通道定为「L0 网关直抓」（L1 册 `C1` 承接机制的通道归属）

## D-030 · 「单一事实源」粒度改为业务键级（域内多源按行标注）+ `Q-003` 逐域填充策略

- **背景**：定 [Q-003](阻塞与未决.md)（各信息面域的主备口径）时发现，三候选（官方源优先 / 抓取源为主 / 单源无备胎）**都默认「按源分表」**，而这条默认并非来自 §3，而是来自 [数据库设计 §设计原则 1](../docs/数据库设计-BaoStock数据层/00-设计总览.md) 的「**每张表**只有一个写入来源（一个同步任务）」。核查另发现：§3「同域替代源 → 独立源表 + 聚合视图」的触发条件是「新源与 **BaoStock 提供同域同语义数据**」——四域（公告 / 龙虎榜 / 股东 / 舆情）**不在** BaoStock 的五个域内，§3 **从未被触发**；四域全落 §2「异构数据域 → 新建表组」，而 §2 对**域内多源**完全沉默。**即：拦路的是原则 1 的粒度，不是 §3。** 负责人 2026-09-27 决定走这次契约级变更以化解 `Q-003`。
- **选项**：
  - 粒度 — **A**. 维持表级（域内多源一律按源分表 + 聚合视图）· **B**. 改**业务键级**（同实体表内按 `source_id` 分行；表边界按**实体语义**定）（选定）· **C**. 维持表级但为四域开例外
  - `Q-003` 填充策略 — **D**. 全局单一策略（一个候选统管四域）· **E**. **逐域定**（四域拓扑各异）（选定）
- **决策**：**B + E**。
- **理由**：
  - **B（粒度为业务键）**：原则 1 要防的是「**同一事实有两套口径**」，把它绑到**表**是过强的——绑到**业务键**才准确：「同一业务键的记录只由一条源产生」。表边界则应由**实体语义**决定：源会失效、增备、换实现，**实体不会**；用易变的轴（源）做表边界，会让表结构随源变动而翻倍或迁移（§3 自己已预留「回头合并迁移」的口子，正是这个病的自白）。技术面已核：`sync_state.table_name` **无唯一约束**，一表挂多任务、逐源水位本就可行。
  - **四域的真实拓扑证明 §3 的轴用错了**：公告 = **覆盖分片**（巨潮全市 / 深交所仅深市 / 东财仅沪市）；龙虎榜 = **实体粒度不同**（上榜记录 vs 席位明细）；股东户数 = **单源**；舆情 = **双市并行互补**（互动易深市 + 上证e互动沪市）+ 热榜（易腐、另一实体）。**没有一个是「同域同语义的平行替代源」**，故 §3 的模型套不上——这也是 §3 保留不动、只补 §2 的原因。
  - **E（逐域定）**：四域备胎条件差异过大，一个全局选择必然在其中两个域失真（A / B 之辩只对公告与龙虎榜有意义；股东户数与舆情下两个候选退化为同一结果）。
  - **收益（本决策的主要价值）**：**表结构与源策略解耦**——`Q-003` 从**架构问题**降为**填充策略问题**，无论日后定谁为主源，**表都不变**，只改往 `source_id` 里填哪一行；同时「覆盖差异」成为列（`coverage`），使「换了源」与「确实没有数据」**机器可判**，治掉主备方案的固有静默病。
- **影响**：
  - **01 契约不改**（经核）：`announcement_id` 产生方仍为 L0、`dataset_snapshot_id` 仍是 `sync_state` 水位组合——多源只是让水位组合**更长**，形态不变。
  - **改动的文档**：[数据库设计 §设计原则 1](../docs/数据库设计-BaoStock数据层/00-设计总览.md)（粒度改写为业务键级 + 例外界定）· [§2](../docs/数据库设计-BaoStock数据层/00-设计总览.md)（补五条多源子条款，**不重编号**以免全项目的「§3」引用失效）· [§与平台共享契约的映射](../docs/数据库设计-BaoStock数据层/00-设计总览.md) 的 `as_of` 行（多源取保守下界）· [02 §5](../docs/技术架构-v2/02-L0-本地优先基座.md)（同上）· [05 §sync_state](../docs/数据库设计-BaoStock数据层/05-同步策略与新鲜度契约.md)（「表级水位」在多源下读作「该任务所负责的行集合」、水位与新鲜度**按 `task_key` 逐源**）· [05 §indicator_dictionary](../docs/数据库设计-BaoStock数据层/05-同步策略与新鲜度契约.md)（登记 `indicator_source_map` 形态）。
  - **`indicator_dictionary` 的多源承载走纯增量**：新增 `indicator_source_map(indicator_key, source_id, source_api, api_field)`——**不动主键、不改既有种子生成口径**，从而**避开**对已 `done` 的 [T-L0-005](tasks/done/M0/T-L0-005-数据源缓存BaoStock首个源落地.md) 的表结构返工。**该 DDL 与四域表组一并随「多源信息面采集与管理机制」立项落地**（本决策只登记形态）。
  - **`as_of` 取值规则变更**：一域多源时取各源水位的**保守下界（`min`）**——该域数据只完整到最慢那条源，取 `max` 会让新源的水位**掩盖**旧源的陈旧（与 [02 §5](../docs/技术架构-v2/02-L0-本地优先基座.md)「某源不可用 → `unavailable` + 标注最后更新时间」同向）。
  - **与 [L0 册 `E3`](遗留问题/L0-遗留问题.md) 的相互作用**（须留意）：`snapshot_id()` 实测满表约 350 字符、**已越界** `EvidenceRef.ref` ≤128 的约束；多源会让 `sync_state` 任务数增加，**使该组合串更长**，`E3` 的处置（待立项）应一并考虑域内多源后的水位数量。
  - **`Q-003` 随本条定为「逐域填充策略」**：公告 = 权威源优先（巨潮为主，其余按覆盖分片兜底）· 龙虎榜 = 按实体分表、席位明细以交易所官方为主 · 股东户数 = 单源 · 舆情 = 双市并行互补（非主备）+ 热榜按易腐数据。**源选择为建议值，随机制立项的表结构一并复核。**

## D-031 · 文本类信息「表行＋文件」两段承载 + 文档取数面归 L0 + RAG 索引为派生物

- **背景**：[未决 Q-005](阻塞与未决.md) 由负责人 2026-09-26 提出（「文本类信息单独整理为文件存储，便于后续接入 RAG 与 AI 自主查阅文档」）——即公告正文 / 舆情问答 / 新闻等**大文本**的承载形态、查阅面归属与检索派生数据的地位，五个子问题均无口径。**已核实无技术阻塞**：[02 §2.1](../docs/技术架构-v2/02-L0-本地优先基座.md) 的 `data_cache` 分区内容**已明列**「公告 / 行情 / 龙虎榜 / 股东 / 舆情」；[`Store`](../src/st_agent/l0/storage/store.py) 已是「分区＋分区内相对路径 → bytes」的**通用 KV**（`put` / `get` / `list_files` / `delete` / `export_partition` / `wipe_partition`，含逐文件 `digest`+`size` 清单、落盘加密、分区级校验），**文本文件可直接落 `data_cache`，存储层零改动**。
- **选项**：
  - ① 承载形态 — **A**. 表行（元数据）＋文件（正文）两段（选定）· **B**. 仅入库表（正文存表列）· **C**. 文件与表冗余双写
  - ⑤ 备份范围 — **D**. 维持按分区、`data_cache` 整体可选 + 强制风险提示（选定）· **E**. 档案型文本默认纳入（须为备份引入子路径粒度 → 改动已 `done` 的 T-L0-006）· **F**. 不管
- **决策**：**A**（①②③④ 随之，逐项见 [Q-005](阻塞与未决.md) 决议栏）+ **D**。
- **理由**：
  - **A**：**B** 把大文本塞进 SQLite 列——查询、备份、加密三处一起变差（`Store` 是「分区 + 路径」的写入单位，正为大文本设计）；**C** 的冗余没有对应收益（正文无第二消费方需要表内副本）。两段构成**一条记录**、`source_id` 一致，正好落在 [D-030](决策日志.md) 的**业务键级**单一事实源上——「表在而文件缺」判**损坏**、「文件在而表缺」判**孤儿**，不留静默状态。
  - **② 由 ① 直接推出**：既然正文在文件、元数据在表，就不该让证据引用去持**路径**（路径会长、会随目录规约变动）。改为持 **L0 生成的 `announcement_id`**，路径**由其确定性派生**——`EvidenceRef.ref` 上限 128 因此**天然满足**（实测 `ref: Annotated[str, Field(min_length=3, max_length=128)]`）。`announcement_id` 取**业务键摘要**（代码 + 标题 + 披露日期）同时兑现 [D-030](决策日志.md) 的「跨源重复归一化、ID 由 L0 生成」：巨潮与深交所给的同一条公告得**同一 ID**，去重与合并一步到位。**此举亦预防 [L0 册 `E3`](遗留问题/L0-遗留问题.md) 那类越界在公告域重演**（E3 的成因正是标识形态当初未锁）。
  - **③**：**Skill 不直读文件**——与官方 Pack 的既有范式一致（`GWT-5` AST 断言执行器不 import `st_agent.l0.*`，取数只经注入的鸭子类型源）；且「文件缺失 → `unavailable`」只在 L0 判一次。`local_read:<path-scope>`（[01 §10](../docs/技术架构-v2/01-平台共享契约.md)）针对**缓存外**文件，读 `data_cache` 内的缓存数据**不是**它的范围——把缓存访问也纳入该权限会让每个 Skill 都要申请一遍，与「`data_cache` 消费方＝全部 Skill」的既有定位冲突。
  - **④**：RAG 索引可由文件重建，**不是事实源**——若让它参与 `as_of` / 快照口径，就是在拿派生物冒充事实。**落点延后**是刻意的：为一个尚未建的能力先动 [02 §2.1](../docs/技术架构-v2/02-L0-本地优先基座.md) 的七分区表（且 `PARTITIONS` 是代码内的封闭注册表、`validate_partition_name` 会拒绝未注册名），属于为假想需求付费。
  - **D**：档案型文本「源失效即不可重取」是真风险（抓取源随时下线），但**备份体积取决于尚未定的同步范围**——现在决定等于猜。以**零机制成本**的方式对冲：维持按分区的一口径，把风险**强制**写进备份 UI 提示与 [05 的新鲜度契约](../docs/数据库设计-BaoStock数据层/05-同步策略与新鲜度契约.md)（新增「**不可逆缺口**」一节，区分「可换源重取」与「永久缺口」）；并留**触发复核**条件，避免这条决定僵死。
- **影响**：
  - **改动的文档**：[01 §1](../docs/技术架构-v2/01-平台共享契约.md) 的 `announcement_id` 行（形态＝业务键确定性摘要 + 长度有界，**不沿用源方 ID**）· [数据库设计 §多源扩展规约 §2](../docs/数据库设计-BaoStock数据层/00-设计总览.md) 补「文本类信息 → 表行＋文件两段承载」子条款 · [02 §5](../docs/技术架构-v2/02-L0-本地优先基座.md) 补同款一条（含「不涉 `local_read`」）· [02 §8.1](../docs/技术架构-v2/02-L0-本地优先基座.md) 补**备份风险提示（须现于 UI）** · [05](../docs/数据库设计-BaoStock数据层/05-同步策略与新鲜度契约.md) 新增「**不可逆缺口**」段。
  - **不动**：[02 §2.1](../docs/技术架构-v2/02-L0-本地优先基座.md) 的分区表（**不**加第八个分区）、[T-L0-006](tasks/done/M0/T-L0-006-备份恢复完全清空数据留存策略.md) 的备份口径（**不**引入子路径粒度）、`Store` / `schema.sql` / `src/`（存储层本就支持，**零改动**）。

## D-032 · 主档外代码「过滤 + 显式计数」，不扩主档、不放宽外键

- **背景**：[未决 Q-004](阻塞与未决.md) 登记于 [L1 册 `C1`](遗留问题/L1-遗留问题.md) 收口评估——四域（公告 / 龙虎榜 / 股东 / 舆情）带回的标的中，可能有 [`security`](../docs/数据库设计-BaoStock数据层/01-核心实体层.md) 主档**未收录**的代码（北交所 `920xxx` / `8xxxx` 等）。**实测（2026-09-27）**：① [BaoStock API 手册](../docs/BaoStock-API手册/README.md) **全目录无**「北交所 / 北京证券 / `bj.`」，其 `code` 说明一律为「`sh` 或 `sz` + 6 位数字」→ 候选 A 的「须 BaoStock 支持」这一支**不成立**；② 域表 `code` 对 `security` 是**硬外键**（`code TEXT NOT NULL REFERENCES security(code)`），且 [schema.sql](../docs/数据库设计-BaoStock数据层/schema.sql) 首行 `PRAGMA foreign_keys = ON` → 未收录代码**插不进去**，**一条记录即可让整批同步失败**；③ 开源仓库 [`a-stock-data`](https://github.com/simonlin1212/a-stock-data) 专门处理此类前缀（其 #46 修复覆盖 `51x` 沪 ETF / `900x` 沪 B / `920x` 北交所），佐证**这类代码确实会出现在其数据流中**。
- **选项**：**A**. 扩展 `security` 覆盖 `bj.`（须另源补主档）· **B**. 过滤未收录代码 + 显式计数与标注（选定）· **C**. 四域表允许多前缀、放宽 `security` 外键
- **决策**：**B**。
- **理由**：
  - **拒 A（扩展主档）**：`security` 的**权威来源必须唯一**（现为 BaoStock）。为四域的「副产品」补录主档行，会让主档变成**多源融合体**，而融合规则——谁权威、`code_name` / `ipo_date` / `type` 如何补全、如何与 BaoStock 的退市状态（`out_date` / `status`）同步——**尚无口径**。那是 [多源扩展规约 §3](../docs/数据库设计-BaoStock数据层/00-设计总览.md) 量级的工程（独立源表 + 聚合视图 + 迁移判据），为一个副产品付这个价不划算；且北交所是否属产品数据面，本质是**产品范围**判断而非数据工程判断。
  - **拒 C（放宽外键）**：§1「代码一律映射进 `security` 主档」是**刚在 [D-030](决策日志.md) 里被强化**的原则。开豁免口子会让域表 `code` 变成「**有时有主档、有时没有**」，此后每一次 join、每一条筛选 SQL 都要处理两种情形——成本从「一处过滤」变成「**分摊到所有消费方**」，是典型的把局部问题全局化。
  - **取 B 且必须「预过滤」而非「靠报错」**：既有 FK 会让一条未收录记录**炸掉整批**，故同步**必须先按主档成员判定并过滤**，把不可入库的行**计数留痕**。这一点与「静默丢数据」有本质区别——铁律 5（可解释）要求缺口**可见**。
  - **顺带厘清一个语义**：未覆盖交易所的标的在四域表中**恒为空**，这是**已知空集**，与「源端确实没有该记录」的**数据缺失**是两回事；消费面须能区分（靠 `filtered_unmapped` 计数），否则会把覆盖缺口误读为「无风险信号」。
- **影响**：
  - **改动的文档**：[数据库设计 §多源扩展规约 §1](../docs/数据库设计-BaoStock数据层/00-设计总览.md) 补四条子条款（主档权威来源唯一 / 未收录代码过滤 + 显式计数 + 硬外键的预过滤要求 / 已知空集 ≠ 数据缺失 / 扩覆盖属契约级变更）· [01-核心实体层](../docs/数据库设计-BaoStock数据层/01-核心实体层.md) 的 `security` 节补「**覆盖面**」段（沪深两市、不含北交所、未收录代码处理路径）。

## D-033 · 数据快照 ID 契约化：`snapshot_id()` 产出确定性摘要 + 消费方直取（L0 册 `E3` 收口）

- **背景**：[T-L1-004.1](tasks/done/M0/T-L1-004.1-官方Pack装载与数据访问基件.md) 构造证据引用时实测暴露 [L0 册 `E3`](遗留问题/L0-遗留问题.md)——`MarketDb.snapshot_id()` 返回的是**可读水位组合串**，满任务表（20 行 `sync_state`）下**实测 349 字符**（形如 `snap|bs_adjust_factor:-@-|…`），既超出 `EvidenceRef.ref` 与 `DataAnchor.dataset_snapshot_id` 的 **128** 上限（构造即失败），也不合 01 §1 的 `dataset_snapshot_id` 形态。当时的临时处置（[D-026](决策日志.md) 选项 G）是在 **L1 侧**作有界摘要，等于把越界留在 L0、让每个消费方自行兜底。三处须选型：① 改造 `snapshot_id()` 还是另立产出面；② 摘要实现放哪（`announcement_id` / `qa_id` 已有一份住在 `l0/info/sync.py`）；③ 消费方遇到**不合约形态**的源串怎么办。
- **选项**：
  - 改造方式 — **A**. `snapshot_id()` 直接产出契约形态，可读串另立 `snapshot_components()`（人选定）· **B**. 保留 `snapshot_id()` 原样、另加 `dataset_snapshot_id()`（纯增量，但旧方法仍是越界 footgun）
  - 摘要归属 — **C**. 把 `digest_id` 提升到 [contracts/identifiers.py](../src/st_agent/contracts/identifiers.py)，全平台一份（人选定）· **D**. 在 `l0/market/db.py` 内联一份（与 info 重复一份口径）

- **决策**：**A + C + E**。
- **理由**：
  - **A**：`snapshot_id()` 的方法名即 ID 名，返回值就该是那个 ID——留成越界串等于把 E3 的症状留在原地，每个真实消费方仍要自行兜底。而「可读水位」不是事实源（`sync_state` 才是），故降为**复核面**（`snapshot_components()`）；02 §5 的「不另维护快照登记表」不变。
  - **C**：01 §1 已把 `announcement_id` 与 `dataset_snapshot_id` 都定义为「确定性摘要」，同类形态**只能有一份实现**（与 [D-018](决策日志.md) 对 `flow_id` pattern「不另造副本」同一取向）。搬家是纯函数位移：签名与形态不变，`st_agent.l0.info.digest_id` 的公开路径经 `info/sync.py` 的导入保留，既有实现与测试零改动。
  - **E**：`snapshot_ref` 是鸭子类型入口（源可以是 L0 之外的实现），「形态合规」须在**唯一出口**断言掉；违规错误携来源类型与非法值，可定位。拒 F：短串（如 `abc`）会静默变成合法 ref，形态漂移无人察觉——正是 E3 的成因。
- **影响**：`MarketDb.snapshot_id()` 返回值**语义变更**（可读串 → 契约 ID，实测 349 → 25 字符），新增 `MarketDb.snapshot_components()`；`BaoStockSync.dataset_snapshot()` 随新口径（签名不变）；`digest_id` 的首页由 `l0/info/sync.py` 迁至 [contracts/identifiers.py](../src/st_agent/contracts/identifiers.py)；`official.common.snapshot_ref` 去掉二次摘要（删 `SNAPSHOT_REF_LENGTH` 与 `hashlib` 导入），违规显式化。**本决策替代 [D-026](决策日志.md) 的选项 G**（该条其余两项 A / D 不受影响，条目不标废弃）。文档侧：01 §1 `dataset_snapshot_id` 行补形态、02 §5 与数据库设计 05 的锚定句补「取其确定性摘要 + 可读原文另取」。

## D-034 · 确定性摘要 ID 封堵随机产出面：`announcement_id` / `dataset_snapshot_id` 的 `generate()` 拒绝（T-SC-002）

- **背景**：[D-030](决策日志.md) / [D-031](决策日志.md) / [D-033](决策日志.md) 一脉把 `announcement_id`（业务键摘要）与 `dataset_snapshot_id`（水位摘要）定为**确定性摘要**形态，01 §1 亦已照此登记；但契约类型上**没有对应的拒绝**——`AnnouncementId.generate()` / `DatasetSnapshotId.generate()` 至今返回**随机 uuid4**，即存在一条与契约定义相悖的产出面：走它则「跨源同一实体得同一 ID」的幂等性与「同水位同 ID」的可复核性**同时失效**，且失效是**静默**的。[T-L0-011](tasks/done/M0/T-L0-011-数据快照ID有界化与消费方直取.md) 收工时以「观察（未立项）」留痕，2026-09-27 由负责人定案收紧。须选型：① 拒绝的范围；② 文档侧是否同批补措辞；③ 是否沿用既有拒绝机制。
- **选项**：
  - 范围 — **A**. 两类一并封（人选定）· **B**. 只封 `dataset_snapshot_id`（留下公告侧的同形缺口）
  - 文档 — **C**. 代码 + 01 §1 措辞同批补（人选定）· **D**. 只改代码（文档与实现又不同源）
  - 机制 — **E**. 复用既有 `_generated_by`（人选定）· **F**. 新造一类「确定性 ID」基类
- **决策**：**A + C + E**。
- **理由**：
  - **A**：两类的失效模式同形（随机产出即失去幂等 / 可复核），只封一类会让「另一类为什么可以随机」无从回答；且两者的真实产出路径都已存在（`digest_id("ann", …)` / `MarketDb.snapshot_id()`），封堵零成本。
  - **C**：`generate()` 的拒绝是**契约语义**（谁能产出该类 ID），不是实现细节——01 §1 不写，读者只能从代码反推；写进两行后文档与实现可互相对照，机器侧由 `test_not_locally_generated_types_reject_generate` 与 `test_generation_partition_covers_all_kinds` 双向锁定。
  - **E**：`stock_id` / `flow_id` 已用该机制（`_generated_by` 非空即抛 `ContractViolation`，其值即拒绝说明）；复用即零新概念，拒绝措辞风格也与既有两条一致（点名产生方 + 给出正确构造路径）。
- **影响**：`st_agent.contracts.identifiers` 的 `AnnouncementId` / `DatasetSnapshotId` 增 `generated_by`——**`of()` 构造路径不变**，`ID_REGISTRY` 与 14 类清单不变；**全仓无调用方受影响**（2026-09-27 grep：`src/` 中 `generate()` 仅 `TraceId` / `SkillRunId` / `ChangeId` / `TrialId` 四处）。契约测试的两处 parametrize 名单收缩，`StockId` / `FlowId` 的两条同形断言**并入 4 类参数表**。文档侧：01 §1 两行补「**不由本机随机生成**（随机产出即失去幂等与可复核性）」。**未动**：L0 的 ID 产出链路（`digest_id` / `MarketDb.snapshot_id()`）与 L1 的 `snapshot_ref`。

## D-036 · 测试分层与 CI 条件化：全量只在集成关卡与主干发生，文档-only 不跑 `pytest`

- **背景**：全量 `pytest` 实测 **1111 条用例 / 约 4 分钟**（2026-09-27 本机 Windows），而 [Git协作规范 §5.2](Git协作规范.md) 与 [ci.yml](../.github/workflows/ci.yml) 此前要求**每个 PR 都全量**，本地 ⑥ 的「跑测试」也没划范围——改一个解析件也要等全量，⑥ 与 CI 双双被拖慢。须选型：① 代码变更时 CI 的测试范围；② 「文档-only 不跑 CI」怎么落地（受必检规则约束）；③ 本地 ⑥ 的范围口径。
- **选项**：
  - CI 代码范围 — **A**. PR 按变更范围 + `push → main` 全量兜底（人选定）· **B**. 代码变更即全量（改动最小，但每个 PR 仍等全量）· **C**. 全程按范围（主干失去自动全量保护）
  - 文档-only — **D**. `check` 照跑、只跑 `verify_docs`，job 内跳过 `pytest` 步骤（人选定）· **E**. 整个 workflow 用 `paths-ignore` 跳过 + 改 ruleset 去掉必检
  - 本地 ⑥ — **F**. 按层映射 + 跨层廉价套件必跑（人选定）· **G**. 只跑改动对应的单个测试文件 · **H**. 不设映射、由 Agent 当场判断
- **决策**：**A + D + F**。
- **理由**：
  - **A**：PR 要的是「改哪层就快验哪层」，主干要的是「合起来的整体还成立」——两者诉求不同，同口径必然有一头受损。代价是全量失败可能落在**合入之后**（需补修复 commit），但主干有一次全量、集成关卡还有一次装配级全量，风险有兜。
  - **D**：**这是被仓库配置逼出来的唯一可行解，不是偏好**——ruleset `main-require-ci`（id `24035392`）要求的必检 context 就是 `check`，而被路径过滤跳过的 workflow **不报状态**：`paths-ignore` 会让必检永远 pending、**auto-merge 卡死**（与 [D-011](决策日志.md) 同一条链路上的坑）。故「文档-only 不跑 CI」只能实现为 `check` 照跑（`verify_docs` 几秒）+ job 内条件跳过 `pytest`。且文档改动正是 `verify_docs` 的管辖面，留着这一遍有价值。

## D-038 · `ann_type` 语义按源声明（不是内容类型）；沪市舆情走全市场流、窗口按「条数上限」登记（T-L0-013 选型）

- **实测证据（2026-09-27 真实请求）**：
  - **`ann_type` 三源**：**巨潮** `announcementTypeName` 30 行**非空 0**（响应另给 `announcementType` 数字码串，各类目**重叠**——`01010503` 出现在全部 4 个类目 ⇒ **反查类目路线实测排除**）；**东财** `codes[].ann_type` 实测 `'A,SHA'` / `'A,SZA'` / `'A,CYB'` / `'A,KCB,SHA'` ⇒ **证券类别/板块码**，**非**内容类型；**深交所** `bigCategoryId` / `smallCategoryId` 实测该窗口 20 行全 null。

- **选项**：

- **决策**：**`ann_type` 取 A；窗口取 A**。
- **理由**：
  - **`ann_type` 取 A**：三源**没有一个是内容类型**；B 的代价是 **26× 请求 + 跨类去重**（同一公告可属多类），且须新增「类目」承载（巨潮 `category` 是**请求参数**、响应不回传 ⇒ 落库需另存一列）；C 是同一笔契约变更。消费方**暂无**内容类型需求时，B / C 都是先付成本。A 零成本、信息不丢（东财值照落该列），只是**声明它是什么**——与 [D-032](决策日志.md) ③「已知空集 ≠ 数据缺失」同源：**不让一列的语义靠猜**。

## D-040 · L1 组合根的装配口径（映射归属 / 会话解锁 / 生命周期回收 / env 取值 / 取数源注入）（T-L1-006 选型）

- **背景**：定 [`T-L1-006`](tasks/done/M0/T-L1-006-L1运行时装配组合根.md)（拆为 `.1` L0 面 / `.2` L1 能力面 / `.3` MCP 与回收 / `.4` 调度）的装配口径。开工时核出五件事：
  ① **D-005 留待的复核**——`provider → host` 映射（`config/llm-provider-host/<provider>.json`）暂归 L1 沙箱，`provider_hosts.py` 的模块 docstring 明写「最终归属由 `T-L1-006` 复核是否迁回 L0」；实测 [`LlmEndpoint`](../src/st_agent/l0/llm/models.py) **无 host 字段**（只有 `provider` / `credential_id`）。
  ② **L0 册 `B2`**——登录态会话密钥缓存未落地：`Store.open` 每次重跑 PBKDF2 600k（主密钥 + `secrets` 各一次，本机约 0.6s/次）；册内明写「若届时仍不做，须显式记 `wontfix` 而非继续悬空」。
  ③ **L1 册 `B1`**——`config/mcp-lifecycle/<server_id>.json` 在 Server 移除后成孤儿；[03 §5.2](../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md) 的「范围边界」又写 `mcp-lifecycle` **不在**回收范围，两处需要一个不矛盾的落点。
  ④ **env 取值无主**——[`mcp/registry.py`](../src/st_agent/l1/mcp/registry.py) 的注释把「凭据库读取」指给组合根，而 `EnvResolver = Callable[[str], str]` 只给**名字**，不给 `env_refs` 与凭据标识的对应关系。
  ⑤ **取数源注入 vs 硬编码**——官方 Pack 的 `install_official_pack` 必收 `market_query`，唯一现成的实现是 L0 的 `MarketDb`。
- **选项**：
  - 映射归属 — **A**. 维持 L1 沙箱（由组合根构造并注入，注入面不变）· B. 迁回 L0 端点面（须改 [02 §4](../docs/技术架构-v2/02-L0-本地优先基座.md) 新增承载）
  - 会话解锁 — **C**. 组合根持一个已解锁 `Store` 供整个会话复用，**不**做进程内密钥缓存 · D. 按 `(root, 口令)` 缓存已解锁 `Store`（重复 `open` 免 PBKDF2）· E. 整体记 `wontfix`
  - `B1` 销账 — **F**. 只清生命周期**当前态记录**（`McpHubStateMachine.recycle_server` 作为移除序列的另一步），审计留痕不动 · G. 连 `execution_log` 的转移/通知一并清 · H. 不改代码，只把描述改准
  - env 取值 — **I**. 骨架期**环境变量名即凭据标识**（经 `CredentialVault.use` 取值并留痕）· J. 造一张别名表（口径无来源）
  - 取数源 — **K**. 必填注入（`market_query` 无缺省）· L. 缺省硬编码 `MarketDb`
- **决策**：**A + C + F + I + K**（人 2026-09-27 ④ 对齐时逐条选定）。
- **理由**：
  - **A**：映射的**唯一消费方**是 L1 沙箱的 `net_access` 核对（[03 §1.5](../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md)）；`LlmEndpoint` 无 host 字段 ⇒ L0 侧没有天然承载位，迁过去要**新增一处 02 §4 承载**而收益为零。维持 L1 + 由组合根注入，既保住「沙箱的两张表都由装配面给」的现状，也不必为此动架构文档。**拒 B** 的理由是成本/收益比，不是「L1 更合适」——若将来端点面确要按 provider 记 host，须新立 `D-NNN` 并以 `supersedes: D-005` 指回。
  - **C**：`B2` 的痛点是「**每次操作都重新解锁**」，而运行时的使用姿势本就是「一个会话解锁一次、持句柄供全程复用」——`build_l1_runtime(store)` 收的就是已解锁句柄，`open_runtime` 只解锁一次。**拒 D**：真要做进程内缓存，就得让口令或快速校验值在进程内存长驻（`(root, 口令)` 做键即是把口令留着），为一次本可避免的重复派生换一处安全面，不划算；**拒 E**：`wontfix` 等于承认缺口不解决，而本条有结构性解。
  - **F**：Server 移除后「当前态」已无意义（`state_of` 只对已注册 Server 成立），留着即成孤儿；而 `execution_log` 的转移 / 通知是**审计**（[D-024](决策日志.md) 已把它划在回收范围外，且该分区 append-only）。故取「清当前态、留审计」——并把这一句写进 [03 §5.2](../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md) 的「范围边界」：`McpSkillMapper.recycle_server` 不含本条，生命周期记录的清理是**移除序列里的另一步**。**拒 G** 违约 `D-024` 的边界；**拒 H** 会让 `state_of` 继续在孤儿记录上炸。
  - **I**：`EnvResolver` 只给名字，`env_refs` 与 `credential_id` 的对应关系**全仓没有口径来源**——凭空造一张别名表就是拿约定当规格。取最保守的默认（同名），并把它写成**骨架期约定**：将来确需别名表，属**纯增量**（解析器换实现，注册表注入面不变）。
  - **K**：`market_query` 是「官方 Pack 可执行」的前提，而唯一可用的缺省值是 L0 的 `MarketDb`——给它做缺省即把装配面绑死在具体类上，恰是「取数只有一条通道、经注入」要防的。明写必填，调用方（应用层 / `T-INT-001` / 用例）各给自己的源。

## D-041 · 股东户数接巨潮备胎（`backup`）并校正 `avg_shares` 键名（`F6` 立项 · T-L0-014 选型）

- **背景**：定 [L0 册 `F6`](遗留问题/L0-遗留问题.md) 的落地——[D-035](决策日志.md) 当初只把「股东户数无备胎」这一**事实前提**标记失效，把「采不采用巨潮」留给人（且当时证据是**源码佐证、未经实测**）。立项前先在真实源上核完三件事：
  ① **端点可用、鉴权成本≈6 行**：`GET https://webapi.cninfo.com.cn/api/sysapi/p_sysapi1034?rdate=YYYYMMDD` → 200 / `resultcode=200`（`20250630` **5173** 条、`20240930` **5110** 条、`20260630` **5253** 条）；`Accept-Enckey` ＝ **固定密钥 AES-128-CBC-PKCS7(unix 秒)**（`key`＝`iv`＝`1234567887654321`），算法出自 akshare `data/cninfo.js` 的 `getResCode1()`——**不需要** JS 引擎，而 `cryptography` **已是核心依赖**（故 D-035 记的「须先实现 AES 签名」由一笔前置工作量降为 6 行）。
  ② **形状是实质互补、非冗余**：巨潮按**报告期**一次给全市场（`rdate` 仅季末、起点 2017Q1）；东财 `RPT_HOLDERNUMLATEST` 是 **latest-only、无报告期参数**（须按 `END_DATE` 过滤才可得指定期）⇒ [05](../docs/数据库设计-BaoStock数据层/05-同步策略与新鲜度契约.md) 登记的「重拉最近 8 个季度」**对东财实际只重拉最新一期**，更早季末只有巨潮能给。
  ③ **两源同口径**（同报告期逐票对照 **497** 只）：`avg_shares` **逐票完全一致**（皆＝总股本/户数）、`holder_num` **97.6% 一致**（12 票分歧，最大 17%，如 `000488` 93718 vs 77810）。
  同批实测另发现一条**独立缺陷**：东财解析件读 `AVG_FREE_SHARES`，而真实载荷只有 `AVG_HOLD_NUM` ⇒ `shareholder_num.avg_shares` **恒 `NULL`**，且既有用例把 `None` 当**预期**断言住（夹具同样缺键，故测不出来）。
- **选项**：
  - 采用与否 — **A**. 维持现状（只登记不立项，`F6` 常悬）· B. 采用巨潮（立项）· C. 记 `wontfix`
  - 主备方向 — **D**. 巨潮作 `backup`、东财维持主（册中原计划）· E. 巨潮作 `primary`、东财降备（「权威源优先」）
  - 键名缺陷归属 — **F**. 并入本立项同批修 · G. 另立任务
  - 回补 horizon — **H**. 沿用本域已登记的「最近 8 个季度」（不新增参数）· I. 一次性深回补至 2017Q1
- **决策**：**B + D + F + H**（人 2026-09-27 选定，并明示「**接受东财胜出**」）。
- **理由**：
  - **B**：第二源已验证可用、成本≈6 行、请求量极小（8 请求/周）——此时记 `wontfix`（**C**）属「明知可做而不做」，与铁律 5 相悖；维持现状（**A**）则把**已验证**的事实退记成「待验证」，并让 `F6` 常悬。
  - **D**：**覆盖率**是决定项——东财的 `END_DATE` 可为**期中变动日**（实测夹具即 `2026-09-22`），巨潮只给季末；走 **E** 会**丢失**期中变动日期，且同键值不同时由巨潮**覆盖**东财（实测 12/497 票会翻转，最大 17%）。作 `backup` 后写入走 `INSERT OR IGNORE`：只补空缺、**不覆盖**主源（[D-030](决策日志.md) 的主备让位），口径分歧被限制在「主源缺失」的行。**拒 E** 的另一面是回归面：改一个已 `done` 域的主备方向会牵动 `REPLACE` 覆盖行为与既有行。
  - **F**：该缺陷与 `F4`/`F5` **同族**（「列恒空而无人知」，同在 `parse_shareholder_num_em` 的一处取键错误），修它只改一个键名 + 校正夹具；另立任务会让同一文件被两次往返。故并入本立项，并**新登记 `F7`** 留可解释痕迹。
  - **H**：本域水位语义（05）已写「重拉最近 8 个季度」、`window_for` 的 `shareholder_num` 分支已给 2 年窗口——备胎取同一 horizon 即**不新增参数、不改声明口径**。更早历史（2017Q1+）属对该域水位口径的**修订**，须由消费方需求驱动另立任务（**拒 I**：不把「一次性长跑」混进周期任务）。

## D-042 · Skill 侧权限批准落点：平行账本 + 共用语义、键为 base、官方 Pack 声明清空、复合体独立批准（T-L1-009 选型）

- **背景**：[L1 册 `D1`](遗留问题/L1-遗留问题.md) 登记于 [T-L1-005](tasks/done/M0/T-L1-005-定时调度.md) 的 ④ 对齐——[01 §10](../docs/技术架构-v2/01-平台共享契约.md) 要求「能力在安装/挂载时声明权限，**用户逐项批准**」，MCP 侧早有 [`McpPermissionBook`](../src/st_agent/l1/mcp/permissions.py)（`config/mcp-permission/<server_id>.json`），**Skill 侧只有声明、没有批准态**：`SkillRunner.run(approved_permissions=…)` 每次由调用方现给，全仓无持久化批准面。

  本轮开工前先核出三个事实：

  ① **影响已经发生、不是纸面缺口**：[`SkillRunner`](../src/st_agent/l1/runner/runner.py) 有一道**硬门**（`missing = [p for p in descriptor.permissions if p not in approved]` → `validation_failed`），而**官方 Pack 的 12 个 Skill 全部声明了权限**（10 个 `local_read:<data/cache/**>`、2 个 `net_access:<*.baostock.com>`，[`pack.py`](../src/st_agent/l1/skills/pack.py)）。于是调度与试跑对官方 Skill **恒失败**（实测：恢复一条声明即复现 `Skill 'sk_stock_watch_v1.0' 缺少已批准权限：[…]（01 §10）`）。既有用例全靠每个用例现传 `_pack_permissions(registry)` 才跑得动。
  ② **那 12 条是「声明错位」**：[D-031](决策日志.md) ③ 已裁定「读 `data_cache` 内的缓存数据**不是** `local_read` 的范围」，且**官方执行器从不调用沙箱三类出口**（取数全经注入的 `market_query`，grep 为空）——即它们拦不住任何东西，却照样触发硬门。
  ③ **MCP 侧已有完整的「声明 → 批准 → 装载」链**：[`mapping._require_approved`](../src/st_agent/l1/mcp/mapping.py) 明载「未批准不得装载映射」，是本条要镜像的先例。消费接缝也已留好：[`PermissionSource`](../src/st_agent/l1/scheduler/models.py) 协议 + 组合根 `permissions` 参数（`D1` 解封条件要求它**不变**）。

- **选项**：
  - 落点形态 — **A**. 平行账本（对位 `McpPermissionBook`）· **A′**. 平行落点 + **共用语义与簿记**（选定）· **B**. 泛化统一账本（`config/permissions/<kind>/<id>.json`，须动已 `done` 的 MCP 批准链）· **C**. 批准态塞进 `SkillDescriptor`
  - 账本粒度 — **D**. `skill_id`（base+版本）· **E**. `base`（能力身份）（选定）
  - 官方 Pack 口径 — **F**. 保留声明 + 按 `source=="official"` 播种为 `approved` · **G**. **判为声明错位并清空**（选定）
  - 复合 Skill 批准 — **H**. **独立批准**（选定）· **I**. 继承成员批准态
- **决策**：**A′ + E + G + H**（人 2026-09-27 ④ 对齐时逐条选定；A/D 由本条实现口径登记）。
- **理由**：
  - **A′**：簿记语义（声明登记保留既有决定 / 逐项批准与拒绝 / 按状态读取 / 展示措辞 / 注销）在两个账本上**完全同形**，故收进共用基类 [`PermissionBook`](../src/st_agent/l1/permission_book.py)，批准态形态与展示措辞下沉层间中立的 [`contracts/permissions.py`](../src/st_agent/contracts/permissions.py)——**口径只有一份**（[D-004](决策日志.md) / [D-009](决策日志.md) / [D-033](决策日志.md) 的一贯取向）。落点仍**平行**（各持前缀），故 MCP 的落盘布局与公共 API **逐字节不变**（既有 MCP 用例全绿未改）。**拒 B**：泛化要动已收工的关键路径（回归面＝整条 MCP 批准链）而收益仅是「少一个类」；**拒 C**：`SkillDescriptor` 是**可导出/可分享**对象（[09 生态](../docs/技术架构-v2/09-生态与分享.md)），批准是**本地用户决定**，绝不能随分享物外泄；且 `publish_version` 走 `model_dump()` 复制字段，会让新版本**继承陈旧批准**。
  - **E**：批准属于**能力**而非某一版本——按 `skill_id` 落键会让次版本升级（常态操作）把用户已批准的权限打回待批。按 `base` 落键后，声明变化由 `declare` 对账（新声明转 `pending`、移除的丢弃），与「待检查标记按 base 归集」的既有先例同向。**注意一处实现事实**：两账本的**键空间隔离靠前缀、不靠键形态**——MCP 的 `server_id` 形态（`^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$`）比 Skill base **更宽**（`sk_...` 也是合法 `server_id`），故 `config/skill-permissions/` 与 `config/mcp-permission/` 是**两条独立命名空间**（已由用例钉住）。
  - **G**：三条判据同向——[D-031](决策日志.md) ③ 已否 `local_read` 覆盖缓存数据；官方执行器**自身不发**文件/网络/命令行为（[01 §10](../docs/技术架构-v2/01-平台共享契约.md) 的越界拦的是这三类出口，「行为式」enforcement）；故按声明的**语义范围**它们本就没有可声明的权限。清空后官方 Pack **无需批准**即可执行，`D1` 的实际痛点随之消解。**拒 F**：它要产品**替用户造**「已批准」这一事实，与 [D-039](决策日志.md) 否决「取声明即视为已批准」的理由正相抵；且会留下 11 条与 [D-031](决策日志.md) ③ 相抵的声明。顺带澄清一处**沙箱语义**：清空声明**不削弱**沙箱——空声明的会话语义是**更严**（`_check` 对未声明即 `deny`），只是官方执行器本就不走那些出口。
  - **H**：[D-019](决策日志.md) 已定复合 Skill 的 `permissions` 为其成员的**并集**，而复合体是 [D-019](决策日志.md) 下的一等 Skill、**独立展示**给用户；「成员批过」不等于「复合体被展示过」。**拒 I**：继承会让「聚合了一批已批准 Skill」等同于「新契约已被审视」，把一个未展示过的权限面静默放行。
- **影响**：
  - **新增** [`src/st_agent/contracts/permissions.py`](../src/st_agent/contracts/permissions.py)（`PermissionApproval` / `PermissionDecision` / `PERMISSION_KINDS` / `DECISION_LABELS` / `describe_permission`，层间中立）· [`src/st_agent/l1/permission_book.py`](../src/st_agent/l1/permission_book.py)（`PermissionBook` 共用簿记基类）· [`src/st_agent/l1/skills/permissions.py`](../src/st_agent/l1/skills/permissions.py)（`SkillPermissionBook`，落 `config/skill-permissions/<base>.json`）。

## D-043 · 调度规则：里程碑集成关卡在同优先级内取队首；`T-ECO-001` 依赖补齐（工作流「调度规则」/「集成关卡」校正）

- **背景**：负责人对现行调度规则提出两处质疑，逐条实测后**两处都成立**：

  ① **「关卡天然最后就绪」的因果不成立**。[工作流](工作流.md)「集成关卡」原写「层号排序在最后，故它天然最后进入就绪集」——但 `T-INT-*` 何时进就绪集完全由 `depends_on`（已覆盖本里程碑全部叶子）决定，**层号只影响就绪集内的取用顺序**。于是关卡一旦 ready，它本就是该里程碑唯一的收口阻塞项，却仍被排到 L2/L4 之后。实测即此状态：M0 完成 53/54，唯一未 `done` 的正是 [`T-INT-001`](tasks/done/M0/T-INT-001-M0集成关卡骨架打通冒烟.md)，而账本就绪集队首是 `T-L2-001`——按规则取队首，会把 M0 的收口与**全量验证**（「集成关卡」节：全量测试被强制的唯一场景）一直往后推；关卡要兜住的装配缺口，越拖越晚暴露。

## D-046 · `archive` 连带改正相对链接：候选表按「存在性」判定 + 末尾自动 `render`（M0 首次归档暴露）
