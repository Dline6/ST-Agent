# T-UI-002.4.1 · 入口侧口令协商与显式失败分类

## 目标
在后端入口 [`run_backend`](../../src/st_agent/__main__.py) 装配 L0–L4 **之前**，补一段**口令协商**：
本根需要口令时，向 stdout 发 `event=passphrase_required` 并**阻塞等待**壳经**两个进程之间的管道**
回传一行口令，收到后继续装配；口令错误时**有界重试**，超限即以中性原因显式失败。同时把「需要口令」
从**泛化的打开失败**里分出来——现在它只是一条 `StorageOpenError`（与「keyfile 损坏」「格式标记非法」
混在同一类型里），调用方无法只对「给口令就能过」的情形重试。

触发有**两处**（父 `A2`，2026-10-05 开工读码后订正为「探测 + 异常」并用）：
① **开局只读探测**——「凭据已建立」的明文根因装配**幂等**（端点已存在即整组跳过）而**过得去却拿不到
口令**，失败会被推到**第一次读凭据**时，故必须提前拦；② **装配期异常**——凭据**尚未建立**时探测说
不出「要口令」（要不要写凭据由装配决定），且给错口令的重试也走这里。

**不做**：不动存储侧口径（[D-074](../决策日志.md) 已定）；不碰壳侧
（归 [`T-UI-002.4.2`](T-UI-002.4.2-壳侧口令框与OS凭据库记忆.md)）。

## 验收标准（Given-When-Then）
- **GWT-1**：Given 一个**加密根**且未提供口令，When 以 `--ask-passphrase --handshake json` 启动，
  Then **首行**是 `{"event":"passphrase_required","kind":"main_passphrase",…}`（**不是** `error`），
  经 stdin 投递正确主密码后出 `{"event":"ready"…}` 且退出码 0
- **GWT-2**：Given 一个**明文根**且 `.env` 三键齐备、凭据分区**从未建立**，When 首次启动并要求口令，
  Then 收到 `kind="credentials"` 的口令请求；投递口令后按 **TOFU** 设定凭据口令并正常就绪，
  存 `secrets` 分区的凭据可读；**二次**启动同根（此时凭据**已建立**）⇒ **开局探测即索取**
  （**不**依赖「装配先失败一次」）且须投递**同一**口令才通过
- **GWT-3**：Given 连续投递**错误**口令，When 达到上限（3 次），Then 前 3 次每次都回
  `passphrase_required`（带中性 `reason` 与递增 `attempt`），**第 4 次不再请求口令**而以
  `{"event":"error","code":"passphrase_unavailable"…}` + 非零退出显式失败
- **GWT-4**：Given 任一非口令类的打开失败（keyfile 损坏 / 格式标记非法 / 分区损坏），When 启动，
  Then **不**回 `passphrase_required`、**不**重试，直接出 `error`（+ 机器可读 `code`）
- **GWT-5**：Given 未开协商（无 `--ask-passphrase` 且未给 `--passphrase-env`），When 本根需要口令，
  Then **立即**显式失败（`code="passphrase_required"`，原因含「用 `--ask-passphrase` 或
  `--passphrase-env`」的指引），**不阻塞在 stdin 上**
- **GWT-6**：Given 口令经 stdin 投递，When 全流程跑通，Then 口令不出现在**进程 argv**、**子进程环境**、
  **日志输出**与**存储根内的任何文件**中

## 假设与前提
- **A1 · 「需口令」可由异常类型与既有失败路径区分，不必改装配签名**——前提：`Store.open` /
  `unlock_secrets` 是仅有的两处口令入口，把它们改抛 `StoragePassphraseRequired` 即可让入口
  **只对**这一类重试；装配签名（`build_m2_runtime(root, passphrase, create=…)`）不变。
  若错（另有隐藏的口令失败点）：返工面＝异常分类面。验证方式：GWT-4 的参数化用例（三类非口令失败各一）。
- **A2 · 装配可安全重跑（有界次）**——前提：口令失败发生在装配早期（加密根：`Store.open` 第一跳，
  零副作用；明文根凭据：装配中段的凭据写入），重跑一次 `build_m2_runtime` 不会留下不一致状态
  （配置文件按同一内容重写、清单原子替换）。
  若错（重跑留下半截状态）：返工面＝改为「先打开 / 解锁存储、再装配」的两段式入口（须把 `Store`
  属主外移，触到 [`open_runtime`](../../src/st_agent/l1/runtime.py) 的会话入口口径）。
  验证方式：GWT-2 的首次设定与二次启动各跑一次真装配（同一进程内重跑至少一次）。
- **A3 · 协商期间 stdin 只当口令通道**——前提：口令阶段**不**解释停止词（`stop` 一类的口令不被误判），
  阶段结束（收到口令）后 stdin 回到既有停止词 / EOF 语义；两侧都知晓阶段边界，故无歧义。
  若错（阶段边界不清导致误判）：返工面＝通道协议（须加帧）。验证方式：以口令 ``stop`` 实跑一次，
  断言不触发收尾。
- **A4 · 口令经管道而非环境变量**——前提：[00 §1.1](../../docs/技术架构-v2/00-架构总览.md) 定的通道；
  `--passphrase-env` 作为**无交互**路径保留（终端 / 自用），两者并存不构成第二份真相源（同一个输入的两个入口）。
  验证方式：GWT-6 断言 argv / 环境 / 日志 / 落盘四处均无口令。
- **A5 · 无交互时与既有行为一致**——前提：不给握手协商也不给 `--passphrase-env` 时的「加密根无口令
  ⇒ 显式失败」是 [`T-UI-002.1`](T-UI-002.1-生产运行入口与壳后端握手协议.md) 假设 `A3` 已交付的语义，
  本叶**只**给失败行补 `code`、不改变该语义。验证方式：既有 `test_runtime_entry.py` 的加密根用例保持
  绿（必要时只补 `code` 断言）。
- **A6 · 开局探测必需，且判据与 `Store.open` 的分派同源**——前提：`_seed_llm_records` 的播种**幂等**
  （端点已存在即整组跳过），故「凭据已建立」的明文根**装配能过**、口令却始终没到位（失败被推到首次
  读凭据）；探测据此提前索取。判据只读 keyfile 的 `verifier_secrets` 与 `secrets` 分区是否有数据文件，
  与 `Store.open` **共用** `_read_keyfile_meta`，故不另立一套会漂移的模式判定。
  若错（判定与真实需求分叉）：返工面＝探测判据；验证方式：`tests/l0/test_store_format.py` 的
  `TestPassphraseRequirementProbe`（新根 / 从未建立 / 加密 / 已建立 / 只读不校验 / keyfile 损坏六例）
  + 本叶的「已建立 ⇒ 一次装配成功（`seen == ["cred"]`）」与「从未建立 ⇒ 不索取」两例。
