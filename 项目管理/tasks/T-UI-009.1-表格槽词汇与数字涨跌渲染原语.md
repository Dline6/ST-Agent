# T-UI-009.1 · 表格槽词汇与数字 / 涨跌渲染原语

> [`T-UI-009`](T-UI-009-记忆区持仓行情读面.md) 的**第一叶**。它把 [13-visual-design §10](../../docs/PRD-v2-Agent/13-visual-design.md) 的两条「待补的视觉基线」（`--up`/`--down`/`--flat` 与 `--font-num` 无消费方）补成**可消费的原语**，并顺带修一处实测缺陷。**本叶不建任何页面**。

## 目标

两件交付，都落在**表现层**：

1. **表格槽形状对齐 + 一处漏斗**——`table` 的产出方与渲染件现在形状不一致（见下「事实」），导致生产面上**六张表全是空的**。定下形状、留一处漏斗、修六处产出方。
2. **列级数字 / 涨跌词汇 + 视觉基线**——列声明 `kind`（`text` / `number` / `direction`）；数字列右对齐等宽；涨跌列由**渲染件**统一产出三路冗余编码（颜色 + ▲▼ + 数值符号）。规范 §5 补两行基线、§10 的两条「待补」条目销账。

**已核实的事实**（2026-10-09，**实机实测**，非读码推断）：

- 产出方（[`ui/app.py`](../../src/st_agent/ui/app.py) 六处）给的是**位置形状**：`columns: ["假设","范围",…]`、`rows: [["值1","值2"], …]`。
- 渲染件（[`table.js`](../../src/st_agent/ui/web/js/components/table.js)）读的是**键控形状**：`column.label || column.key`、`row[column.key]`。
- **实机（Edge · 与目标 WebView2 同引擎）**：把两种形状各渲染一次并读 DOM——位置形状的**表头与单元格全为空**，键控形状正常。
- 六处受影响端点：`/api/reflection/experiments` · `/api/reflection/training` · `/api/eco/inbox` · `/api/eco/index` · `/api/eco/imports` · `/api/eco/violations/history`。
- **为什么没有测试拦下**：`tests/ui/test_ui_reflection.py` 的断言锁的正是位置形状（`slots["rows"][0][0]`、`slots["columns"][-1] == "状态"`）——纯 Python 侧看不见这个错位；前端又没有 JS 测试。dev 走查样本恰好用键控形状，所以走查页一切正常。
- **键控形状不是本批新选的**：[`l3/render/describe.py`](../../src/st_agent/l3/render/describe.py) 的 `AGENT_RUN_COLUMNS` 早就是键控形状，其旁注原文即「`table` 渲染件按 `[{key, label}]` 取值——**渲染面是形态的权威**」。故本批不是另定一种形状，而是把**六处离群者拨回已宣告的权威**；七处 `table` 产出方里只有这六处离群（第七处是 L3 的 `describe_agent_run`，本就合规）。

## 验收标准（Given-When-Then）

- GWT-1：Given 上述六处端点的产出，When 取描述并**实机渲染**，Then 每张表的表头与单元格**非空**且与上游数据一致（红-绿：改动前实机全空——证据见 [执行日志](../执行日志.md) `[T-UI-009]` 的对齐行）
- GWT-2：Given 列声明 `kind: "number"`，When 渲染并读 **computed style**，Then 单元格右对齐、`font-family` 取自 `--font-num`、`font-variant-numeric` 含 `tabular-nums`
- GWT-3：Given 涨跌列取 **正 / 负 / 零 / 无数据** 四值，When 渲染，Then 依次出 `num--up`+`▲`+`+x.xx%` / `num--down`+`▼`+`-x.xx%` / `num--flat`+`—`（**不带**符号）/ 中性「—」（**无**方向符、**无**方向色）——四路都不静默留白
- GWT-4：Given 渲染出的涨跌单元格，When **剥去全部颜色**（把令牌值换成同一色），Then 涨跌仍**可判**（▲▼ 与符号俱在）——规范 §2.2 的灰阶判据
- GWT-5：Given 新的列词汇与规范条文，When 跑守卫，Then 断言「涨跌编码三路恒同时」（**删任一路即红**）且 `app.css` 仍只引用已声明令牌；同批把规范 §10 的两条「待补」条目改写为已落

## 假设与前提

- **A1 · 形状取「键控」而非「位置」**（2026-10-09 ④ 对齐前选定，[D-105](../决策日志.md) ①）：前提是位置形状的六处产出方是**缺陷实体**（实机全空），而键控形状是渲染件的既有读取面、也是 dev 走查样本的形状，且**只有键控能让列携带 `kind`**。若错（位置形状才是产品口径）→ 返工面＝改渲染件去读位置形状，并另想一处安放列级 `kind`。**验证方式**：六处端点实机渲染非空（GWT-1）。
- **A2 · 涨跌编码归渲染件，产出方只给数值**（2026-10-09 ④ 对齐前选定，[D-105](../决策日志.md) ②）：前提是「颜色与符号恒同时出现」是**视觉规矩**（规范 §2.2 的灰阶判据），应由渲染面**结构上**保证；若由各产出方各自拼成品字符串，规范就退化成一条自觉纪律。若错（产出方须给成品文案）→ 返工面＝列级 `kind: "direction"` 退回纯文本，灰阶判据改由产出方保证。**验证方式**：GWT-3 / GWT-4 的守卫（删任一路即红）。
- **A3 · 六处产出方同批跟改，不留一处旧形状**：前提是这六处都走同一漏斗，改一处即全改。若错（某处有独立约束不能跟改）→ 返工面＝该处保留位置形状，但渲染件**不兼容**双形状（[01 §12](../../docs/技术架构-v2/01-平台共享契约.md)：「未登记即显式降级」，不做宽容解析）——故该处必须一并跟改，无可退。**验证方式**：GWT-1 逐端点实机渲染。
- **A4 · `text_kinds` 标法不变**（列头 `generated` / 行 `data`）：前提是槽级标注的口径（[D-064](../决策日志.md)）不受形状改变影响——键控后**仍是整槽标注**，不做同槽混合。若错（键控后须按单元格标注）→ 返工面＝`UiDescription` 的 `text_kinds` 语义变更，属契约变更，须先走[铁律 8](../工程宪法.md)。**验证方式**：`tests/ui` 里既有的中性化门用例不改即绿（含「`data` 槽含第一人称放行」那条）。
