# T-L1-003.1 · WorkflowDAG 模型 + 校验 + 持久化与版本

## 目标

落地 03 §3.1 的 WorkflowDAG schema——L1 创作侧的数据基础：节点（引用 skill_id + 参数绑定）、边（数据流连线，携带类型契约）、分组（子流程）、`schedule`、`version`。并交付其**静态校验**（成环检测 / 连线契约匹配 / 中性化命名 / 参数绑定合法性）、**持久化**（多版本共存）与**版本操作**（diff / 回滚）。

## 验收标准（Given-When-Then）

- GWT-1 成环阻止：Given 工作流形成循环依赖（A→B→A），When 保存/校验，Then 拒绝并指出环路径（逐节点列出），**不落盘**。
- GWT-2 连线契约匹配：Given 节点 A 的输出契约未声明 `risk_level`、节点 B 的输入契约 `required: [risk_level]` 且声明其类型为 `string`，When 校验该连线，Then 判定不匹配并给出「这里需要一个 string 类型的输入」式说明；两侧契约匹配时放行。
- GWT-3 中性化命名：Given 工作流 `name` 含拟人化词汇（人名 / 第一人称 / 情感措辞），When 保存，Then 拒绝并指向 01 §6。
- GWT-4 版本共存 / 回滚：Given 工作流 v1.0 已保存，When 发布 v1.1 后回滚到 v1.0，Then 取回的 v1.0 **逐字段还原**，且 v1.1 仍在版本历史中可 diff。
- GWT-5 引用方「待检查」：Given 工作流某节点引用 `sk_x_v1.0`，When `sk_x` 发布主版本 v2.0（`SkillRegistry` 写入待检查标记），Then 该工作流被标「待检查」（**不**自动改引用）；用户确认后标记清除。

## 假设与前提

- A1 `flow_id` **升格为 [01 §1](../../docs/技术架构-v2/01-平台共享契约.md) 的第 13 类契约 ID**，且契约层形态**直接对齐真实格式** `wf_<注册名>_v<主>.<次>`——`_make_id_type` 加可选 `pattern` 参数、`FlowId` 用显式 pattern，不复制 `SkillId` 那种「登记形态 `^sk_[0-9a-f]{20}$` 与真实 `sk_<名>_v<主>.<次>` 对不上」的双轨（④ 对齐定案，见 [D-018](../决策日志.md)）。依据（2026-09-26 核查）：01 §1 原为 12 类（机器副本 `contracts/identifiers.py::ID_REGISTRY`），无 `flow_id`；而工作流与「视角」同属 01 §9 的「可导出/可分享/可回滚对象」，`lens_id` 在 §1 表内、`flow_id` 不在 → 同构待遇。**零数据库影响**：`docs/数据库设计-BaoStock数据层/` 的「共享契约概念 → 本库落地」表只映射 `stock_id` / `dataset_snapshot_id` / `as_of`，其余 §1 ID 在该目录 0 命中，工作流落 `config` 分区加密 JSON、不入 SQL。走宪法 8 的 ⑦ 链（先改 01 §1 → 同步 03 §3.1 → 再改契约代码与 L1 实现），单批闭环 / 若错（升格后仍出现跨层形态漂移）：须再补 §1 约束措辞 / 验证：`tests/contracts/` 的 13 类断言 + `workflow/ids.py` 直接复用契约层 `FLOW_ID_PATTERN`（仓库内不存在第二份副本）。
- A2 连线契约匹配复用 `contracts.schema_check.check_link`（D-009 方言口径），不另造匹配规则（01 §2 明令「各层不得各造一套」）/ 若错（方言不够表达投资域连线）：须扩 01 §2 方言并同步判定件 / 验证：GWT-2 双向用例（匹配放行 / 不匹配报缺口）。
- A3 工作流持久化于 `config` 分区（`workflow/<flow_id>.json`），与 `skill-registry/` 同构、同分区；版本以文件共存实现（同 base 多版本各一文件）——与 `SkillRegistry` 的版本机制对称，复用 [D-009](../决策日志.md) 建立的方言与 `Store` 的 [D-015](../决策日志.md) 并发口径 / 若错（`config` 分区语义上不适合承载结构化对象）：需另立分区（涉 02 §2.1 分区表变更）/ 验证：GWT-4 多版本共存与回滚。
- A4 「待检查」按 01 §9 **以本工作流为单位**标记（读 `SkillRegistry.pending_updates`，命中即标；不新增注册表口径），确认后清除 / 若错（须支持逐节点粒度）：须扩标记结构 / 验证：GWT-5。
- A5 `schedule` 字段本任务只定义**数据形态**（定时 / 事件 / 手动三态 + 参数位），不实现触发——调度器归 `T-L1-005`（03 §6）/ 若错（形态不足以承载调度需求）：`T-L1-005` 开工时返工本字段 / 验证：`T-L1-005` 消费时不需改本任务模型。
- A6 公共 API 为新增包（`l1.workflow`），且 01 §1 的登记是**纯增量**（加一类 ID + `_make_id_type` 加一个可选参数；既有 12 类的形态与行为零变更）→ ⑦ 链只需 01 + 03 两处文档改动，不触及 02 与其余各层 / 若错（增量改动破坏既有面）：`tests/contracts/` 与全量用例会显式失败 / 验证：`git diff --name-only` 仅 `docs/技术架构-v2/{01,03}-*.md`、`src/st_agent/contracts/{identifiers,__init__}.py`、`src/st_agent/l1/workflow/**`、`tests/{contracts,l1}/**`。
- A7 `follow_latest` 以**次版本**递增记录「引用跟进」——跟进只改节点引用的 Skill 版本，工作流自身对外契约的派生在 `T-L1-003.2`（复合 Skill 面）才落地；若跟进的新主版本确实改了工作流的对外契约，用户确认时给出的 `changelog` / `impact` 即是留痕（且原版本保留可回滚） / 若错（跟进应记为工作流的主版本变更）：`follow_latest` 改走 major bump 并强制 changelog / 验证：`T-L1-003.2` 落地 IO 契约派生后复核一次。
