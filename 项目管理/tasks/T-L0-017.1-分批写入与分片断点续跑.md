# T-L0-017.1 · 分批写入与分片断点续跑

## 目标
把逐码任务的**写入粒度**从「一码一次整库加解密」改为「一批码一次」，并给长跑脚本补上**显式窗口 + checkpoint** 骨架——使全市场长跑从不分批 → 可分批、从「中断即白跑」→「中断只回退一批、可跨会话续跑」。不改水位语义、不改 `sync_state` schema。

## 验收标准（Given-When-Then）
- GWT-1 批内合并写：Given 逐码任务（`bs_k_daily`）对 N 只证券取数，When 计量对库的写事务次数，Then 事务次数 = ⌈N/批大小⌉ 而非 N，且落库行数与逐码写**逐字节等价**（同一批内 UPSERT 幂等）。
- GWT-2 显式窗口（分片可用）：Given 库内已有数据（全库水位已推进到今日），When 以显式起点参数再跑**另一批**码，Then 该批按给定起点取到整窗口数据（不被全库水位跳空），且任务水位仍取全库 `max(trade_date)`、单调不回退。
- GWT-3 中断只回退一批：Given 分批长跑在第 k 批失败，When 修好后重跑，Then 第 1..k−1 批不重取（checkpoint 判已完成）、第 k 批补齐、已入库行不重复、失败批留有可查原因。
- GWT-4 脚本可中断续跑：Given 长跑脚本以显式起点 / 分片 / 续跑参数运行，When 中途中断后重跑，Then 依 checkpoint 从上次位置续跑；摘要含**批粒度进度**与逐任务行数 / 水位 / 耗时；主口令仍只经环境变量传入，**不进 argv、不进摘要、不落盘**。
- GWT-5 零泄漏与审计不变：Given 上述改动，When 检查，Then 真实数据仍只落本地加密分区、盘上无明文，抓取仍**逐次经网关**留审计（`data_fetch` 条数 = 实际抓取次数）。

## 假设与前提
- A1 批内合并写不改变既有续跑语义（`tests/l0/test_full_sync.py` 的五条 GWT 除「逐码一事务」这一**隐含**假设外保持绿）/ 若错：需回改 007.1 的语义 pin 或其用例，`T-L0-007.1` 接口面随之复核 / 验证：跑 `pytest tests/l0/test_full_sync.py` + 新增事务计数用例
- A2 显式窗口只**加**覆盖入口、不改 `window_for` 的规则，故不触发【铁律 8】的契约级变更（05 记的 `bs_k_daily` 水位语义＝全库 `max(trade_date)` 保持不变）/ 若错：须先改 05 再改码 / 验证：`verify_docs.py --strict` + 契约用例
- A3 checkpoint 属长跑脚本的运行态，落 `--root` 同级、不进 Git、不承载口令 —— 不放 `sync_state`（避免动机器建表变更与 schema 两副本同步）/ 若错：改放 `sync_state` 须同批改 `schema.sql` 两副本与 05 / 验证：`git status` 无 checkpoint 文件、摘要与 checkpoint 均无口令
- A4 「中断只回退一批」的代价上界＝一批的行数与抓取次数（批大小可调，默认值取使单次事务开销可忽略的量级）/ 若错：调默认批大小即可，不改语义 / 验证：用例钉住批大小 → 事务次数关系；真跑时实测单批耗时
