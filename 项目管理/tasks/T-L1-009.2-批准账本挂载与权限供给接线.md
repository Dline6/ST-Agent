# T-L1-009.2 · 批准账本挂载与权限供给接线

## 目标

把 `.1` 的账本接进运行时：组合根持 `SkillPermissionBook`，并出一个实现 [`PermissionSource`](../../src/st_agent/l1/scheduler/models.py) 协议的 adapter 注入 `Scheduler`——**消费方的注入接口面签名不变**（[L1 册 `D1`](../遗留问题/L1-遗留问题.md) 解封条件的明文要求）。三处解析口径同批定案：复合 Skill **独立批准**、MCP 派生 Skill 的批准**委托 MCP 账本**（该事实在 MCP 侧已存在，不另造第二份）、空账本仍 `fail-closed`。

## 验收标准（Given-When-Then）

- **GWT-1 批准即生效（端到端）**：Given 组合根装配的运行时 + 一个声明了权限的 Skill，When 对它的 base `approve` 一条声明后按定时目标执行，Then 该次执行放行（信封非「缺少已批准权限」）；When 未批准时，Then 拦成 `validation_failed`（**不自动放行**，[D-039](../决策日志.md) 否决 F 的口径不破）。
- **GWT-2 空账本仍 fail-closed**：Given 空账本（无任何批准记录），Then 批准集为空、声明了权限的 Skill 一律 `validation_failed`；既有 `test_declared_permissions_are_not_auto_granted` 继续绿。
- **GWT-3 消费接缝不变**：Given `Scheduler.__init__(…, permissions=…)` 与 `PermissionSource` 协议，Then 二者签名**零变更**；adapter 只作 `PermissionSource` 的实现被注入。
- **GWT-4 复合 Skill 独立批准**：Given 一个工作流目标（执行其**复合 Skill**），When 复合体的 base 未被批准而其**成员** Skill 已批准，Then 该目标仍 `validation_failed`（**不继承**成员的批准态）。
- **GWT-5 MCP 派生 Skill 委托 MCP 账本**：Given `sk_mcp_<server>_<tool>`（其 `permissions` 即该 Server 的声明），When 该 Server 的权限已获批准，Then 该 Skill 的批准集＝`McpPermissionBook.approved_permissions(server_id)`（**不**重复要求 Skill 侧批准）。
- **GWT-6 回归**：受影响范围用例全绿；`verify_docs.py --strict` 检查 1–8 全 0；账本 `render` 后 SYNC。

- **A1 · MCP 派生 Skill 可反查到 Server**：`McpToolMapping` 携 `skill_id`，故「遍历 `list_servers()` × `mappings(sid)`、比对 `base_of(m.skill_id)`」可反查所属 Server（无需新增 mapper API、不改 done 模块）。若错（判定遍历面不可接受）：返工面＝在 `McpSkillMapper` 增设反查方法（纯增量）。
- **A2 · `build_l1_runtime` 缺省改为 adapter 不破坏既有语义**：既有用例的失败面来自「批准集为空」而非「来源为 None」，故空账本下行为逐字节同现状。验证：GWT-2 + 既有 `test_runtime_scheduler.py` 全绿。
- **A3 · 复合 Skill 的 base 可由 `composite_skill_id` 解析**：`scheduler._skill_of` 已按此解析执行体，adapter 取同一函数即「批准对象＝执行对象」，不引入第二套解析。验证：GWT-4。
- **A4 · 试跑侧不改**：`TrialRunner` 的 `approved_permissions` 仍是构造参数（[trial.py:386](../../src/st_agent/l1/workflow/trial.py)）；本叶只接**调度**侧供给。试跑由调用方（Studio / L3 控制台）经同一账本取值，属下游接入面，不在本叶。
