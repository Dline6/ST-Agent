# T-L1-003.2 · 复合 Skill（工作流 → 命名 Skill + 依赖提示）

## 目标

落地 03 §3.2：把一条校验通过的工作流保存为**复合 Skill**（「命名的工作流」）——对外暴露统一的输入输出契约与参数，`source=user-built` 进入 Skill 库，与原子 Skill 同样能被 L3 调度、被后续工作流继续编排。依赖的原 Skill 缺失时走「依赖提示」流程，不静默通过。

## 验收标准（Given-When-Then）

- GWT-1 保存为复合 Skill：Given 一条校验通过的工作流，When 保存为复合 Skill（命名 + 描述），Then 生成 `SkillDescriptor`（`source=user-built`）注册进 Skill 库，`SkillRegistry.list_all()` 可见且可按 `skill_id` 寻址。
- GWT-2 统一输入输出契约（默认推导 + 可显式覆盖）：Given 工作流有未连线的入端口/出端口，When 保存为复合 Skill**未**显式给出 schema，Then 由其推导 `input_schema` / `output_schema`；显式给出时以显式为准，且与未连线端口**不一致即拒**。
- GWT-3 参数暴露：Given 工作流某节点参数为字面量，When 保存为复合 Skill 并声明暴露该参数，Then 该参数进入 `SkillDescriptor.parameters`（经 `SkillRegistry.set_parameters` 双通道可改）。
- GWT-4 依赖缺失提示：Given 复合 Skill 引用的某原 Skill 在注册表中不存在（或版本缺失），When 保存/加载，Then 返回依赖提示（逐条列出缺失 `skill_id` + 所属节点），**不静默通过、不落半成品**。
- GWT-5 命名中性化与重名：Given `name` 未过 01 §6 校验、或与既有 Skill 的 `name` 重名，When 保存为复合 Skill，Then 拒绝并说明理由（复用 01 §6 规则，不另立命名口径）。

## 接口面

- 输入（消费的前置接口）：
  - `T-L1-003.1` 的 `st_agent.l1.workflow`：`WorkflowDAG` / `WorkflowNode` / `ParamBinding`（`dag.nodes[].params` 的绑定形态）、`WorkflowValidation`（保存前须 `validate_dag` 通过）、`WorkflowStore.get` / `get_latest` / `active`（加载侧由 flow base 取回 DAG）、`workflow.ids.{base_of, parse_flow_id, flow_id_for}`、`workflow.errors.WorkflowError`
  - T-L1-001.1 [`registry.py`](../../src/st_agent/l1/skills/registry.py)：`SkillRegistry.register` / `get` / `get_latest` / `list_all` / `_skill_path`（重名与依赖判定）、`skills.ids.{skill_id_for, base_of, check_skill_id, parse_skill_id}`、`skills.registry.SKILL_PREFIX`
  - `T-SC-001.4` 契约：`contracts.capability_types.{SkillDescriptor, ParameterSpec, Provenance}`、`contracts.registry_types.SemVer`、`contracts.neutrality.NeutralityGuard`（01 §6）
- 输出（本任务交付的公共 API / 落盘位置）：
  - `st_agent.l1.workflow.composite`：
    `save_as_composite_skill(dag, registry, *, name, description, inputs=None, outputs=None, exposed_params=()) -> SkillDescriptor`、
    `derive_io_contract(dag, registry) -> tuple[dict, dict]`（未连线端口推导）、
    `missing_dependencies(dag, registry) -> tuple[DependencyGap, ...]`、
    `composite_skill_id(flow_id) -> str` / `source_flow_id(skill_id) -> str`（复合 Skill ↔ 来源工作流的回指对）、
    `DependencyGap`（`node_id` / `skill_id` / `reason`）、`CompositeDependencyError`（携 `gaps`）
  - 落盘：**复用** `config` 分区 `skill-registry/<skill_id>.json` 布局（经 `SkillRegistry.register`，不新造存储面；复合 Skill 与原子 Skill 同库）
  - 消费方：`T-L1-003.4`（保存入口）/ `.5`（模板 fork 后可保存）、`T-ECO-001`（`.stskill` 导出，`composite_skill_id` / `source_flow_id` 即回指机制）、`T-ECO-002`（导入侧复用 `missing_dependencies`）、`T-L3-001`（Skill 库浏览）
  - 暂不交付：复合 Skill 的**删除联动**（删 Skill 是否连带删工作流）——本任务不建删除路径；[L1 册 A2](../遗留问题/L1-遗留问题.md) 是 MCP 映射面，不覆盖此处

## 假设与前提

- A1 复合 Skill 注册**复用** `SkillRegistry` 与 `skill-registry/` 布局，不新造注册表——它在 Skill 库里就是一个普通 `SkillDescriptor`（`source=user-built`），故 L3 调度 / 版本更新 / 待检查等既有机制自动适用 / 若错（复合 Skill 需独立生命周期，如回指工作流定义、删除时联动）：须为 `SkillDescriptor` 加字段（涉 01 §2 契约变更）/ 验证：GWT-1 + 全量既有 Skill 用例绿。
- A2 统一输入输出契约默认**由未连线端口推导**（④ 对齐定案）：未连线的入端口并集 → `input_schema.properties`，未连线的出端口并集 → `output_schema.properties`；可显式覆盖，覆盖值与推导值不一致即拒（不静默取其一）/ 若错（推导口径无法表达聚合式输出，如把多个节点输出汇成数组）：须提供显式覆盖为主要路径并补推导规则 / 验证：GWT-2 两例（默认推导 / 显式覆盖 + 不一致被拒）。
- A3 参数暴露为**显式声明**（`exposed_params`），不自动把节点参数全部上浮——节点参数是内部绑定的实现细节，全上浮会让复合 Skill 的参数面板噪声过大 / 若错（用户期望全量可调）：改为「默认全暴露 + 可标记内部」 / 验证：GWT-3。
- A4 依赖缺失走**提示流程而非拒绝保存**（03 §3.2「导入方走依赖提示流程」）：保存被拒会让用户在依赖尚未安装时无法留存草稿；本任务返回 `DependencyGap` 供上层提示 / 若错（提示语义不足以覆盖导入侧需求，`T-ECO-002` 需要更强的校验口径）：由 `T-ECO-002` 扩本返回值 / 验证：GWT-4。**调和见 A10**（草稿留存的承担者是 `WorkflowStore` 而非复合物化）。
- A5 `provenance` 沿用默认空 `Provenance()`（复合 Skill 是本机自建，非导入），`source=user-built` / 若错（自建物也需追溯链）：须在 09 §5 扩口径 / 验证：GWT-1 断言 `source` 与 `provenance`。
- A6 推导契约的 `properties` 键取**节点限定点号键** `<node_id>.<prop>`（④ 定案，已同步 [03 §3.2](../../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md)）/ 若错（下游按裸名传参，如 `.stskill` 导出侧或 L3 调用面期望 `risk_level`）：须为复合 Skill 加别名映射或改用裸名并补消歧规则，波及 `T-ECO-001` 与 L3 调用面 / 验证：GWT-2 断言键名与回指。
- A7 「已连线」判据与 §3.1 的**粗粒度节点到节点边模型对称**（④ 定案）：入端口「已连」= 该节点有入边 ∨ 有同名绑定（`literal` 或 `ref`）；出端口「已连」= 该节点有出边 ∨ 被其他节点以 `ref` 引用 / 若错（边不应整体吞掉端口级判定）：须改为纯值级（只认 `ref`），推导集变大 / 验证：GWT-2 两例 + 一条「有入边即不外露」用例。
- A8 复合 Skill 标识**由工作流 base 派生**：`wf_<名>_v<主>.<次>` → `sk_<名>_v<主>.<次>`，版本随 `dag.version`（④ 定案）/ 若错（需与原子 Skill 命名空间区分）：加固定前缀会同时改 `source_flow_id` 回指规则，波及 `T-ECO-001` 导出与导入 / 验证：GWT-1 断言 `skill_id` 形态 + `source_flow_id` 往返可逆。
- A9 显式覆盖的「不一致即拒」判据 = **键集必须相等 + 同名键的 `type` 必须相等**，其余关键字（`required` / 描述等）随显式（④ 定案）/ 若错（覆盖仅需细化、不该锁键集）：改为子集口径，须同步 03 §3.2 / 验证：GWT-2 三例（默认推导放行 / 一致覆盖放行 / 多键、少键、`type` 不符三类被拒）。
- A10 依赖缺失时 `save_as_composite_skill` **抛** `CompositeDependencyError`（携逐条 gaps），不落半成品；A4 的「草稿留存」由**工作流本身已在 `WorkflowStore` 落盘**承担——用户不丢工作，只是复合 Skill 的物化等依赖就绪（④ 定案）/ 若错（上层要求「返回提示」而非异常）：改为两态返回对象，波及 `T-L1-003.4` 保存入口调用面 / 验证：GWT-4 断言异常携逐条 `node_id` + `skill_id`，且**该次调用未在 `skill-registry/` 留下任何文件**。
- A11 `offline_level` 取所引用 Skill 的**最差**（全 `full`→`full`；任一 `none`→`none`；否则 `degraded`）、`permissions` 取**并集**（④ 定案）——复合体只能声明它的部件所能支持的离线能力与权限面 / 若错（应固定 `full` / 空权限，或应作显式参数）：改 `save` 签名或常量，波及 .stskill 导入侧的权限申请展示（09 §4）/ 验证：GWT-1 断言两字段由 deps 派生 + 一条「任一 dep 为 `none` → 复合为 `none`」用例。
