# T-L1-003.2 · 复合 Skill（工作流 → 命名 Skill + 依赖提示）

## 目标

落地 03 §3.2：把一条校验通过的工作流保存为**复合 Skill**（「命名的工作流」）——对外暴露统一的输入输出契约与参数，`source=user-built` 进入 Skill 库，与原子 Skill 同样能被 L3 调度、被后续工作流继续编排。依赖的原 Skill 缺失时走「依赖提示」流程，不静默通过。

## 验收标准（Given-When-Then）

- GWT-1 保存为复合 Skill：Given 一条校验通过的工作流，When 保存为复合 Skill（命名 + 描述），Then 生成 `SkillDescriptor`（`source=user-built`）注册进 Skill 库，`SkillRegistry.list_all()` 可见且可按 `skill_id` 寻址。
- GWT-2 统一输入输出契约（默认推导 + 可显式覆盖）：Given 工作流有未连线的入端口/出端口，When 保存为复合 Skill**未**显式给出 schema，Then 由其推导 `input_schema` / `output_schema`；显式给出时以显式为准，且与未连线端口**不一致即拒**。
- GWT-3 参数暴露：Given 工作流某节点参数为字面量，When 保存为复合 Skill 并声明暴露该参数，Then 该参数进入 `SkillDescriptor.parameters`（经 `SkillRegistry.set_parameters` 双通道可改）。
- GWT-4 依赖缺失提示：Given 复合 Skill 引用的某原 Skill 在注册表中不存在（或版本缺失），When 保存/加载，Then 返回依赖提示（逐条列出缺失 `skill_id` + 所属节点），**不静默通过、不落半成品**。
- GWT-5 命名中性化与重名：Given `name` 未过 01 §6 校验、或与既有 Skill 的 `name` 重名，When 保存为复合 Skill，Then 拒绝并说明理由（复用 01 §6 规则，不另立命名口径）。

## 接口面

- 输入（消费的前置接口）：
  - `T-L1-003.1` 的 `st_agent.l1.workflow` 包：`WorkflowDAG` / `WorkflowValidation`（保存前须校验通过）
  - T-L1-001.1 [`registry.py`](../../src/st_agent/l1/skills/registry.py)：`SkillRegistry.register` / `get` / `get_latest` / `list_all` / `skill_id_for`、`base_of`（重名与依赖判定）
  - `T-L1-003.1` 同批交付的 `st_agent.l1.workflow.ids`：`flow_id` 与 `skill_id` 的对应关系（复合 Skill 的描述中回指来源工作流）
- 输出（本任务交付的公共 API / 落盘位置）：
  - `st_agent.l1.workflow.composite`：`save_as_composite_skill(dag, *, name, description, inputs=None, outputs=None, exposed_params=()) -> SkillDescriptor`、`derive_io_contract(dag) -> tuple[dict, dict]`（未连线端口推导）、`missing_dependencies(dag, registry) -> tuple[DependencyGap, ...]`
  - 落盘：**复用** `config` 分区 `skill-registry/<skill_id>.json` 布局（不新造存储面；复合 Skill 与原子 Skill 同库）
  - 消费方：`T-L1-003.4`（保存入口）/ `.5`（模板 fork 后可保存）、`T-ECO-001`（`.stskill` 导出）、`T-L3-001`（Skill 库浏览）

## 假设与前提

- A1 复合 Skill 注册**复用** `SkillRegistry` 与 `skill-registry/` 布局，不新造注册表——它在 Skill 库里就是一个普通 `SkillDescriptor`（`source=user-built`），故 L3 调度 / 版本更新 / 待检查等既有机制自动适用 / 若错（复合 Skill 需独立生命周期，如回指工作流定义、删除时联动）：须为 `SkillDescriptor` 加字段（涉 01 §2 契约变更）/ 验证：GWT-1 + 全量既有 Skill 用例绿。
- A2 统一输入输出契约默认**由未连线端口推导**（④ 对齐定案）：未连线的入端口并集 → `input_schema.properties`，未连线的出端口并集 → `output_schema.properties`；可显式覆盖，覆盖值与推导值不一致即拒（不静默取其一）/ 若错（推导口径无法表达聚合式输出，如把多个节点输出汇成数组）：须提供显式覆盖为主要路径并补推导规则 / 验证：GWT-2 两例（默认推导 / 显式覆盖 + 不一致被拒）。
- A3 参数暴露为**显式声明**（`exposed_params`），不自动把节点参数全部上浮——节点参数是内部绑定的实现细节，全上浮会让复合 Skill 的参数面板噪声过大 / 若错（用户期望全量可调）：改为「默认全暴露 + 可标记内部」 / 验证：GWT-3。
- A4 依赖缺失走**提示流程而非拒绝保存**（03 §3.2「导入方走依赖提示流程」）：保存被拒会让用户在依赖尚未安装时无法留存草稿；本任务返回 `DependencyGap` 供上层提示 / 若错（提示语义不足以覆盖导入侧需求，`T-ECO-002` 需要更强的校验口径）：由 `T-ECO-002` 扩本返回值 / 验证：GWT-4。
- A5 `provenance` 沿用默认空 `Provenance()`（复合 Skill 是本机自建，非导入），`source=user-built` / 若错（自建物也需追溯链）：须在 09 §5 扩口径 / 验证：GWT-1 断言 `source` 与 `provenance`。
