# T-L1-005.3 · 离线到期处置（照跑标注 / 待补与补跑或跳过）

## 目标

兑现 [03 §6](../../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md) 第三条：断网期间到期的调度——**离线可执行者照常执行**（用最后快照并在结果中标注），**不可执行者记「待补」**，网络恢复后按**用户配置**补跑或跳过。

## 验收标准（Given-When-Then）

- GWT-1 离线可执行者照跑并标注：Given 网关离线，When 到期目标所引 Skill 的最差 `offline_level` 为 `full` 或 `degraded`，Then 照常执行且在本条运行记录上**显式标注**「离线执行、数据停留在最后快照」（不冒充实时）；信封上的数据截止时间由执行器经 `ctx.freshness` 落在 `as_of` / `last_updated_at`，调度器**不代填**。
- GWT-2 离线不可执行者记待补：Given 网关离线，When 到期目标的 `offline_level` 为 `none`，Then 不执行、记一条「待补（`pending_reconnect`）」且状态可查，且**不**产生失败 SkillRun。
- GWT-3 恢复后按配置补跑（幂等）：Given 存在待补项且用户配置＝补跑，When 网络恢复后触发一次处置，Then 该目标**补跑一次**并清空待补集（错过的条数写进说明，不静默；**重复触发不再执行**）；仍离线时补跑不吞掉待补集。
- GWT-4 恢复后按配置跳过：Given 同上但用户配置＝跳过，When 网络恢复后触发一次处置，Then 不执行、记「已跳过」可查，待补项被清空。
- GWT-5 配置面按 01 §7 登记：Given 未显式配置，When 读取，Then 取登记条目的默认值；When 用户改配置，Then 产生 `change_id`（复用既有配置变更口径），且改后行为随之变化。

## 接口面

- 输入（消费的前置接口）：
  - `T-L1-005.2`（本批姊妹）· `src/st_agent/l1/scheduler/` 的 `Scheduler.tick` 与执行接线、`ScheduleTarget`
  - `T-L0-004`（done）· [`net/gateway.py`](../../src/st_agent/l0/net/gateway.py) 的 `EgressGateway.online` / `.set_online(online)`（离线判定与恢复信号；离线拦截信封带 `pending_reconnect`）
  - `T-L1-001.1`（done）· [`skills/registry.py`](../../src/st_agent/l1/skills/registry.py) 的描述体 `offline_level`（`full` / `degraded` / `none`；复合体取部件最差）
  - 契约 [01 §7](../../docs/技术架构-v2/01-平台共享契约.md) `ConfigEntry` 七字段（配置登记形态）
- 输出（本任务交付的公共 API / 落盘位置）：
  - `src/st_agent/l1/scheduler/` 的离线处置：`Scheduler.catch_up(now)`（恢复后按配置补跑或跳过，幂等）＋ `Scheduler.tick` 路径内的离线**分流**（按 `offline_level` 照跑并标注 / 记 `deferred` 并累计待补）；待补集落 `config/scheduler/<target>.json` 的 `pending`
  - [`scheduler/policy.py`](../../src/st_agent/l1/scheduler/policy.py)：`SchedulerPolicy`（`config_id` = `scheduler-policy/offline-catch-up`，缺省 `catch-up`）+ 变更留痕 `execution_log/scheduler-change/<change_id>.json`
  - 消费方：`T-L1-006`（组合根注入网关以驱动在线态并接 `catch_up`）

## 可关闭的遗留

无（已逐条核 [L0 册](../遗留问题/L0-遗留问题.md) 与 [L1 册](../遗留问题/L1-遗留问题.md) 未闭区，无归属本任务或解封条件指向本任务者）。

**范围澄清（与相邻条目的边界）**：[L0 册 `A5`](../遗留问题/L0-遗留问题.md) 的「离线补发执行」指的是 **L5 渠道投递**的补发（归属候选 `T-L5-002`），[02 §7](../../docs/技术架构-v2/02-L0-本地优先基座.md) 的「云端渠道补发」同指此事——两者都**不是**本任务的「调度到期补跑」。本任务只处置**调度触发的 Skill 执行**，不改动上述条目的归属与解封条件。

## 假设与前提

- A1 离线判定取 `EgressGateway.online` 单一事实源，不另建在线态 / 若错：需另立在线态口径并同步 [02 §7](../../docs/技术架构-v2/02-L0-本地优先基座.md) / 验证：GWT-1 / GWT-2 的离线用例与 `set_online` 双侧。
- A2 「离线可执行」的分级判据取目标所引 Skill 的 `offline_level`（复合体已按最差聚合，无需重算），`full` 与 `degraded` 一律照跑、`degraded` 另在结果标注 / 若错：分级判据与 02 §7 的三级口径脱节 / 验证：GWT-1 / GWT-2 的三级覆盖。
- A3 补跑或跳过的配置项**新登记**一条 [01 §7](../../docs/技术架构-v2/01-平台共享契约.md) `ConfigEntry`（`scope=global`，默认值取二者之一并在 ④ 定案时明确）；**不改 01 契约本身**（§7 只定义条目形态，D-005 已有先把条目落盘、契约不动的先例）/ 若错：须改契约并走工作流第 ⑦ 步 / 验证：GWT-5 的默认值与改配置两侧。
- A4 **待补集＝离线期间错过的到期点**（升序去重），处置**每目标一次**——一次补偿该目标的全部待补到期点，不按条数重放（长离线后连刷几十遍既是噪声也不合用户预期）；错过的条数写进说明，故仍有据可查 / 若错：需改为逐条补跑或加上限，GWT-3 用例重写 / 验证：GWT-3 的「错过 2 个到期点 → 补跑一次」与幂等用例。
- A5 本任务不实现「离线横幅三类清单」的渲染（[02 §7](../../docs/技术架构-v2/02-L0-本地优先基座.md) 的 UI 面归 L3 / 前端），只交付其数据面 / 若错：渲染方缺数据 / 验证：待补与已跳过状态可经 `Scheduler.status` 查到。
