# T-UI-018.2 · 设置区：备份、恢复与完全清空

> [`T-UI-018`](T-UI-018-设置区与全局要素.md) 三叶之一（[D-114](../决策日志.md) ① / ③）——补上 [11-sitemap §3.8](../../docs/PRD-v2-Agent/11-sitemap.md) 的三条屏：**一键备份**（输入密码 → 单加密文件）、**恢复**（输入密码 → 完整还原）、**完全清空**（三次确认 → 彻底删除本地数据）。三叶里**唯一的破坏性面**。

## 目标

- **三条声明面**——各一张 `permission_approval_card`（[11-sitemap §2.1](../../docs/PRD-v2-Agent/11-sitemap.md) 的形态对位）：逐条讲清「这次要动什么」（备份含哪些分区 / 恢复覆盖什么 / 清空删什么），**不代用户表态**。
- **页面级 chrome**——密码输入、归档落点、恢复目标、**清空的三步确认**（先例＝ [`renderEvolutionPage`](../../src/st_agent/ui/web/js/pages/evolution.js) 的出厂重置块）。
- **`POST /api/settings/backup`** ——`{passphrase, dest?, include_data_cache?}` → 单个加密归档；**归档不得落在存储根之内**（清空删的是整个根，放进去等于一起删）。
- **`POST /api/settings/restore`** ——`{archive, passphrase, target_root?, target_passphrase?}` → 完整还原；覆盖写当前根时置重启闸门。
- **`POST /api/settings/wipe`** ——`{confirmations: [...]}` → [`wipe_all`](../../src/st_agent/l0/backup/backup.py)；三枚**有序**令牌不足即拒。

**本批的边界**（不越界）：

- **加密 / 落盘 / 归档的本体归 L0**（[`l0/backup/`](../../src/st_agent/l0/backup/)）——本叶只做交互面与确认门，不重造。
- **明密转换不归本叶**——它写的是**新根**、不动当前根，与清空 / 恢复不同类（也因此**不置闸门**），归 [`.1`](T-UI-018.1-四设置页与配置落值面.md) 的存储页。本叶的闸门只为「破坏了运行中的根」而设。
- **不引「新根」参数**：备份归档落点可由用户给，但恢复的目标根**默认就是当前根**（[11-sitemap §3.8](../../docs/PRD-v2-Agent/11-sitemap.md) 的 Flow 是「完整还原」而非「迁到别处」）。

## 验收标准（Given-When-Then）

- GWT-1：Given [11-sitemap §3.8](../../docs/PRD-v2-Agent/11-sitemap.md) 的三条屏，When 逐条走查，Then **三条都有可见载体**——两条声明卡 + 三块操作 chrome
- GWT-2：Given 一键备份，When 输入密码并提交，Then 产出**单个加密归档**并回报路径；归档落在**存储根之内即拒**（`validation_failed` + 原因）
- GWT-3：Given 「完全清空」，When 三次确认（三枚有序令牌）未集齐，Then `validation_failed` 且**一个文件都不删**；集齐后彻底删除存储根整目录并显式回报，同时置**进程级重启闸门**——此后**全部**数据面端点回 `unavailable` + 重启原因（`/api/health` 除外）
- GWT-4：Given 备份 / 恢复，When 密码错误或归档损坏，Then **如实报错**（输入类 ⇒ `validation_failed`；完整性类 ⇒ `failed` + `log_ref`），**不道歉、不模糊**、不静默成功
- GWT-5：Given 恢复，When 校验通过，Then 完整还原（含图谱结构 / 参数 / 历史对话）并回报还原的分区与文件数；覆盖写当前根时明说「须重启后继续」
- GWT-6：Given 文案，When 核对，Then 按[契约 9 中性表达](../../docs/PRD-v2-Agent/10-platform-capabilities.md)撰写，**无拟人化**（破坏性动作照实陈述后果，不劝不吓）
- GWT-7：Given 真组合根 + 真回环服务，When 在 Edge 走查备份 → 恢复（错密码）→ 清空三步确认，Then 全程可用、控制台无新增报错

## 假设与前提

- **A1**：**备份归档必须落在存储根之外**——[`wipe_all`](../../src/st_agent/l0/backup/backup.py) 删的是存储根**整目录**，而 [02 §8.3](../../docs/技术架构-v2/02-L0-本地优先基座.md) 明说「清空后提示『备份文件位置由用户自行处理』」——那句提示成立的前提就是归档不在根内。本叶的缺省落点是 `root.parent / "<root>-backups"`，并对用户给的落点做**解析后的**包含判定（`..` 与符号链接都算）。**若错的影响**：把归档放进根内会让「清空」同时毁掉唯一的备份，且表面上一切正常（两次操作各自都成功）。**验证方式**：集成用例断言根内落点回 `validation_failed` 且**无任何文件被创建**；单测钉 `_is_inside` 对 `..` 逃逸判否。
- **A2**：**清空 / 恢复之后，本进程的存储句柄失效**——`wipe_all` 删目录、`restore_backup` 覆盖写分区，两者都让内存里的清单缓存与磁盘不一致；继续读写要么报错、要么**静默作用于陈旧清单**（后者才是要防的）。故设**进程级闸门**：闸门置位后**全部**数据面端点回 `unavailable` + 重启原因。**若错的影响**：不设闸门则清空后页面照常「看起来能用」，而任何一次写入都建立在已删的根或陈旧清单上；只在 `_call_face` 一处设闸则会漏掉那些自行构造 `unavailable` 的面（`/api/chat/context` 即一例）。**验证方式**：集成用例在清空后断言 `/api/settings/storage` 与 `/api/chat/context` **都**回 `unavailable` + 「重启」、而 `/api/health` 仍 `ok`。
- **A3**：**用户输入类失败与完整性失败要分开报**——`BackupAuthError`（密码错）与 `WipeConfirmationError`（确认不足）是**输入**问题，应为 `validation_failed`；`BackupCorruptedError`（归档损坏 / 恢复写入失败）是**完整性**问题，应为 `failed` + `log_ref`。**若错的影响**：不翻译则全落进「未预期失败」——用户会把「密码打错了」读成「工具坏了」（而 L0 的异常树不是 `ValueError`，`_call_face` 只认它，故翻译必须显式）。**验证方式**：集成用例断言两枚令牌回 `validation_failed`、错密码回**非 ok** 且带原因。
- **A4**：**恢复的默认目标是当前存储根**（[11-sitemap §3.8](../../docs/PRD-v2-Agent/11-sitemap.md) 的 Flow 是「完整还原」）——`target_root` 可给，但缺省即当前根，且**覆盖写当前根时才置闸门**、还原到别处则不动当前进程。**若错的影响**：若把「恢复」实现为只能落到新目录，用户就得先关应用再手工迁移，M7 打包期的体验会与 PRD 的「一键还原」不符。**验证方式**：`_run_restore` 的 `over_live` 分支（`Path(target_root) == root`）决定是否置闸门；用例覆盖覆盖写当前根一态。
