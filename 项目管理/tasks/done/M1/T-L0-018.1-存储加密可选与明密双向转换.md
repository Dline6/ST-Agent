# T-L0-018.1 · 存储加密可选（默认关）与明密双向转换

## 目标
把 `Store` 的落盘加密由**唯一形态**改为**可选形态**：新建存储**默认不加密**（免口令），并交付**加密 ⇄ 明文双向转换**；同时压掉「一次事务＝整库加解密」的固定开销。既有加密存储的读写行为逐字节不变（向后兼容）。

## 验收标准（Given-When-Then）
- GWT-1 加密默认可关且格式自辨：Given `Store.create(root)` **不带口令**，When 落盘并 `Store.open(root)`，Then 免口令即可读写、分区文件为明文可读；Given **既有加密根**，When `Store.open(root, 口令)`，Then 行为与现状逐字节一致（口令错仍拒开）；两种根都由 `open` **自行分派**，调用方不指定格式，格式标记本身不含任何密钥材料且可人读。
- GWT-2 明密双向转换：Given 任一根目录，When 转换到另一格式，Then 分区集合 / 文件相对路径 / 文件内容**逐字节等价**、`Store` 侧读回一致；转换**幂等**（重复跑结果不变）、**中断不留半格式根**（要么完整新根、要么无）。
- GWT-3 完整性不随降密而降：Given 明文模式，When 某文件被篡改，Then 仍按 §2.3 报损坏（清单 digest 与原子替换保留）——「不加密」不等于「不校验」；且 `secrets` 分区**仍为密文**（见 A5），明文模式不解除 §2.2 的凭据隔离。
- GWT-4 落盘往返降耗：Given 明文模式下的批量写（逐码同步的批内合并写路径），When 计量单次事务的固定开销，Then 相对加密模式**显著下降**（可量化对比，基线取 2026-10-04 实测的 5.3 秒/GB/次）。
- GWT-5 契约先行（铁律 8/9）：Given 本批变更，When 检查，Then [PRD story-05](../../../../docs/PRD-v2-Agent/story-05-local-first.md) 的「本地加密存储」「单个加密文件」两条硬指标、[架构 README 全局硬约束](../../../../docs/技术架构-v2/README.md) 第 1 条、[工程宪法](../../../工程宪法.md) 产品铁律 1、[02 §2.2](../../../../docs/技术架构-v2/02-L0-本地优先基座.md) 均**已改实**（改码之前），且断链校验通过。

  - T-L0-002 [`vault.py`](../../../../src/st_agent/l0/secrets/vault.py)：凭据库（`secrets` 分区的消费方）
  - T-L0-006 备份（[02 §8.1](../../../../docs/技术架构-v2/02-L0-本地优先基座.md)「单个加密归档文件」的口径随本任务复核）

- 输出（本任务交付的公共 API / 落盘位置）：
  - `Store.create(root, passphrase=None)`：`passphrase=None` ⇒ **明文模式（默认）**；给出 ⇒ 加密模式（与现状同）
  - `Store.open(root, passphrase=None)`：按存储根内的格式标记自动分派
  - 存储根内**明文**格式标记文件（`store.json`：格式名 + 版本；**不含**密钥材料）
  - `Store.convert(source, target, *, passphrase=None, to_format=…)`（或等价的公开转换入口）：明密双向转换，**源不动、写新根**
  - `项目管理/tools/convert_store.py`：操作侧 CLI（口令只经环境变量，不入 argv）
  - `tests/l0/test_store_format.py`：格式判别 / 双向转换 / 幂等 / 篡改仍报损坏 / 向后兼容的离线用例

## 可关闭的遗留
- L0 / L1 / L2 / L3 四册未闭区逐册扫过：**无命中**（本任务不承接既有遗留；由它产生的新遗留按册规登记）

## 假设与前提
- A1 格式标记落在**存储根**（明文），而非分区内——`Store.open` 必须在解密任何东西**之前**就知道该怎么读 / 要不要口令 / 用哪个 keyfile / 要不要派生密钥 / 怎么校验完整性。/ 若错：只能用隐式判据（如「keyfile 在 ⇒ 加密」），歧义大、兼容性差 / 验证：GWT-2 的双格式用例
- A2 「默认关」只作用于**新建**存储；既有加密存储行为逐字节不变（`open` 仍要口令，格式标记缺失时按加密口径读——兼容历史根）/ 若错：需一次性迁移全部既有根并改 `open` 语义 / 验证：既有 `tests/l0/test_store*.py` 全绿 + 新增「无标记根按加密读」用例
- A3 明文模式**保留**清单 digest（SHA-256）、原子替换与崩溃残留回收——降的是**机密性**，不是**完整性 / 一致性**（02 §2.3 / §2.4 不因本任务放宽）/ 若错：损坏检测随之失能，违背「可解释 / 失败显式化」/ 验证：GWT-4 的篡改用例
- A4 转换落「**源不动、写新根**」，不做就地重写——就地重写需要额外的崩溃恢复设计，且失败即两份都不完整 / 若错：需补就地转换的中断恢复设计 / 验证：GWT-3 的中断用例（转换中途中断 → 源完整可读、无半格式根）
- A5 **`secrets` 分区单独保留加密**（负责人 2026-10-04 拍定，取代本册登记时的待定）：明文模式下其余**六个分区**免口令、明文落盘；`secrets`（API Key / 凭据）**仍须口令**方可读写，沿用 §2.2 的「独立 salt 重新派生」与 §3 的隔离口径——即 `Store.open(root)` 免口令可开普通分区，**访问 `secrets` 时才要求口令**（惰性解锁）。这是本口径最敏感的一处副作用，02 §2.2 与 §3 的条文须写明 / 若错：凭据将明文落盘、属安全事件面 / 验证：GWT-3 的「secrets 仍为密文」用例 + 02 §3 条文
- A6 本任务**不引入**新的第三方依赖（复用 `cryptography`；明文模式反而少用它）/ 若错：不适用 / 验证：`pyproject.toml` 的 `dependencies` 零变更
