# T-L3-005.2 · 反馈采集点

## 目标

兑现 [05 §9](../../../../docs/技术架构-v2/05-L3-对话主入口.md) 第二条：推送 / 结论 / 建议的**五类反馈入口**（采纳 / 忽略 / 否定 / 追问 / 点赞）在交互层采集，产生 `FeedbackEvent`（[08 §1](../../../../docs/技术架构-v2/08-L6-反思演进.md)）交 L6。**L3 不建反馈存储**——反馈全部进 L6 的本地反思数据池（`reflection` 分区），L3 只产事件。

## 验收标准（Given-When-Then）

- **GWT-1 · 五动作采集**：Given 任一推送 / 结论 / 建议的反馈入口，When 用户采纳 / 忽略 / 否定 / 追问 / 点赞，Then 产出 `FeedbackEvent`——`feedback_id`（[01 §1](../../../../docs/技术架构-v2/01-平台共享契约.md) 的 `fb_` 形态）、`target`、`action`（`adopted` / `ignored` / `rejected` / `queried` / `liked`，五类穷尽）、`reason`、`timestamp`（带时区）、`context`（08 §1 六字段齐备）。
- **GWT-2 · 否定类的理由入口必填**：Given `action="rejected"`（否定类建议），When **未提供** `reason`，Then 采集被拒（`validation_failed` + 理由）——兑现 08 §1「否定类建议**必填入口**」；其余四类 `reason` 可选填，缺省不影响采集。
- **GWT-3 · `target` 三类可寻址且形态受校验**：Given `delivery_id`（某条推送）/ `trace_id`（某条结论）/ `change_id`（某条建议）三类 target，When 采集，Then 三类皆接受且按 [01 §1](../../../../docs/技术架构-v2/01-平台共享契约.md) 的 ID 形态校验；**不合形态 → `validation_failed`**（不静默收下无法寻址的 target）。
- **GWT-4 · 发出 `FeedbackRecorded` 事件（[01 §11](../../../../docs/技术架构-v2/01-平台共享契约.md)）**：Given 一次成功采集，When 送达，Then 经**注入的事件接收面**发出 `PlatformEvent(event="FeedbackRecorded")`（`payload` 含 `feedback_id` / `target` / `action` / `reason` / `context`，并携**适用时**的 `trace_id` / `change_id`）；**缺省不注入即不送达**——仍返回采集结果，但在结果的送达面里**显式标注「未送达」并点名归属任务**（`T-L6-001`，同 [`FEEDBACK_POOL_OWNER`](../../../../src/st_agent/l3/config/handling.py) 的既有口径），**不假装已送达、也不静默丢弃**。
- **GWT-5 · L3 零落盘**：Given 一次采集完成（含送达与未送达两态），When 检查分区，Then `feedback` 相关**零落盘**——反馈池归 L6（08 §1「反馈全部进本地反思数据池（L0 `reflection` 分区），不外发」），L3 不新建存储、不代写 L0。

## 接口面

- **输入（消费的前置接口）**
  - [08 §1](../../../../docs/技术架构-v2/08-L6-反思演进.md) 的 `FeedbackEvent` 字段表——本叶的**实现依据**（六字段：`feedback_id` / `target` / `action` / `reason` / `timestamp` / `context`）
  - `T-SC-001.1` / `T-SC-002`：[`FeedbackId`](../../../../src/st_agent/contracts/identifiers.py)（01 §1，`fb_` 形态）· [`PlatformEvent`](../../../../src/st_agent/contracts/time_events.py)（01 §11，`FeedbackRecorded` 已登记）· [`ResultEnvelope`](../../../../src/st_agent/contracts/result_envelope.py)（01 §5）
  - 三类 target 的 ID 类型（01 §1）：[`DeliveryId`](../../../../src/st_agent/contracts/identifiers.py) / [`TraceId`](../../../../src/st_agent/contracts/identifiers.py) / [`ChangeId`](../../../../src/st_agent/contracts/identifiers.py)
  - `T-L3-003.2`（done）先例：[`FEEDBACK_POOL_OWNER`](../../../../src/st_agent/l3/config/handling.py)（`"T-L6-001"`）——「原因去哪」的点名口径沿用
- **输出（本任务交付的公共 API / 落盘位置）**
  - 新增 `src/st_agent/l3/feedback/`（本叶建 `__init__.py` 与 `collector.py`）：
    - `FeedbackEvent`——08 §1 六字段的机器可读形态（`feedback_id` 由本层生成，见假设 A1）
    - `FeedbackCollector`——采集面：`record(target, action, *, reason=None, context=None)`（产 `FeedbackEvent`）与送达（经注入的事件接收面）；五动作的取值域与「否定类必填理由」在构造期钉死
    - `FeedbackDelivery`——送达结果（已送达 / **未送达 + 点名**），使「事件去哪」不靠猜
  - 落盘：**零落盘**（反馈池归 L6；本层不建存储、不代写 L0 `reflection` 分区）
  - 同批改 [05 §9](../../../../docs/技术架构-v2/05-L3-对话主入口.md)：补「反馈由交互层采集并**产生** `FeedbackEvent`」的落地口径；同批把 [01 §1](../../../../docs/技术架构-v2/01-平台共享契约.md) 的 `feedback_id` 产生方登记由 L6 改为**交互层（L3）**（铁律 8：先 01 → 05 → 代码）

## 假设与前提

- **A1 · `feedback_id` 由 L3 生成，同批改 [01 §1](../../../../docs/技术架构-v2/01-平台共享契约.md) 的产生方登记**：05 §9 明说反馈在**交互层采集、产生** `FeedbackEvent`，而 01 §1 现登记其产生方为「L6」——两处不符，按铁律 8 的顺序（01 → 05 / 08 → 代码）改实。若错（id 仍应由 L6 赋）：返工面＝01 §1 登记回退 + 本叶的 id 生成点移除。
- **A2 · `FeedbackEvent` 的字段表实现照 [08 §1](../../../../docs/技术架构-v2/08-L6-反思演进.md)，不另立 [01](../../../../docs/技术架构-v2/01-平台共享契约.md) 契约条目**：08 §1 已给出六字段表，01 §11 已登记事件名与其发布方（交互层），故本叶是**实现方**而非新结构的登记方（同 [`ConfigDraft`](../../../../src/st_agent/l3/config/draft.py) 由 [05 §5](../../../../docs/技术架构-v2/05-L3-对话主入口.md) 定义、L3 实现的先例）。若错（须在 01 另立小节）：返工面＝01 契约新增小节 + 05 §9 / 08 §1 回指改写。
- **A3 · 送达经注入的事件接收面，缺省不送达**：L6 尚未开工（`T-L6-001` 为 `todo`），故「发出事件」的落点只能靠注入；沿用本仓「未注入即不假装完成 + 点名」的既有范式（采集结果照常返回，送达面如实标注）。若错（应由组合根统一发事件）：返工面＝`FeedbackCollector` 的签名与 `T-INT-002` 的装配面。
- **A4 · 「否定类」＝ `action="rejected"` 一类，其 `reason` 必填**：08 §1 原文作「用户说明的原因（否定类建议必填入口，可选填）」。若错（必填面另有划分，如 `queried` 也算）：返工面＝`FeedbackEvent` 的构造期校验点。
