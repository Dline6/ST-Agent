# T-UI-022 · 回环服务拒绝请求时排空请求体

## 目标

让 [`UiRequestHandler`](../../../../src/st_agent/ui/server.py) 在**未读请求体**即回响应时先把声明的体读净（有界），使客户端拿到的是那支 `ResultEnvelope` 错误 JSON，而不是一个**网络层异常**。

## 背景（本项由 T-UI-021 的 ⑥ 验证期发现）

[`do_POST`](../../../../src/st_agent/ui/server.py) 的拒绝分支一律**在 `_read_json_body()` 之前** return：令牌无效 / `Host` 不符 / 路径不在 `_POST_ROUTES` 时，请求体**从未被读走**。响应写完后 `daemon_threads` 的 handler 线程结束、连接关闭，而 socket 里躺着未读数据——**Windows 在此时发 RST**，客户端读到的是 `ConnectionAbortedError: [WinError 10053]`。

**实测复现**（2026-10-11 与本条 ④ 对齐期，本机 Windows，脚本见「复现」节）：4 MiB 体打 401 路径 3/3 中招、打 404 路径 2/3 中招；小体（`{}`）不中招——故它表现为**负载 / 体量相关**的间歇失败。这正是 `T-UI-021` 范围套件里 `tests/ui/test_ui_face_ports.py::test_new_paths_are_get_only[/api/graph/status]` 偶发 FAILED（`ConnectionAbortedError`，单跑 5/5 全绿）的成因；未读体这一行为**与 T-UI-021 的守卫改动无关**（守卫判定对该请求前后一致）。

**为什么要修**：拒绝路径的语义是「**显式告知失败**」（[00 §6 失败显式化](../../../../docs/技术架构-v2/00-架构总览.md)）。连接被复位时前端拿到的是 `fetch` 层的网络错误，六态信封**根本没机会显示**——本该 point at「令牌失效」的 401 退化成一句无信息量的「Failed to fetch」。这与 [`T-UI-003`](../M3/T-UI-003-对话端点请求体失败显式化.md) 在同一条链路上立下的「客户端不获 `RemoteDisconnected`」是同一类不变量，只是落在**更低的传输层**。

## ④ 对齐期的范围实测（2026-10-12，本机 Windows）

缺陷不是「拒绝分支」独有——**任何写完响应就关闭、而声明体未读净的路径**同症。四 MiB 体、各 8–20 次实测：

| 路径 | 现状（`ok` 次数 / 次数） |
|---|---|
| `POST /api/health`（401 拒绝） | 0/8 |
| `POST /api/nope`（404 拒绝） | 复现期 2/3、3/3 |
| `POST /api/chat`（**合法路由**，`_read_json_body` 截断在 256 KiB） | 7/8 |
| `GET /api/health`（`do_GET` 同样从不读体） | 1/8 |
| `GET /js/render.js`（静态壳；响应体较大） | 8/8 |

排空策略对照（同一 4 MiB 体、401 路径）：

| 策略 | `ok` |
|---|---|
| 不排空 | 0/8 |
| 排空 2 MiB（留 2 MiB 未读） | 17/20 |
| 排空 3 MiB（留 1 MiB 未读） | 19/20 |
| **读满声明的 4 MiB**（64 KiB 分块丢弃 / 256 KiB 分块） | **20/20 · 20/20** |

⇒ 判据是「**关闭时接收队列里不得有未读数据**」：只排一部分仍留残量、仍是间歇失败（`3 MiB` 那条已有一例中招）。故**必须读满声明的 `Content-Length`**。

## 验收标准（Given-When-Then）

- **GWT-1** Given 一枚大于套接字缓冲的请求体（4 MiB，见「复现」节的口径），When 打**三条拒绝路径**（缺令牌 ⇒ 401 / `Host` 不符 ⇒ 403 / 路径不在 `_POST_ROUTES` ⇒ 404），Then 客户端**拿到那支信封**（对应状态码 + 可 JSON 解析的载荷，含 `status` / `render`），**不**出现任何传输层异常（`ConnectionAbortedError` / `RemoteDisconnected` 等一律判失败）。
- **GWT-2** Given 同样的超大请求体，When 打**合法路由**（`POST /api/chat`，面未注入故回 `unavailable`），Then 客户端拿到 `200` 信封且**无传输层异常**；且**解析口径不变**——超过 `_MAX_BODY_BYTES` 的体仍只按前 256 KiB 解析，超出部分截断后按畸形处理（fail-closed 给 `{}`）。
- **GWT-3** Given 一轮**带请求体**的 `GET`（本服务从不支持该形态，但客户端可发），When 打 `/api/health`，Then 同 GWT-1（拿到信封、无传输层异常）。
- **GWT-4** Given **常态请求**（小体 / 空体 / 无 `Content-Length` / `Content-Length` 非数字或负数），When 打既有端点，Then 行为**逐字不变**：解析结果同前、既有 `tests/ui` 与 `tests/integration` 用例全绿（排空不得改变正常路径语义，也不得把「无体」当成「要读」。

## 假设与前提

- **A1**：**必须读满声明的 `Content-Length`** 才能消除复位——任何小于声明长度的排空都仍留未读数据、仍是间歇失败。**若错的影响**：修不干净（GWT-1 变成概率通过，等于没修）。**验证方式**：已由 ④ 对齐期的策略对照实测钉住（2 MiB 17/20、3 MiB 19/20 vs 读满 20/20 ×2），并由 GWT-1 在用例里守住。
- **A2**：**`Content-Length` 是本服务唯一的体长口径**——`_read_json_body` 只认它，`Transfer-Encoding: chunked` 从不受支持，故「读净」也只按它计。**若错的影响**：带 chunked 的客户端仍会在关闭时遇复位（但本服务本就不支持该形态，失败形态不变、不新增缺陷）。**验证方式**：全仓 grep 无 chunked 生产者（前端 `fetch` 与 `http.client` 均自动带 `Content-Length`）；GWT-1/2 以真客户端覆盖。
- **A3**：排空**只读、不解析、不落账**——被读掉的是**已被拒绝或已被截断**的体，丢弃它不改变任何已有语义（[`T-UI-003`](../M3/T-UI-003-对话端点请求体失败显式化.md) 的归一化口径：畸形 / 超大 ⇒ `{}`）。**若错的影响**：误改解析口径会让合法请求也走 fail-closed。**验证方式**：GWT-4 + 既有 `tests/ui` 全绿。
- **A4**：「有界」取**两个界**——**不多读一个字节**（上限＝声明的 `Content-Length`）+ **内存 O(64 KiB)**（分块读弃）；**不引入 socket 超时**。**若错的影响**：一个声明了巨大 `Content-Length` 却慢发 / 不发的本机客户端，会把一个 handler 线程按在**读**上（此前拒绝路径是即时响应）；线程服务下不影响其他连接，且**同一形态在 `_read_json_body` 上早已存在**（它本就按声明长度阻塞等读）。**验证方式**：A2/A4 由 GWT-1–3 与读代码覆盖；若要收紧为**时间界**，加一处 `settimeout` 即可（本任务未取，理由：不新增一类防护、也不改变威胁模型——攻击者恒可占用一个线程）。

## 复现

最小脚本（`PYTHONPATH=src` 后运行）——起真服务，向 401 路径 POST 一个大于套接字缓冲的体：

```python
import http.client
from st_agent.ui.server import serve

with serve(dev=False) as running:
    body = b"x" * (4 * 1024 * 1024)
    conn = http.client.HTTPConnection("127.0.0.1", running.port, timeout=5)
    conn.request(
        "POST", "/api/health", body=body,
        headers={"Host": f"127.0.0.1:{running.port}", "Content-Length": str(len(body))},
    )
    print(conn.getresponse().status)  # 多数轮次在此抛 ConnectionAbortedError
```

症状对照：体小（`b"{}"`）时稳定拿到 `401`。

## 备注

**未在本批修**——`T-UI-021` 的对齐范围只含守卫的允许集口径；混入一处 socket 语义改动会把两条口径揉进同一条决策。本条独立立项、待其自身 ④ 对齐。候选取向（留待 ④ 判）：拒绝前**有界排空**请求体 vs. 回拒绝后置 `close_connection` 并排空 vs. 交由 `Connection: close` + 读空的组合。

**④ 对齐结论**（2026-10-12，经负责人逐项拍定，见 [D-119](../../../决策日志.md)）：取「**响应写出前把声明的体读净**」这一条**不变量**（非只补拒绝分支），并按上表实测把覆盖扩到**全径**——`do_POST`（三条拒绝分支 + 重启闸门 + 接受路径）· `do_GET`（含静态壳）· `send_error` 出口（未支持的方法 ⇒ 501）。**「只补 POST 三条拒绝分支」与「POST 全径、GET 不动」均未取**——上表四条同症路径留着的就是同一个缺陷。界取「读满声明的 `Content-Length`、64 KiB 分块读弃、无 socket 超时」（理由与「不加时间界」的取舍见 [D-119](../../../决策日志.md) ② 与下文 `A4`）。任务备注原备的另两条候选**否决**——`close_connection` 早已为真（服务是 HTTP/1.0，`BaseHTTPRequestHandler` 每请求必关连接，故它不构成差异）；`Connection: close` 只影响**客户端**是否复用连接，与「关闭时是否有未读数据」无关（复位由未读数据触发，实测部分排空仍中招即是反证）。
