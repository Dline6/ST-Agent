# T-L3-006 · 能力安装 / 导入审批面（双通道）

> **本任务是 [L1 册 `D2`](../../../遗留问题/L1-遗留问题.md) 的点名承接方**（2026-09-29 由 [`T-L3-004.1`](../M1/T-L3-004.1-推理链时间线渲染件.md) / [`.2`](../M1/T-L3-004.2-上下文草稿裁决卡渲染件.md) 批次 ④ 对齐时就地修正归属；本批 2026-09-30 ④ 对齐后**两半都销**——写入入口 + 注销回收，见 D-066）。

## 目标
给 [01 §10](../../../../docs/技术架构-v2/01-平台共享契约.md) 权限模型的**逐项批准**这一环补上 L3 侧的**双通道**（对话 + 结构化面板）表现面：能力的权限申请在此**展示 + 逐项批准 / 拒绝**，并调用 L1 的 `SkillPermissionBook.declare` / `approve` / `reject` 落账。落点口径见 [03 §5.1](../../../../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md)（MCP Server 添加时「连接测试 + 权限申请展示 + 逐项批准」）与 [09 §3](../../../../docs/技术架构-v2/09-生态与分享.md)（导入流水线的「权限审核 → 用户批准 → 安装」）。

## 验收标准（Given-When-Then）

- Given 一个声明了权限的能力（挂载的 MCP Server 或待导入的分享物），When 打开审批面，Then 逐项列出其声明权限（经 `describe_permission` 的中性措辞），**不合并成一句话**
- Given 用户在审批面逐项批准，When 提交，Then 经 [`SkillPermissionBook.approve`](../../../../src/st_agent/l1/skills/permissions.py) 落账（挂载时先 `declare`），**未经批准的能力仍 `fail-closed`**
- Given 用户拒绝某项，When 提交，Then 落 `reject` 且原因随返回值透传（反馈池归 [L6](../../../../docs/技术架构-v2/08-L6-反思演进.md)）
- Given 未注入批准账本，When 打开审批面，Then `unavailable` + 点名（**不假装已批准**）

## 接口面
- **输入**：
  - [`l1/skills/permissions.py`](../../../../src/st_agent/l1/skills/permissions.py)——`SkillPermissionBook.declare` / `approve` / `reject`（写入入口**由本任务的 `open` / `approve` / `reject` 三个动词承担**；D2 销账）
  - [`l1/mcp/permissions.py`](../../../../src/st_agent/l1/mcp/permissions.py)——MCP 侧账本（`McpPermissionBook`），同一鸭子端口消费
  - [`contracts/permissions.py`](../../../../src/st_agent/contracts/permissions.py)——`PermissionApproval` / `describe_permission`（中性措辞的**唯一口径**）
  - [`contracts/ui_description.py`](../../../../src/st_agent/contracts/ui_description.py)——UI 描述契约（本批**新增** `permission_approval_card` 型）
  - [`l1/skills/registry.py`](../../../../src/st_agent/l1/skills/registry.py)——`SkillRegistry.unregister`（本批接 `permission_book.forget`，D2 回收半）
- **输出**：
  - [`l3/approval/panel.py`](../../../../src/st_agent/l3/approval/panel.py)——`CapabilityApprovalPanel` 门面（`open` / `view` / `approve` / `reject` / `submit`）· 载荷模型 `ApprovalItem` / `CapabilityApprovalView` / `ApprovalRequest` / `ApprovalSubmission`
  - [`l3/render/describe.py`](../../../../src/st_agent/l3/render/describe.py)——`describe_approval`（`permission_approval_card` 描述件；按 `permission` 并联 `items`（数据） + `labels`（生成文案））
  - [`ui/web/js/plugins/l3/permission_approval_card.js`](../../../../src/st_agent/ui/web/js/plugins/l3/permission_approval_card.js)——对应渲染件（逐条呈现、不合并、不落值）
  - **落盘：无新分区**——批准态落 L1 的 `config/skill-permissions/<base>.json`（Skill 侧） / `config/mcp-permission/<server_id>.json`（MCP 侧），本任务只接线

## 可关闭的遗留
- **L1 册 `D2`**（Skill 侧批准账本的写入入口无落点 + 注销时账本回收）——**本批两半都销**：
  - **写入入口** = `CapabilityApprovalPanel.open` 经账本 `declare`；`approve` / `reject` 逐项落账（GWT-1..3）
  - **回收联动** = `SkillRegistry.unregister` 经注入的 `permission_book.forget(base)`，**镜像** `McpServerRegistry.remove_server → permissions.forget` 的既有先例（03 §5.2 组合根回收序列；L1 册 `B1` 的同类处置）
  - 交付后按[册规](../../../遗留问题/README.md) 3/4 移入 L1 册「已闭（备查）」；留痕见执行日志 `[T-L3-006]`。

## 假设与前提

- **A1 · 审批面载体的归属**：L3 只产结构化视图数据 + 描述件；**渲染件同批交付**——同 [`.1`](../M1/T-L3-004.1-推理链时间线渲染件.md) / [`.2`](../M1/T-L3-004.2-上下文草稿裁决卡渲染件.md) 的先例（任务名带「渲染件」即 L3 视图数据 + 前端 JS 双份交付）。若错（须 L3 自出渲染产物）：与既有归属叠床架屋。**验证**：任务 `## 接口面` 已双列 L3 描述件 + UI 插件两条输出；`tests/ui/test_ui_registry.py` 断言两侧类型集合不漂移。
- **A2 · 与 [09 §3](../../../../docs/技术架构-v2/09-生态与分享.md) 导入流水线的分工**：[`T-ECO-002`](../../T-ECO-002-导入校验流水线官方Skill索引生态边界.md) 承载**校验流水线**，本任务承载**用户面**（展示 + 逐项批准）；两者经 `SkillPermissionBook` 交汇，**不各造一套批准记录**。若错（双写）：批准态分叉。**验证**：本任务的 `CapabilityApprovalPanel` **只经注入的账本端口**读写；`SkillPermissionBook` 与 `McpPermissionBook` 共用 `PermissionBook` 基类（`T-L1-009.1` 已消歧，D-042）。
- **A3 · 里程碑**：按 2026-09-29 负责人确认维持 M2 / P1；本批 ④ 复核无改判需要——MCP 挂载面（[03 §5.1](../../../../docs/技术架构-v2/03-L1-能力底座-Skills与MCP.md)）与复合 Skill 独立批准已在 T-L1-009.2 的 `SkillPermissionSource` 里就位，本任务补上「用户面」这一半即闭环。**验证**：`T-INT-003` 的 `depends_on` 已含本任务（[检查 7](../../../工作流.md) 兜底）。
- **A4 · 组件类型新增的契约代价**：本批**新建** `permission_approval_card` 型走 [铁律 8](../../../工程宪法.md) 顺序（01 §12 → 契约代码 → L3 / UI）。若错（复用 `report_card` / `conflict_adjudication_card`）：安全语义（逐条不合并 + 三态控件）压进不匹配的槽，槽词汇表反而更难懂。**验证**：`tests/contracts/test_ui_description.py` 已把实现型数量从 6 → 7 钉死；`ui/registry.py` 与本模块 `describe_approval` 的必填槽一致（`{"items","labels"}`）。
- **A5 · 不做浏览器交互接线（POST 审批端点）**：本批只交付视图数据 + 描述件 + 渲染件；**提交动作走对话面或面板通道的后续接线**（组合根 `build_m1_runtime` 的对话门面不接审批动词——那是 `T-INT-003` M2 关卡的装配面）。**验证**：`api.js` 只发 GET；渲染件的 `panel_field` 只给控件形态，不接交互。
