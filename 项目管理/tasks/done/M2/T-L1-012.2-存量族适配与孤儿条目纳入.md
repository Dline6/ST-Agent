# T-L1-012.2 · 存量族适配与孤儿条目纳入

## 目标

把仓库现存的 01 §7 条目接进 `.1` 交付的门面——**不改名**（存量前缀与其落盘布局保留，01 §7 原文即「各子系统自落 `config/<前缀>*.json` 属存储布局的一种，不构成契约」），各族以**适配器**登记进 `ConfigRegistryFacade`，读取与落值**一律委托各族 owner 的既有 API**（不另造一套校验 / 留痕，避免同一取值两条写路径分叉）。同批把 [02 §9](../../../../docs/技术架构-v2/02-L0-本地优先基座.md) 的**两条孤儿条目**（`retention.chat_history_days` / `retention.execution_log_days`——由 [`retention_config_entries()`](../../../../src/st_agent/l0/backup/models.py) 产出却**从未落盘、从未注册**）纳入注册。

## 验收标准（Given-When-Then）

- **GWT-1 · 孤儿纳入**：Given 全新仓库（`config` 分区为空），When `list()`，Then 两条 `retention.*` 条目**在列**（取值取 [`get_policy`](../../../../src/st_agent/l0/backup/backup.py) 的当前值，缺省即产品默认）；`set("retention.chat_history_days", 30)` 经 [`set_policy`](../../../../src/st_agent/l0/backup/backup.py) **真生效**（`get_policy` 读回 30）并产生 `ChangeRecord`——补上该族原本缺失的变更留痕。
- **GWT-2 · L1 三族委托既有 API**：`entry_for` / `list` / `apply` 对 `scheduler-policy/offline-catch-up`、`mcp-hub/reconnect-max-retries` 与 `mcp-hub/reconnect-interval-ms`、`llm-provider-host/<provider>` 四类条目**经各族 owner 的 `set` / `register` / `update` 落值**——取证方式是**既有校验仍生效**：`scheduler-policy` 的越界取值（非 `catch-up` / `skip`）经门面 `apply` 一样被拒（不绕过 owner 的值域门）。
- **GWT-3 · L2 族经组合根注入（本批只读）**：`memory-policy/<条目>` 族**不由 L1 直接 import L2**（[铁律 7](../../../工程宪法.md)「层间只向下依赖」）——由组合根把 L2 侧的适配器**注入** `register_family`；注入后 `list(scope="global")` 含该族条目、`entry(config_id)` 可读，未注入则该族**不在列**（不臆测、不伪造）。**该族的落值不在本批**（取值是对象 / 列表，见 A5），经门面 `apply` 一律 `fail-closed` 并点名 owner API。
- **GWT-4 · 不改名 · 存量零回归**：既有四族的 `config` / `execution_log` 路径与文件**一字未变**；各族既有用例（`tests/l1/test_scheduler_policy*.py` / `test_mcp_*` / `test_sandbox*` / `tests/l2/test_memory_config*`）全绿，`config` 分区内 `list_files` 的既有条目集合在门面注册前后相同。
- **GWT-5 · 门面为唯一登记入口、族可扩展**：`register_family(family)` 是本叶存量族与后续新族的**唯一**接入点；同一 `config_id` 被两族声明时**即拒**（不静默后者覆盖前者）。

## 假设与前提

- **A1 · 「适配」＝委托 owner API，不是直接读写文件**：`SchedulerPolicy.set` 的值域校验、`McpHubStateMachine.set` 的非负整数门、`MemoryPolicyStore.set` 的「值未变不落盘」都必须经门面照样成立——门面是**统一入口**，不是**旁路写盘**。
  - 若错的影响：若门面直接按 `config_id` 派生路径写 `ConfigEntry`，会绕过各族校验，同一取值两条写路径分叉（正是 [01 §7](../../../../docs/技术架构-v2/01-平台共享契约.md) 单一事实源欲防之事）；返工面＝各适配器的落值实现。
  - 验证方式：GWT-2 的越界取值经门面一样被拒；GWT-4 的存量用例全绿。
- **A2 · retention 族的留痕由门面补，不改 L0 的 `set_policy` 签名**：L0 的 [`set_policy`](../../../../src/st_agent/l0/backup/backup.py) 只落 `RetentionPolicy`、**不产生** `ChangeRecord`（其条目形态 `record_history=True` 尚未被兑现）。门面在 `apply` 委托 `set_policy` **之后**补落一条 `ChangeRecord`（落 `execution_log`，前缀归本族），**不改** L0 既有函数签名与既有用例。
  - 若错的影响：若判定留痕应归 L0 产出（须改 `set_policy` 签名 / 加可选参数），则返工面＝L0 backup 一处 + 其既有用例（`T-L0-006` 已 `done`，属对既有交付面的增补）。
  - 验证方式：GWT-1 的 `apply` 返回非空 `ChangeRecord` 且 `get_policy` 读回新值；`tests/l0/test_backup.py` 既有用例全绿（签名未变）。
- **A3 · memory-policy 族的适配器落 L2、注入方是组合根**：L2 在 L1 之上，L1 门面**不得** import L2（[铁律 7](../../../工程宪法.md)）。故适配器工厂落 `l2/memory/`，由 `.3` 的组合根装配时传入。
  - 若错的影响：若为省事让 L1 import L2，`tests/test_layering.py`（层间依赖方向）当场红；返工面＝适配器落点。
  - 验证方式：GWT-3（未注入即不在列）＋ `tests/test_layering.py` 全绿。
- **A4 · 门面注册的族集合在 `.3` 的组合根里定，不在 `families.py` 里硬编**：`families.py` 只**提供**各族适配器类；哪些族进当前运行时（如 memory-policy 是否在场）由组合根决定，避免 L1 静态依赖「L2 一定在场」。
  - 若错的影响：若在 `families.py` 里硬编全套族，未装 L2 的运行时会构造失败；返工面＝注册点从库搬到组合根。
  - 验证方式：GWT-3（注入与否决定在列）＋ `.3` 的装配用例。
- **A5 · 写面按「取值形状」划界，不是按族划分**：门面 `apply` 的语义是**逐条目一次落值**（01 §7「一次调用同时完成『值生效』与『产生 `change_id`』」），故**标量条目**（`retention.*` / `scheduler-policy/offline-catch-up` / `mcp-hub/*` / `llm-provider-host/*`）走门面并**委托 owner 的 `set` / `update`**；**复合取值条目**（L2 `memory-policy/*` 的 baseline / dynamics 是对象、whitelist / questions 是列表）**本批只读**，其写面归各自 owner API（把对象 / 列表塞进统一标量落值面只会造出一条与 owner 校验并行的第二写路径）。
  - 若错的影响：若判定门面应连复合取值一并落值，须在 L2 补逐条 setter 包装（约 150–200 行）且当前**零消费方**；返工面＝L2 的新包装模块 + 本叶 GWT-3。
  - 验证方式：GWT-3 的 `apply` fail-closed 分支（点名 owner API）＋ 标量四族的落值经门面后 **owner 的既有校验仍生效**（GWT-2）。
