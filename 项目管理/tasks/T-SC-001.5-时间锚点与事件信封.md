# T-SC-001.5 · 时间锚点 dataset_snapshot_id / as_of 与事件信封

## 目标
实现 [01-平台共享契约](../../docs/技术架构-v2/01-平台共享契约.md) §8 的时间锚点类型（dataset_snapshot_id + as_of，用户本地时区语义、内部传输带时区）与 §11 事件清单的统一事件信封（核心事件名 + 强制携带关联 trace_id / change_id）。新鲜度水位与陈旧判据本身由 L0（T-L0-005）按数据库设计 sync_state 落地，此处只定类型口径。

## 验收标准（Given-When-Then）
- GWT-5：Given 快照/新鲜度需求，When 标注数据时间，Then 统一用 `dataset_snapshot_id` + `as_of`（§8），不另立第二套口径。
- GWT-SC11：Given 一个跨层上行事件，When 构造事件，Then 事件名属于 §11 核心事件清单且携带关联 trace_id / change_id（如适用）。

## 接口面
> 追补于 2026-09-26：本任务完成早于接口面机制落地，据已合入代码与执行日志回溯填写（非 ④ 对齐时填写）。
- 输入（消费的前置接口）：T-SC-001.1 的 ID 类型（`dataset_snapshot_id` / `change_id` / `trace_id`）
- 输出（本任务交付的公共 API / 落盘位置）：
  - `st_agent.contracts.time_events`：`DataAnchor`（`snapshot_id` / `as_of` / 六数据域 / `.is_stale`）、`StalenessVerdict`、`PlatformEvent`（10 事件名，构造期强制 `trace_id` / `change_id` 关联）
  - 无本任务落盘（事件信封类型；发布与订阅由各层承载）
  - 消费方：T-L0-005（水位 → `StalenessVerdict`）、T-L1-001.4（复用新鲜度查询，未开工）、T-L1-001.3（`BehaviorViolation` 载荷）
