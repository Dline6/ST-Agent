# 工作流（每个叶子任务跑一遍）

```
① Spec    ← 读 Story 的验收标准（What，只读，不改）—— ../docs/PRD-v2-Agent/story-NN.md
② Plan    ← 读对应架构层的数据/接口契约（How，只读，不改）—— ../docs/技术架构-v2/0X-LN.md
③ Task    ← 建 tasks/T-*.md 任务文件（唯一真相源）；按「拆分触发」判定是否拆分；填 depends_on；账本行由 render 生成
④ Align   ← 开工闸门：向人复述意图并获确认后才动手（不可跳过）
⑤ Implement ← 只喂「工程宪法 + 该任务文件 + 它链接到的契约小节 + 未决 open 段」给 Agent
⑥ Verify & Log ← 跑测试 + 断链校验 → 写执行日志（有决策则同步决策日志）→ 任务文件 status=done → 跑 render（派生父状态 + 刷新账本）
⑦ Sync    ← 若触发契约/架构变更：先改 01 平台契约 → 同步架构文档 → 更新受影响任务 + 记决策日志
```

## ④ 意图对齐（开工闸门 · 宪法第 11 条）

Agent 读完 Spec/Plan、建好任务之后、写代码之前，用一段话向人复述并等确认：
- 我理解这个任务要交付什么（一句话）
- 验收怎么算通过（逐条对齐 Story 的 Given-When-Then）
- 我打算怎么做（技术路径要点）
- 我做了哪些假设 / 有没有 open 未决（若有 → 先登记 [阻塞与未决.md](阻塞与未决.md)，任务转 `blocked` 等回填，不对齐不放行）

人回「对」之前不得进入 ⑤。对齐结论（尤其假设与取舍）用一行写进该任务的执行日志 `对齐` 字段。

## 拆分触发（命中任一即拆子任务）

- 验收 GWT 条数 > 5
- 涉及 2 个及以上契约小节 / 架构层
- 跨越 spec 与 plan 的一次性改动（如"建 schema + 写查询 + 补视图"）
- 单次预计 Agent 会话轮次 > 20
- 中途新增需要独立记录的决策

拆分方式：原任务转为父节点，新任务用点号 ID（`T-L2-003` → `T-L2-003.1` / `.2` …，嵌套建议 ≤ 2 层）。

## 父任务状态派生（禁止手写）

父任务 `status` 与 `children` 由叶子聚合自动算，Agent 与人都不得手填：

| 条件 | 父状态 |
|---|---|
| 所有 children 都 `done` | `done` |
| 任一 child `blocked` | `blocked` |
| 任一 child `doing` | `doing` |
| 其余 | `todo` |

父任务 `depends_on` = 所有 children 的 `depends_on` 并集，去掉指向父自身子树的边。派生由 `tools/render_ledger.py render`（或 `status`）自动重算，人不手填父状态。

## 调度规则（AI 如何选下一个任务）

1. 就绪集 = `status=todo` 且 `depends_on` 全部 `done` 且父链无 `blocked` 的**叶子任务**
2. 就绪集内排序：`priority`（P0>P1>P2）→ 架构层号升序 → id 字典序，取队首
3. 收工顺序严格为：任务文件置 `doing` → 读 Spec/Plan → **④ 对齐确认** → 干活 → 写日志 → 任务文件置 `done` → 跑 `render`（派生父状态 + 刷新账本）
4. 冷启动实现顺序：`01 契约 → L0 → L1 → L2 → L3 → L4 → L5 → L6 → ECO`

## 任务文件字段（YAML frontmatter）

```yaml
id:            # 点分层级号 T-<层>-<序号>[.子号]
parent:        # 上级 id，顶层为 null
title:         # 一句话
story:         # 回指 ../docs/PRD-v2-Agent/...
arch:          # 回指 ../docs/技术架构-v2/...（文件相对，即 ../../docs/）
arch_link:     # 供账本渲染的 [标签](../../docs/..) 串；render 会自动改写为 ../docs 显示
priority:      # P0 | P1 | P2
milestone:     # M0 | M1 | M2 ...
depends_on: [] # 前置 id 列表
status:        # todo | doing | blocked | done
decisions: []  # 引用的 D-NNN
verify:        # 验收证据摘要 + 执行日志锚点（done 时填）
```

正文只写三块：**目标 / 验收标准（GWT） / 涉及契约（链接到具体小节）**。实现细节不进文档，留给代码、commit 与执行日志。

## 账本生成与归档（tasks/ 是唯一真相源）

`任务账本.md` 是**派生视图，禁止手改**——它的表格、里程碑完成度、就绪集全部由 `tools/render_ledger.py` 从 `tasks/*.md` 的 frontmatter 生成。改任务只改对应 `tasks/T-*.md`，再跑命令刷新。这从根上杜绝"账本一行 + 文件一份"双写漂移。

```bash
# 在 项目管理/ 目录下
python tools/render_ledger.py render    # 扫描 tasks/ 与 tasks/done/ → 重新生成 任务账本.md
python tools/render_ledger.py status    # 按 children 派生父状态 + 打印就绪集
python tools/render_ledger.py archive   # 把「全部任务 done」的里程碑整批移入 tasks/done/<Mn>/
python tools/render_ledger.py archive --dry   # 预览将归档哪些里程碑，不实际移动
python tools/verify_docs.py             # 收工/提交前一键自检：断链+依赖图+账本同步+过期措辞（--strict 更严 / --fix 顺带刷新账本）
```

**生命周期**：任务 `done` 后其行仍留在账本活跃区；当某里程碑下所有任务都 `done`，跑 `archive` 把这一批文件整体移到 `tasks/done/M0/`，账本对应区塌缩成"✅ M0 12/12"一行并转入"已归档"节——这样 `tasks/` 顶层永远只有进行中的工作，账本不会随时间无限膨胀。

Agent 每次把任务置 `done` 后（工作流 ⑥）跑一次 `render`；收工一批任务后若发现某里程碑满员，顺手跑 `archive`。断链校验会覆盖账本与所有任务文件的相对链接（含 `tasks/*.md` 回指 `../../docs/` 的链接）。

## 入库（Git）

七步跑完后如何落到版本库——分支命名绑定任务 ID、提交信息带 `Task:` trailer、`.gitignore` 数据主权红线、pre-commit/PR 卡点、里程碑 tag——统一见 [Git协作规范.md](Git协作规范.md)。收工 commit 前过一遍其 §5.3 checklist（`verify_docs.py --strict` + 账本已 `render` + 执行日志含验证行）。
