# 工作流（每个叶子任务跑一遍）

```
① Spec    ← 读 Story 的验收标准（What，只读，不改）—— ../docs/PRD-v2-Agent/story-NN.md
② Plan    ← 读对应架构层的数据/接口契约（How，只读，不改）—— ../docs/技术架构-v2/0X-LN.md
③ Task    ← 建 tasks/T-*.md 任务文件（唯一真相源）；按「拆分触发」判定是否拆分；填 depends_on；账本行由 render 生成
④ Align   ← 开工闸门：向人复述意图并获确认后才动手（不可跳过）
⑤ Implement ← 只喂「工程宪法 + 该任务文件（含其 `## 接口面` 交接点）+ 它链接到的契约小节 + 未决 open 段」给 Agent
⑥ Verify & Log ← 跑测试 + 断链校验 → 写执行日志（含假设复核行；有决策则同步决策日志）→ 任务文件 status=done → 跑 render（派生父状态 + 刷新账本）
⑦ Sync    ← 若触发契约/架构变更：先改 01 平台契约 → 同步架构文档 → 更新受影响任务 + 记决策日志
```

## ④ 意图对齐（开工闸门 · 宪法第 11 条）

Agent 读完 Spec/Plan、建好任务之后、写代码之前，用一段话向人复述并等确认：
- 我理解这个任务要交付什么（一句话）
- 验收怎么算通过（逐条对齐 Story 的 Given-When-Then）
- **接口面**：输入从哪来（逐条点名上游任务 id + 具体 API/落盘位置）、输出去哪（本任务交付的公共 API 与落盘位置）
- 我打算怎么做（技术路径要点）
- 我做了哪些假设 / 有没有 open 未决（若有 → 先登记 [阻塞与未决.md](阻塞与未决.md)，任务转 `blocked` 等回填，不对齐不放行）

人回「对」之前不得进入 ⑤。对齐结论落两处：① 任务文件两节——`## 接口面` 实填（输入逐条给「上游任务 id + 具体 API/落盘位置」，上游尚未交付的写「待 `<id>` 交付」；输出列本任务交付的公共 API 与落盘位置，暂不交付的显式标注）与 `## 假设与前提` 节按 `A1、A2…` 编号写入（每条含前提内容 + 若错的影响 + 验证方式；确认无假设写 `无（<原因>）`，不留空）；② 执行日志 `对齐` 行引用编号（如 `假设见任务 A1–A3`）。

**接口面未实填不放行**——它是第 ⑤ 步受限上下文里唯一的跨任务接口交接点；缺了，实现方只能去翻兄弟任务的代码猜，接口漂移会在下游任务开工时才暴露（Q-001 组合根缺口即此类）。

## 拆分触发（命中任一即拆子任务）

- 验收 GWT 条数 > 5
- 涉及 2 个及以上契约小节 / 架构层
- 跨越 spec 与 plan 的一次性改动（如"建 schema + 写查询 + 补视图"）
- 单次预计 Agent 会话轮次 > 20
- 中途新增需要独立记录的决策

拆分方式：原任务转为父节点，新任务用点号 ID（`T-L2-003` → `T-L2-003.1` / `.2` …，嵌套建议 ≤ 2 层）。跨层装配与端到端验证不按此拆分——归里程碑集成关卡（见下节）。

## 集成关卡（里程碑收口）

每个有任务的里程碑必须有**一个**集成关卡任务（`T-INT-NNN`，与里程碑同号），把该里程碑分散在各任务里的交付**装配起来跑一次端到端**。单任务的 GWT 全是注入 Fake 的单测，装配关系与跨层数据流恰恰是它们集体覆盖不到的部分——Q-001（组合根无人承载）就是这类缺口的实例。

- **锚点**：验收标准取自 [00-架构总览 §5 端到端数据流](../docs/技术架构-v2/00-架构总览.md)（八步生命周期）与所辖层间的接口约定，逐条改写为 GWT；**不重复**单任务已覆盖的单元行为。
- **依赖**：`depends_on` 必须覆盖本里程碑全部叶子任务；并与上一里程碑的关卡串联（`T-INT-00n` 依赖 `T-INT-00(n-1)`）。覆盖度由 `verify_docs.py` 检查 7 把关，新增任务后记得同步补进关卡依赖。
- **字段**：`priority: P0`、`milestone` 同所辖里程碑、`parent: null`（跨层，不挂任何层的子树）；层号排序在最后，故它天然最后进入就绪集。
- **例外**：长跑/运营类任务（真实网络、小时级批处理）可在 frontmatter 标 `gate: skip` 并在备注写明理由——不计入关卡依赖覆盖、不阻塞收口；但完成前该里程碑仍不能 `archive`。功能交付任务不得使用该标记。
- **收口语义**：里程碑 `archive` 与打 tag 之前，其关卡任务必须 `done`——否则「骨架打通」「最小闭环」这类里程碑目标是**未经装配验证的声明**。
- **真实路径**：涉及真实网络/长跑的部分（真实抓取器全量、真实 LLM 端点）标 `@pytest.mark.live` 放 `tests/live/`，默认排除、按需单跑；离线部分（装配 + Fake 数据）必须进默认 `pytest`，保证 CI 可重复。

## 父任务状态派生（禁止手写）

父任务 `status` 与 `children` 由叶子聚合自动算，Agent 与人都不得手填：

| 条件 | 父状态 |
|---|---|
| 所有 children 都 `done` | `done` |
| 任一 child `blocked` | `blocked` |
| 任一 child `doing` | `doing` |
| 其余 | `todo` |

父任务 `depends_on` = 所有 children 的 `depends_on` 并集，去掉指向父自身子树的边。派生由 `tools/render_ledger.py render`（或 `status`）自动重算，人不手填父状态。

## 调度规则（AI 如何选下一个任务）

1. 就绪集 = `status=todo` 且 `depends_on` 全部 `done` 且父链无 `blocked` 的**叶子任务**
2. 就绪集内排序：`priority`（P0>P1>P2）→ 架构层号升序 → id 字典序，取队首
3. 收工顺序严格为：任务文件置 `doing` → 读 Spec/Plan → **④ 对齐确认**（假设编号进任务文件）→ 干活 → 写日志（含假设复核：成立 / 已推翻→联动未决或新任务）→ 任务文件置 `done` → 跑 `render`（派生父状态 + 刷新账本）
4. 冷启动实现顺序：`01 契约 → L0 → L1 → L2 → L3 → L4 → L5 → L6 → ECO`

## 任务文件字段（YAML frontmatter）

```yaml
id:            # 点分层级号 T-<层>-<序号>[.子号]
parent:        # 上级 id，顶层为 null
title:         # 一句话
story:         # 回指 ../docs/PRD-v2-Agent/...
arch:          # 回指 ../docs/技术架构-v2/...（文件相对，即 ../../docs/）
arch_link:     # 供账本渲染的 [标签](../../docs/..) 串；render 会自动改写为 ../docs 显示
priority:      # P0 | P1 | P2
milestone:     # M0 | M1 | M2 ...
depends_on: [] # 前置 id 列表
status:        # todo | doing | blocked | done
decisions: []  # 引用的 D-NNN
verify:        # 验收证据摘要 + 执行日志锚点（done 时填）
```

正文只写五块：**目标 / 验收标准（GWT） / 接口面 / 假设与前提 / 涉及契约（链接到具体小节）**。实现细节不进文档，留给代码、commit 与执行日志。

`## 接口面` 是**跨任务交接点**（2026-09-26 机制落地）：**输入**逐条列消费的前置接口（上游任务 id + 具体 API/落盘位置），**输出**列本任务交付的公共 API 与落盘位置。它是第 ⑤ 步受限上下文里唯一的接口来源——架构文档写的是设计契约（字段表），不是实现后的调用面。`doing` / `blocked` / `done` 任务缺该节或仍为占位，`verify_docs.py --strict` 判失败（同样适用历史豁免清单）。

`## 假设与前提` 格式（④ 对齐时填，`todo` 可留占位）：每条 `A<n>` 编号，含三要素——前提内容 / 若错的影响（波及任务或返工面）/ 验证方式（何时、如何证实或证伪）；确认无假设写 `无（<原因，如：纯执行既定协议>）`。`doing` / `blocked` / `done` 任务缺该节或仍为占位，`verify_docs.py --strict` 判失败（2026-09-25 机制落地前已 `done` 的 12 个历史任务除外，不追补）。

## 账本生成与归档（tasks/ 是唯一真相源）

`任务账本.md` 是**派生视图，禁止手改**——它的表格、里程碑完成度、就绪集全部由 `tools/render_ledger.py` 从 `tasks/*.md` 的 frontmatter 生成。改任务只改对应 `tasks/T-*.md`，再跑命令刷新。这从根上杜绝"账本一行 + 文件一份"双写漂移。

```bash
# 在 项目管理/ 目录下
python tools/render_ledger.py render    # 扫描 tasks/ 与 tasks/done/ → 重新生成 任务账本.md
python tools/render_ledger.py status    # 按 children 派生父状态 + 打印就绪集
python tools/render_ledger.py archive   # 把「全部任务 done」的里程碑整批移入 tasks/done/<Mn>/
python tools/render_ledger.py archive --dry   # 预览将归档哪些里程碑，不实际移动
python tools/verify_docs.py             # 收工/提交前一键自检：断链+依赖图+账本同步+过期措辞+假设完整+接口面+集成关卡（--strict 更严 / --fix 顺带刷新账本）
```

**生命周期**：任务 `done` 后其行仍留在账本活跃区；当某里程碑下所有任务都 `done`，跑 `archive` 把这一批文件整体移到 `tasks/done/M0/`，账本对应区塌缩成"✅ M0 12/12"一行并转入"已归档"节——这样 `tasks/` 顶层永远只有进行中的工作，账本不会随时间无限膨胀。

Agent 每次把任务置 `done` 后（工作流 ⑥）跑一次 `render`；收工一批任务后若发现某里程碑满员，顺手跑 `archive`。断链校验会覆盖账本与所有任务文件的相对链接（含 `tasks/*.md` 回指 `../../docs/` 的链接）。

## 入库（Git）

七步跑完后如何落到版本库——分支命名绑定任务 ID、提交信息带 `Task:` trailer、`.gitignore` 数据主权红线、pre-commit/PR 卡点、里程碑 tag——统一见 [Git协作规范.md](Git协作规范.md)。收工 commit 前过一遍其 §5.3 checklist（`verify_docs.py --strict` + 账本已 `render` + 执行日志含验证行）。
