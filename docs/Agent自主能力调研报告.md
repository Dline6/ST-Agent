# Agent 自主能力调研报告

> **状态：待商讨 · 未立项。** 本报告回答两个问题：①主流 Agent 原生具备哪些工具与能力；②本项目要补齐"自主工具调用"这条根，还缺哪些机制。

## 0. 结论摘要

**一句话诊断**：项目缺的不是"工具"，而是**运行时循环**。L1 已经是一个相当完整的**工具执行器**（权限账本、沙箱、DAG、留痕俱全），但它被一条**确定性派发链**驱动——模型只在链的**起点**出现一次（把输入归成一个意图），此后全程不参与。主流 Agent 与本项目的根本分岔在于：**模型在循环里，还是模型在循环外。**

**三个层次的真实缺口**（按"离根的距离"排序）：

| 层 | 缺口 | 现状实证 |
|---|---|---|
| **根** | 无 Agent Loop；模型看不到工具清单；工具结果不回填模型 | `http_transport.py:122-129` 请求体只有 `messages`，无 `tools`；全项目无 loop 模式 |
| **中** | 上下文管理建成未接线；对话历史从不回填；无预算/压缩 | `assemble_context` 已实现但**只有测试调用**（`l3/chat/session.py:477`） |
| **中** | 记忆只以"条数"进 prompt；无向量/语义检索；RAG 被显式延后 | `l4/ports.py:154-161` 只传 `memory_count`；`reader.py:128` 为子串加权；D-031 明写延后 |

**建议的最小闭环**（不是立项，是方向）：把 L1 `SkillRunner` 当作**已有**的工具执行面，在其外围补一个运行时循环，循环的两半分别是「工具契约暴露」与「结果回填」——**这两半项目里都不存在**。

## 1. 主流 Agent 的原生工具面

### 1.1 Claude / Claude Code

**评价：工具面最宽，"目录 + 按需展开"是它的核心工程手法。**

本会话实际暴露给我的工具（可直接佐证）：文件面 `Read` / `Edit` / `Write` / `Glob` / `Grep` / `NotebookEdit`；执行面 `Bash`；网络面 `WebFetch` / `WebSearch`；编排面 `Agent`（子 Agent）/ `Skill`（技能）/ `TodoWrite`（任务）/ `ExitPlanMode`（计划闸门）；外接面 MCP tools；任务面后台任务。另有 hooks（PreToolUse / PostToolUse / PreCompact / SubagentStop 等十余个事件点）、权限模式（default / acceptEdits / plan / auto / bypassPermissions）、自动记忆目录、插件系统。

平台侧（API 层）另有一组与项目诉求高度相关的原生工具：**memory tool**（跨会话记忆读写）、**tool search**（工具太多时按需检索，避免 schema 挤爆窗口）、**context editing**（主动清理上下文）、**code execution**、**computer use**、**text editor**、**web search**。

### 1.2 OpenAI Codex

**评价：工具数最少但最"工程完备"，上下文管理与多 Agent 是它的重资产。**

从仓库源码实取（`codex-rs/core/src/tools/`，非文档转述）：

- **核心工具**：`exec_command`、`write_stdin`（交互式 shell）、`apply_patch`、`update_plan`（显式计划工具）、`view_image`、`current_time`
- **工具治理**：`tool_search`（延迟加载）、`request_permissions`、`request_user_input`（+ async 变体）、`send_message_to_user_async`
- **上下文自省**：`get_context_remaining`（模型可自查还剩多少窗口）、`new_context_window`
- **多 Agent**：`spawn_agent`、`send_input`、`wait_agent`、`resume_agent`、`close_agent`、`interrupt_agent`、`list_agents`、`send_message`、`followup_task`

### 1.3 WorkBuddy

**评价：与本项目形态最接近（桌面常驻 + 本地执行 + 扩展生态），其 24 个机制几乎是一份"要补什么"的清单。**

## 2. 项目现状实测

### 2.1 六个关键事实（均附证据）

1. **LLM 出网请求体没有工具面。** `l0/llm/http_transport.py:122-129` 的 body 只有 `model` / `messages` / `stream`，无 `tools` / `tool_choice` / `response_format`。
2. **端点能力不声明函数调用。** `l0/llm/models.py:63` 的 `EndpointCapability` 只有 `max_context_tokens` 与 `supports_structured_output`；结构化输出靠 prompt 约定 JSON + 手工解析（`l3/intent/protocol.py:591`、`l4/ports.py:107`）。
3. **全项目只有 5 个 LLM 调用点，且都是"单轮无状态纯文本"。** `l3/intent/protocol.py:659`（意图理解）、`l4/ports.py:163` 与 `:295`（视角合成 / 证据重研判）、`app.py:1218` 与 `:1348`（L6 训练理解 / 模式观察）。每个调用点**各自拼字符串**，无系统提示、无历史、无记忆正文。
4. **上下文装配器已建成，但生产链路零调用。** `l3/chat/session.py:477` 的 `assemble_context`（含 4000 字符预算、记忆切片近端截取）**只被 `tests/l3/test_chat_session.py` 引用**——这是一处已交付但未接线的资产。
5. **记忆有图谱、有读写，但进不了 prompt 正文。** L4 编排确实读了记忆切片并记 `memory_read` 链步（`l4/deliberation.py:319-360`），但注回 prompt 的只有 `memory_count=len(...)`（`l4/ports.py:154-161`）。L1 Skill **完全读不到记忆**——`SkillContext`（`l1/runner/runner.py:79-113`）只有 `llm` / `gateway` / `freshness` / `sandbox`，**无记忆句柄**。
6. **检索是结构性子串匹配，无向量、无 RAG。** `l2/memory/reader.py:128` 的 `query` 按任务类型亲和 + 主题子串 + 置信度 + 时近度线性加权（`:158-189`），模块文档明写"语义检索不在此面"。全仓 grep `embedding|faiss|chroma|qdrant|cosine|rerank` **零命中**；核心依赖仅 `pydantic` + `cryptography`。RAG 在 D-031 ④ 被**刻意延后**（`项目管理/决策日志.md:404-415`）。

### 2.2 已有的资产（明确不要重造）

- **工具执行面**：`SkillRunner`（`l1/runner/runner.py`）——参数校验、输入/输出 schema 核验、依赖 DAG 递归、权限逐项核对、沙箱会话、执行留痕，**这是 agent loop 需要的"工具执行"组件的 90%**。
- **工具注册与契约**：`SkillDescriptor` + `ToolSpec`（`l1/mcp/models.py:42`，含 name/description/input_schema/output_schema）——**已经是工具契约的形状**，只是从没被序列化给模型。
- **治理三角**：权限账本（`l1/permission_book.py`）、沙箱（`l1/sandbox/`）、Trace 链（`contracts/trace.py`）。
- **调度器**：`l1/scheduler/`（cron、tick、catch_up、run_forever）——自主性的"时间维度"已具备。
- **会话持久化**：`SessionStore`（`l3/chat/session.py:246`）——树状可分支、可搜索、可导出，**但历史从不回填 prompt**（仅 L6 模式观察取样最近 40 条）。
- **反思闭环骨架**：L6 提案/实验/变更/授权/回滚全套，由常驻循环定时驱动（`app.py:2095-2111`、`__main__.py:305-320`），但默认走人工闸门（`l6/authorization.py:212-243` 仅 `autonomous` 档 + 低风险放行；`memory.*` 恒 `never-autonomous`）。

## 3. 差距分析与根因

### 3.1 根因：缺"运行时"这一层

```
现在：  用户输入 → [模型: 归一个意图] → 确定性路由 → 执行 → 渲染        ← 模型在循环外

主流：  用户输入 → ┌─→ [模型: 看工具清单 + 历史 → 出一个动作]
                  │        ↓
                  │   权限/沙箱闸门 → 工具执行
                  │        ↓
                  └── 结果回填 ← ─ ─ ─ ─ ─ ─ ┘                        ← 模型在循环里
```

项目把"模型判断"压缩成了**一次性的入口分类**，之后全靠声明式编排。这在**受限域**（投资决策里可枚举的少数意图——本次增补前为六类）是**优点**——确定性、可审计、不会幻觉出工具。但它的天花板是**组合爆炸**：任何"先查 A，看结果再决定要不要查 B"的任务，都必须预先写成 Skill 依赖或工作流，模型无法临场编排。

**L4 多视角推理是最典型的受害者**：它是一套固定算法编排（roster → lens → divergence → aggregation），LLM 只在每个 lens 里被单次调用。它无法"根据第一轮视角的分歧，决定第二轮该追问哪个视角"。

## 4. 与项目铁律的张力（**本次商讨的核心**）

新增自主能力会同时撞上三条铁律，这些不是实现细节，是**必须先定的方向问题**：

**张力一：铁律 2「Agent 严格中性」vs 循环内的自主文本。**
现状之所以能轻松过中性闸门，是因为模型的输出被压缩到极小面（一行 JSON 意图）。一旦模型在循环里自主推理、自主生成中间文本，**未过闸门的自由文本会成倍增长**。需要定：循环的中间推理是否**永不外显**、只对**最终交付物**过中性闸门？还是每一步都要过（会严重拖慢并可能误杀）？

**张力二：铁律 7「层间只向下依赖」vs 循环天然跨层。**
一个 loop 要同时够到 L1（执行工具）、L2（记忆）、L4（推理）、L6（训练）。现有层序 `l3 < l4 < l6` 且跨层一律经 `01-平台共享契约`。循环**放哪一层**是个真问题——放 L3 会让 L3 反向依赖 L4/L6；放组合根（`app.py`）则把编排逻辑堆进装配点。可能需要**新开一层（L7 运行时）**或**在契约层新增"运行时面"**。

**张力三：用户确认闸门 vs 自主执行。**
现状是"未经确认的确认卡直接 `validation_failed` 拒绝派发"（`l3/dispatch/bus.py:306`）——这是**每次必经**的硬闸门。自主 loop 的本质是**取消逐步确认**。需要定：闸门从"每次必经"改为"按风险分级"？分级依据是什么（读操作放行 / 写操作与出网必经 / 记忆写入恒必经，与 L6 授权档位对齐）？

> 这三条张力决定了架构形态，**建议在画任何技术方案之前先定这三条**。

## 6. 张力三方案比选（自主度与确认闸门）

**先摆既有资产**——项目**已经有**一套完整的自主度机制，只是作用域被锁死在 L6 演进：

| 构件 | 内容 | 位置 |
|---|---|---|
| `Tier` | `manual` / `collaborative`（缺省）/ `autonomous` | `l6/authorization.py:61-65` |
| `RiskClass` | `autonomous-ok` / `collaborative-required` / `never-autonomous` | `:67-70` |
| 判据 | `permit_decision(scope) -> PermitDecision`：非自主档一律不放行；自主档也只放行低风险范围 | `:212-238` |
| 保守默认 | 未命中任何规则 → 按**必须协作**，不静默放行 | `:202-208` |
| 红线单点 | `memory.` / `memory-policy/` 恒 `never-autonomous`（08 §7） | `:86-99` |
| 治理配套 | 档位与清单均为 01 §7 条目、切换留痕；UI 设置页已交付（T-UI-004.3） | `:245-263` |

**所以张力三的真问题不是"要不要有闸门"，而是"分级键是什么、在哪一层管"。** 现有闸门的形态本身（三档 + 白名单 + 保守默认 + fail-closed）无需改动，要改的只是**它管谁**。

### 方案 T-1：复用 L6 档位，分级键从 `config_id` 泛化到"动作标识"

- **做法**：`classify()` 的键空间从 config 前缀扩到工具/动作标识（`skill.sk_stock_watch`、`memory.write`、`net.egress` …），三档与三风险类原样复用；循环内每个动作过 `permit(scope)`
- **利**：零新概念；留痕、UI、白名单语义全部现成；memory 红线一处生效
- **弊**：L6 是**反思演进层**，借它管"日常工具调用"会让层职责模糊——演进是每周、低频、配置面；运行期授权是每轮、高频、动作面，**两种节律**
- **改动面**：`l6/authorization.py` 泛化键域；01 §7 条目语义扩写

### 方案 T-2：新立独立的"运行授权"面，与 L6 档位并列

- **做法**：01 §7 新增 `agent.autonomy-tier` + `agent.action-grading`；L6 的 `evolution.*` 不动
- **利**：语义干净，两套节律各自演进；L6 边界不模糊
- **弊**：**两张分级清单必然漂移**——`memory.*` 要在两处都标 `never-autonomous`，将来加一条红线容易只改一处；UI 要维护两个设置页
- **改动面**：01 §7 两条新条目；新面落点（L3 或横切）；UI 加页

### 方案 T-3：共享风险清单，档位分设（推荐候选）

- **做法**：**`RiskClass` 与那张清单共享**（分级键空间统一为"范围标识"，config 前缀与动作标识共存于**一张白名单**），但**档位条目分设**：`evolution.authorization`（已有）与 `agent.authorization`（新立）
- **利**：`memory.*` 只标一次，**红线保持单点**；档位各自可调（可"演进保守、运行自主"或反之）；复用 `classify` 与 `PermitDecision` 的全部语义（保守默认、不命中即协作、fail-closed）
- **弊**：需定键空间命名规范以免 config 前缀与动作标识撞车；需说清"一张清单、两档位"的读法
- **改动面**：01 §7 一条新档位条目 + 清单键域扩写；`classify` 由 L6 私有读面提为**共享读面**（或上提契约层）

### 方案 T-4：能力描述体自带风险级（"只能收紧"）

- **做法**：`SkillDescriptor` 像现在声明 `permissions` 一样声明 `risk_class`；闸门读描述体
- **利**：新装 MCP 工具自带分级，无需人工登记
- **弊**：**第三方可自称低风险绕过闸门**。除非规定"描述体**只能收紧不能放宽**"（中心清单判 `collaborative` 的，描述体说 `autonomous-ok` 无效）——但加上这条后，它就退化为 T-3 的**补充**而非替代
- **结论**：**不应单独采用**

**倾向：T-3。** 核心理由是让 08 §7 的 memory 红线保持**单点**——多点登记等于给漂移留口子，而这个项目对"静默放宽"的洁癖（未分类即保守、损坏即不放行）正是它最值钱的工程品性。

## 7. 循环落点方案比选

> **⚠️ 修正报告 §5 的一处假设。** 我在 §5 写"循环天然跨层 ⇒ 可能要改铁律 7 / 新开层"。核过 `DispatchBus` 现状后要改：**跨层这件事项目已经解过了**，用的是**鸭子端口注入**。循环无非是多调几次这些端口。

**这张表决定了选项空间**（循环要够到的目标，相对 L3 的方向与现成通路）：

| 目标 | 相对 L3 | 现成通路 |
|---|---|---|
| L1 工具执行 | 下 | L3 **可直接 import**（`l1`=2 < `l3`=4） |
| L2 记忆读写 | 下 | L3 **可直接 import**（`l2`=3 < `l3`=4） |
| L4 多视角推理 | **上** | 已有鸭子端口 `deliberations=`（`l3/dispatch/bus.py:274-282`） |
| L6 训练 / 提案 | **上** | 已有鸭子端口 `trainings=`（同上） |
| L5 触达 | **上** | 事件 + 调度器，非调用 |
| UI 描述 | 下 | `l3/render/` 已产出（01 §12 定"产出方＝L3"） |

**即：循环要够到的四个上层，通路已经全部存在。落点选在 L3，不需要改任何铁律。**

### 落点 A：L3 内新增 `l3/runtime/`（子模块，非新层）

- **做法**：L3 新增运行时子模块持有 loop；工具执行经 L1、记忆经 L2（均可直接 import），L4/L6 经既有鸭子端口
- **利**：**零规则改动、零层表改动、零存量改写**；L3 职责本就含"任务派发"（`l3/dispatch/`），loop 是其自然延伸；单测住 `tests/l3/`
- **弊**：L3 已很大（现有 10 个子模块）；"运行时"是**横切关注**，塞进 L3 会让它同时是"对话壳"与"执行运行时"；将来若有非对话触发（调度器直接驱动 loop），逻辑要从 L3 反向抽出
- **改动面**：`src/st_agent/l3/runtime/**`（新）；`l3/dispatch/bus.py` 增去向或旁路；`tests/l3/**`

### 落点 B：横切包 `st_agent/agent/`，**不进层表**（同 `ui` / `app` 的处理）

- **做法**：新包承担 loop，**不进 `LAYER_ORDER`**，改由专属用例约束"只向下消费 contracts/l0–l6，且无层反向 import 它"（照抄 `test_ui_is_client_only` 的形态，`tests/test_layering.py:96`）
- **利**：职责独立、可单测；不污染 L3；**不重演"把横切面塞进层表"的反向编码**（D-060 ⑤ 的教训）
- **弊**：**触发方向要解**——loop 由 L3 的用户轮次发起，若 loop 在 `agent/`，则 L3 调它＝L3 import `agent`，而 `agent` 又 import L1/L2；若规定 `agent` 与 `app`/`ui` 同类（**不被任何层 import**），L3 就只能经**组合根注入的端口**发起——那等于 loop 实际由组合根驱动，退化成落点 C 的方向问题
- **改动面**：新包；`tests/test_layering.py` 新增一组约束用例；组合根接线

### 落点 C：新开 L7 运行时层（进层表）

- **做法**：层表加 `l7`，运行时成为第七层
- **利**：职责在架构图上显式
- **弊**：**代价最大，且我判断买不到对应的收益**——
  1. **方向困境**：L7 在 L3 **之上**，而 L3 发起用户轮次却要调 L7 ⇒ 反向依赖。要么走组合根注入（C 退化成 B），要么让运行时**常驻旁路**（L3 只投递任务、运行时异步驱动）——后者把"一轮对话返回结果"变成"投递 + 回调"，**动摇整个 L3 的同步信封语义**
  2. **横切面不该进层表**：这正是 D-060 ⑤ 对 `ui` 的结论——"把 `ui` 塞进层表等于把'不是第七层'反向编码"。运行时与 `ui`/`app` 同属横切，进层表是**重演同一个错误**
  3. **改动面最大**：`tests/test_layering.py`（`LAYER_ORDER` + `APP_ALLOWED_IMPORTS`）、`项目管理/tools/render_ledger.py`（`LAYERS`）、`tests/test_tools.py:219` 的 `L4 < ECO < L5 < L6` 断言链、`docs/技术架构-v2/00-架构总览.md` §2 的六层图与表、`01-平台共享契约.md`、**`CLAUDE.md` 开篇"六层架构 L0–L6"**、`README.md`，另建 `10-L7-*.md`
  4. **存量改写量化**：上述文档与用例均属**活跃区**；已归档的 **177 个任务无需改写**（它们引用层名、不引用层号）——这是唯一的宽慰。但 `CLAUDE.md` 与 `00-架构总览` 是**入口级契约**，改动波及后续所有会话的冷启动口径
- **结论**：只有选"常驻旁路（异步）"路线时，C 才有独立收益；否则相对 B 只是多付改层表的成本

### 落点 D：常驻运行时 + 事件驱动旁路（可与其他落点组合）

- **做法**：运行时**常驻**（像 `Scheduler`），不在 L3 调用栈里。L3 产出"待驱动的循环任务"经 01 §11 事件/端口交给运行时；运行时驱动 loop、调 L1/L2/L4/L6，结果经 L5 渠道回投或回写会话
- **利**：**彻底绕开方向困境**——运行时居最上、永不反向；与项目既有的"事件上行 + 组合根订阅"范式同构（先例：`Scheduler`、`_ChangeNotifier`）；天然支持非对话触发
- **弊**：**异步化**——"一轮对话即返回"变成"投递 + 回调/轮询"，`DispatchOutcome` 的同步信封语义要扩；loop 中途问用户需要新的往返协议（现有确认卡是同步的）
- **改动面**：01 §11 事件（或端口）+ 组合根订阅 + 运行时包

**倾向：先落点 A，为落点 B 留门。** 理由：A 的**零改动**能最快拿到可验证闭环；只要把 loop 的**内部依赖面**设计成"只经端口取用上层"，日后要搬去横切包（B）或常驻旁路（D）都只是**搬家、不是重写**。**不推荐 C**——它付了改层表的成本，却买不到方向困境的解法。

## 8. 最小闭环（T-3 + 落点 A 已定）

### 8.1 插入点已定位（实证）

`l4/deliberation.py:341` 的 `_run_one` 是**证据获取的确定性地带**：

```python
bundle = list(lens.skill_bundle)          # 视角声明的一组 skill_id
for sid in bundle:
    outcome = self._runner.run(sid, {})   # 顺序执行，模型全程不参与
```

**模型只在数据收齐后被叫一次**做方向研判（`l4/ports.py:147` `synthesize(lens, ok_outputs, memory_ids, sufficiency)`）。同理 `l3/dispatch/bus.py:355` 的 `query` 去向也是单次确定性 `runner.run(confirmation.target, ...)`。

> **"自主工具调用"要做的就是：把这两处"固定清单顺序执行"换成"模型在工具目录里逐步选"。** 缝已经找到了。

### 8.2 修正：上一轮一个判断错了

我在 §7 隐含"落点 A 与首刀切 L4 冲突（L4 不能调 L3）"——**错了**。`LAYER_ORDER` 是 `l3`=4 < `l4`=5，**L4 → L3 是向下依赖，机器守卫放行**（`tests/test_layering.py:79` 只拦 `LAYER_ORDER[target] > order`）。且已有先例：`l6/pool.py:33` import `st_agent.l3.feedback`（l6=7 → l3=4）。

但要提醒两条边的**性质不同**：L6 → L3 依赖的是**数据契约**（`FeedbackEvent` 类型），L4 → L3 若发生，依赖的是**运行时行为**。后者重得多。且现状是 **`l4/**` 全层零 import L3**（已核），加这条边是**新增**而非沿用。

**所以落点 A 对两条路径都合法**，差别只在首刀切哪里（见 §8.4 D-b）。

### 8.3 闭环的五个机制

| # | 机制 | 最小形态 | 依赖 | 本期**不做** |
|---|---|---|---|---|
| **M1** | 工具目录暴露 | `SkillRegistry` 的 `SkillDescriptor` 序列化成工具条目（id / 描述 / 参数 schema）进 prompt | 需给 `SkillRunner` 加一个**目录读面**（现只有 `match`） | 工具检索/延迟加载（G14） |
| **M2** | 循环驱动 | 模型输出 `{"action":"call"\|"finish", …}` → 过闸门 → 执行 → 结果回填 → 再决策；**带步数与调用数上界** | M1、M4 | 并行工具调用、子 Agent |
| **M3** | 动作闸门（T-3 落地） | 每步 `classify(scope)`；`autonomous-ok` 放行，其余**终止并交还用户** | T-3 契约落点 | 中途挂起 / 恢复 |
| **M4** | 循环工作上下文 | 任务 + 工具目录 + 已执行动作与结果（超阈值**截断 + `log_ref` 指针**） | 新装配件 | 压缩、外部化 |
| **M5** | 产出接入既有渲染 | 循环产出 `ResultEnvelope`；**链由 `SkillRunner` 自动追加 `skill_run` 步** | 无 | — |

**M5 是个白捡的便宜**：`SkillRunner._execute` 每跑一个 Skill 就 `chain.append_step(...)`（`l1/runner/runner.py:273-279`），所以多步循环**天然产出一整条 trace**——铁律 5（可解释）零额外投入。这也意味着循环的每一步都可被既有 `explain` 去向展开。

### 8.4 关键澄清：G4 **不是**接线 `assemble_context`

我此前把"上下文装配"笼统记为 G4，容易被误读为"把 `assemble_context` 接上"。**两者不是一回事**：

| | `assemble_context`（`l3/chat/session.py:477`） | 循环的工作上下文 |
|---|---|---|
| 内容 | 会话**近端消息** + 记忆切片 | 任务 + **工具目录** + **已执行动作与结果** |
| 预算 | 4000 字符，记忆占 50% | 待定，需容纳工具结果脚手架 |
| 消费者 | L3 会话渲染 | 循环每一轮的模型调用 |

它俩可共用预算工具，但**装配逻辑要新写**。把既有资产当"已建成大半"来规划，是这次最容易踩的坑。

| **D-g** | 中性边界 | 循环中间推理是否外显 | **中间推理不外显**；最终产出为**结构化证据**（非自由文本）交既有渲染件；**不给统一建议**（铁律 4） |

**D-b 我要多说一句**：选项 (b) 的吸引力在于它保护了 `query` 现有语义。项目一路的做法都是"新增面不覆写旧面"（`_build_l3` 只增可选参数、`TickResult` 只增字段、缺省路径逐字节不变）——`query` 的确定性是可审计性的一部分，不该被 loop 的不确定性稀释。

### 8.6 本期明确不做（及为什么）

| 不做 | 为什么可以不做 |
|---|---|
| RAG / 向量检索（G11/G12） | 不在"自主调用工具"的关键路径上。循环证明之后，检索质量是可独立升级的一维 |
| 多 Agent / 子 Agent（G13） | 同上；且它是**上下文隔离**方案，而 M4 已先解决"上下文装得下" |
| 上下文压缩（G6）/ 大输出外部化（G7） | D-e 的截断 + 指针已够跑通；压缩是**规模化后的**优化 |
| 原生 function calling（D-a 的 b） | (a) 已可跑；等端点能力声明扩了再补 |
| 工具检索 / 延迟加载（G14） | 官方 12 个 Skill 的量级不需要；MCP 接多了才需要 |

**一句话**：最小闭环只回答一个问题——**模型能不能在受控闸门下，自己决定调哪个工具、看到结果后再决定下一步**。RAG、多 Agent、上下文压缩都是它**之后**的事。

### 8.7 专论 D-a：三档而非两档，且门控依赖一个未兑现的前提

**结论：原生 function calling 更可靠，且可靠性增益恰好落在循环最脆的两处。** 但要先说清代价落在**哪一层**。

**① 可靠性增益（三点，对应循环的真实失效点）**

| 增益 | 机制 | 对照 T3 的失效模式 |
|---|---|---|
| 参数 schema 由提供方强制 | constrained decoding / grammar | T3 全靠模型自觉。项目**已在擦屁股**：`_parse_json_object` 剥 ``` 围栏（`l4/ports.py:110-112`）、`parse_understanding` 同样剥围栏（`l3/intent/protocol.py:596-599`）——两处都在为 T3 的不守规矩写容错 |
| **"是否结束"有明确信号** | 无 `tool_calls` 即结束 | T3 要模型输出 `{"action":"finish"}`，而模型极易顺手多写一段话——**这是循环终止条件的可靠性**，比参数解析更要命 |
| 工具选择经过训练 | 模型在 tool-use 格式上做过 RL | T3 的"选哪个工具"靠描述文本的字面理解；并行调用无原生支持 |

**② 三档，不是两档**

项目**已声明** `supports_structured_output: True`（`l0/llm/models.py:70`、`l1/runtime.py:98`），但**从未发过 `response_format`**——全仓 grep `response_format` / `json_schema` **零命中**。即现在的"结构化输出"纯粹是 prompt 约定（T3），而能力档却写着 T2。

| 档 | 机制 | schema 强制 | 结束信号 | 本项目成本 |
|---|---|---|---|---|
| **T1** | 原生 function calling | 提供方 | 无歧义 | **L0 对外接口改动** |
| **T2** | `response_format: json_schema` | 提供方 | schema 内一个字段 | **零 L0 改动**，但要把该字段真发出去 |
| **T3** | prompt 约定 JSON | 无 | 靠模型自觉 | 零（现状） |

**T2 值得单独留档**：它以零接口改动拿到 T1 的"schema 强制"这一半收益，代价是**拿不到"结束信号无歧义"**那一半。

**③ 代价落在 L0 对外接口，不在解析层**（铁律 8 序：01 契约 → 02-L0 → 代码）

- `LlmClient.invoke(endpoint_id, prompt, *, …)`（`l0/llm/client.py:105`）签名要能收 `tools`、能回 `tool_calls`
- `StreamEvent`（`l0/llm/models.py:172`，`kind ∈ chunk/done/error`）要加一类或加字段
- `http_transport` 的请求体（`l0/llm/http_transport.py:122-129`）要加 `tools`；`_content_chunks`（现只取 `delta.content`）要加**按 index 拼接 `delta.tool_calls` 增量**——SSE 流式下拼工具调用参数是这堆活里最绕的一处
- 且 transport 的 body 是在 sender 工厂闭包里由 `prompt` 拼的（`:115-129`），新增参数要穿透 `invoke → transport → factory` 三层

**④ 未兑现的前提：能力声明目前是"宽松假设"，不是探测结果**

`l1/runtime.py:98`：

```python
LLM_CAPABILITY = {"max_context_tokens": 128_000, "supports_structured_output": True}
```

其 docstring 自陈：**"取一个不设限的宽松档…真实档位待设置页任务按端点配置"**。也就是说——

> **今天的能力声明是对任意端点的硬编码假设，不是事实。**

**这直接决定门控能不能成立**：若照此把 `supports_function_calling` 也写成宽松 `True`，门控就建在虚构上——**一个假的 `True` 会把 `tools` 发给不认识它的端点，比不门控更糟**。协商机器本身是齐的（`l0/llm/registry.py:155-170` 的 `satisfies()` 能拒），缺的是**被协商的那份数据是真的**。

**⑤ 建议**

1. **协议做成端口**，不硬编码档位——循环（M2）只认端口，T1/T2/T3 是同一接口的三个实现，日后换档不重写循环
2. **T1 先行**：可靠性是目标，而 L0 接口改动迟早要付；若先做 T3，等于先建一半要扔的脚手架
3. **先兑现能力诚实性**：`supports_function_calling` 必须是真的（启动探测一次 / 设置页由用户选），否则门控无意义——**这可能要在 M1 之前插一个 L0 的小任务**
4. **兜底 fail-closed + 显式告知**（同 D-f），不静默退回 T3

### 11.2 陷阱一：启动探测与"幂等播种"相冲

`l1/runtime.py:571` 的 `_seed_llm_records` 明写**"端点已存在即整组跳过"**——幂等播种**不会更新**既有端点记录。而探测的作用恰恰是**更新**能力档。

⇒ **探测必须是播种之后的独立补丁步骤**，不能塞进 `_seed_llm_records`。若塞进去，第二次启动起探测结果永远写不进去（且不报错）。

另两条约束：
- 探测是**出网调用**，须经 `gateway.llm_transport` 并以 `NetworkEvent` 留痕（[02 §6](技术架构-v2/02-L0-本地优先基座.md) 网络活动透明化）——用同一 transport 即免费获得审计
